## 2. 待用户拍板的决策点（开工前置）

**D-A 目标口径**：
- (a) 10× Java（~3.3ms/chunk，重议触发条件原设目标）→ 必须做批量合并（跨 chunk 攒批 + 异步 dispatch + readback 摊销），架构改动大；
- (b) 生产默认启用 GPU channels（追平/略超 Java + 释放 CPU）→ 改动小（门控翻转 + 优雅回退硬化 + dll/spv 打包进 jar），但性能收益可能为负（369ms/chunk 小批量教训 vs 27.69 CPU）——**若不解决摊销，(b) 单独不成立**；
- 推荐：以 (a) 的摊销架构为课题主体，(b) 是其验收形态（摊销达标后才谈默认启用）。

**D-B 载体路线**：
- (a) 沿用 C++ gpu_ffi.dll FFI（现成、已验证；代价 = C++ 已归档但需维护 build.ps1 -Ffi + 发布链打包 dll+spv + 跨编译器 ABI）；
- (b) Rust 原生 GPU（wgpu/vulkan-rs 重写 GpuDensityEngine）——单一工具链、发布干净，但重写+重验证成本高（shader 可复用 spv）；
- 本计划默认 (a)（spv 与引擎已验证逐位对齐，重写违反「不放弃但也不做无谓重写」）；(b) 列为远期。

**D-C 批量架构**（若 D-A=(a)）：
- 攒批窗口设计：worldgen 线程模型（chunk 并发 fill）→ GPU 提交单线程化 + 56+ chunk 攒批 → 双缓冲（计算/回读重叠）；风险 = 引入延迟/顺序依赖，需与线程池铁律（丢失唤醒前科）联审。

## 4. 风险 & 回退
- GPU 提交与多线程 fill 并发 → 驱动层崩溃前科（P2-4，0xC0000005）：保 Mutex 串行 + 攒批在同锁内。
- 零退化铁律：所有 GPU 路径默认关，验收含「门控关闭 = 逐位 1.0.27」。
- 摊销不达标（<1ms/chunk 不可达）→ 负面结论落盘回退（D24/D25 先例，负面结论也是结论）。
