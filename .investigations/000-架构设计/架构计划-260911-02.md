## 2. 已知事实（Phase 0 前置，来自日志 triage + 源码核对）

1. 执行体 = 最新产物（`sha256=dd3b645f…`，含 ca_min 门控微修），`stageMask=3` 三维度 enabled。
2. 载体 = **集成服**（客户端 + 服务端同 JVM），VD 10→32、模拟距离 32，旁观飞行 ~2 min。
3. seed `7349435828306001495` 与 260910-08 §6「朋友报告」同 seed ⇒ 同机/同人两次报告（待确认）。
4. CoreSwap 异步池 = `Util.getMainWorkerExecutor()`，**与 vanilla 同阶段同池**（`NoiseChunkGeneratorMixin.java:61-68`）⇒ 朴素「池争用」假设需形态差证据。
5. 本块 A/B 载体（dev server + Chunky，无客户端）**结构性覆盖不到**集成服争用面（verdict-260911-01 §3 ⚠️）。

## 3. 候选假设（互斥，Phase 2 必须 fan-out）

- **H1 客户端共享工作池争用**：客户端区块网格构建与异步 worldgen 抢同一池；需证「CoreSwap 的占用形态与 vanilla 可辨差」（否则 vanilla 应同样卡）。
- **H2 对照缺失假象**：VD32 + 高速飞行本身极端负载，同机 vanilla 同样卡（#64/#65）。
- **H3 跨 JNI 形态差**：CoreSwap 每 chunk 393KB 级数据跨 JNI + Java 侧逐块写回，与 vanilla 直写 PalettedContainer 的分配/GC/锁形态不同；突发请求下尾延迟与 GC 停顿可辨。
- **H4 ca_min 门控微修引入**（必须排除的自家嫌疑）：理论方向相反（修后工作量严格减少），但需实测排除——用上一版 jar（297680e7）同场景对照。
