## 依据（Phase 1 实测，`f2-phase1-cost-split.md`）

- 单线程真值 50 ms/chunk；池宽 23 时膨胀 96 ms（1.9×），总 CPU +42%（331→471 cpuSec）。
- wall 在池宽 11 已与 23 持平（41 vs 38 s）⇒ 超订不换吞吐、只烧 CPU。
- 机制：vivo 路径并发度 = Java 池宽（cores-1=23），引擎设计的 `physical-2=10` 被绕过（只 spawn 空转线程）。

## 改动（单点）

`NoiseChunkGeneratorMixin.wgDispatch`（`:92-98`，三分支唯一分派点）加**信号量背压**：

- 许可在**调用线程**（worldgen 车道）获取 → 池内只跑已获许可的任务（避免阻塞池线程）。
- 任务完成（`whenComplete`）释放；提交失败路径也释放（防泄漏）。
- 规模：`-Dcoreswap.maxinflight=N` 显式覆盖；**默认 = 物理核-2**（与引擎 `adaptive_threads` 同源：`logical/2 - 2`，本机 24 逻辑 → 10）；`N<=0` = 不限（旧行为）。
- `-Dcoreswap.syncfill=1` 路径不受影响（内联执行，无并发）。

## 验证（预置）

1. **行为门（MUST，零差异）**：`-Dcoreswap.mixlog=1` 下逐 chunk `[WG-CONTENT] hash=` 在「不限 vs 限 10」两臂**逐 chunk 相同**（同 seed/region）——限流只改调度，内容必须逐位一致。
2. **性能门**：3 臂交错 bench（不限 / 10 / 6），比 wall + cpuSec + `[PERFPROF] fill=`。
3. **实机门（决定性）**：用户客户端实机跑 N 扫描（默认 / 8 / 6 / 4），看 FPS 与 `inflight max`。
4. **门禁**：`scan_cpp_anchors.py invalid=0`（若触及 Rust；本次预期不触及）。

## 风险

- 许可泄漏 → 全部许可被占 = 永久停顿。缓解：提交失败释放 + `whenComplete` 释放 + 日志计数（`[WG-INFLIGHT]`）。
- 车道阻塞过久 → 区块加载变慢（有意代价，可调 N）。
- 不影响内容（由行为门证明）。
