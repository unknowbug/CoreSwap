# RE-Framework 同步申请：core-knowledge 增加「项目级错误记录强化」适配说明
# 来源：CoreSwap（E:\PYTHON\CoreSwap）2026-08-15 用户拍板方案 C
# 用途：供 RE-Framework 维护侧评估是否在框架层（core-knowledge skill / 模板）同步增强

---

## 一、背景（为什么提这个）

CoreSwap 项目在 2026-08-13 用户明确「错误优先原则」：**错误信息 + 详细记录「为什么错」比验证通过的正确结论更重要**（已写入项目 AGENTS.md 三-2，含五段式格式、判错经验沉淀、错误台账独立成篇纪律）。

但在 2026-08-15 实践中发现：知识库更新 subagent 加载的是框架通用 **core-knowledge skill**，其错误记录要求是「通用错误账本条目格式」（errors/error-NNN-*.md，含错误现象/诊断过程/排除/结论四段），**缺少项目级强化的三处**：

1. **五段式格式**（现象→根因→定位→修复→教训）vs skill 的四段式（现象/诊断/结论/排除后认识）——结构相近但命名与深度要求不同；skill 未写「不得只记『已修复』而不记『为什么错』」。
2. **判错经验沉淀要求**：项目要求「符号级错误一定是结构错不是精度错，先查公式/索引/坐标」这类**可复用判错方法**必须沉淀；skill 未强化。
3. **载体灵活性**：skill 写死 `knowledge/errors/error-NNN-*.md` 独立文件；项目实际用 `.investigations/<课题>/<课题>-errors.md` 独立成篇 + 末尾速查表（A-G/D 系列一个文件）——框架通用层未说明「项目可自定义错误台账载体」。

本次 D22 草稿质量达标，是靠 prompt 显式要求「按现象→根因→定位→修复→教训格式（参照 D21）」兜底，**不是 skill 自动保证**。

## 二、CoreSwap 侧已落地的适配（方案 C，2026-08-15）

- 新建 `knowledge/SUBAGENT-KNOWLEDGE-GUIDE.md`（项目级知识库产出须知）：错误优先原则 + 五段式格式 + 项目载体映射 + 产出自检清单。
- 引用方式：派知识库 subagent 的 prompt 加一行「先读该文件，按其中格式与载体要求产出草稿」。
- 优先级：项目级文件 > 框架通用 skill（与 AGENTS.md 优先级规则一致）。

## 三、建议框架层同步的内容（供评估，非强制）

若 RE-Framework 认为该强化有跨项目通用价值，可在 core-knowledge skill 增加一节「项目级错误记录强化（可选适配）」：

```markdown
## 项目级错误记录强化（框架可选适配，2026-08-15 CoreSwap 提议）

- **错误 > 正确**是通用原则（已含），但项目可定义更高详实度要求：
  - 五段式：现象（具体数据）→ 根因（机制层面，为什么错）→ 定位（诊断方法/工具）→ 修复（改了什么）→ 教训（下次避坑 + 可复用判错经验）；
  - **不得只记「已修复」不记「为什么错」**；被排除假说完整保留（排除链条是核心资产）。
- **判错经验**（可复用的判错方法，如「符号级错误一定是结构错不是精度错，先查公式/索引/坐标」）必须沉淀，比单条错误更有价值。
- **载体灵活**：错误台账默认 `knowledge/errors/error-NNN-*.md`，但**项目可自定义独立错误台账文件**（如 `.investigations/<课题>/<课题>-errors.md` + 末尾速查表）——skill 应允许「项目指定载体」而非写死目录。
- 项目可用 `SUBAGENT-KNOWLEDGE-GUIDE.md` 类文件承载项目级强化，prompt 一行引用；框架 skill 保持通用层（错误优先 + 条目格式基线）。
```

## 四、同步边界建议

- 框架 skill 保持「通用基线」（错误 > 正确、条目格式、已排除保留）不变；
- 项目级强化（五段式、判错经验、载体映射）归项目侧文件（SUBAGENT-KNOWLEDGE-GUIDE.md 模式），框架提供「可被项目覆盖」的说明即可；
- 若框架要内置五段式，建议在 skill 错误账本条目格式里把「诊断过程」段改名/补充为「定位（诊断方法/工具）」并加「教训（可复用判错经验）」段——与 CoreSwap 五段式对齐。
