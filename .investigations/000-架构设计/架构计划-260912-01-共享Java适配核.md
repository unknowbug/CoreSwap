## 3. 关键设计决策（**需用户拍板**）

### D-1 共享机制（三选一）
| 选项 | 形态 | 结论 |
|---|---|---|
| **M1（推荐）** | 新增仓库根 `java-core/src/main/java/`（非 mixin 共享源，与 `worldgen-core/` 命名对称）；两版 `build.gradle` 各加一行 `sourceSets.main.java.srcDir('../../../java-core/src/main/java')`；铁律「**一个类只有一个家**」（共享 or 分版，不得两处存在） | 成本最低、无第二真相源、mixin AP/refmap 天然同 source set |
| M2 | gradle 子工程 / composite build + jar 依赖 | ❌ 否决：共享源必须**在每版映射下**编译（mixin/loom），子工程产出要按版本二次 remap（两个 artifact + 版本耦合），且 refmap/AP 跨 source set 易碎 |
| M3 | 生成式（单一模板 + 版本补丁代码生成） | ❌ 否决：引入构建期生成器 = 第二真相源，与「源码即事实」冲突；仅在 M1 个别文件不可行时局部回退 |

### D-2 抽取边界（三档，可递进）
- **范围 A（最小运行时核，推荐起步）**：`CppWorldgen` / `CppBridge` / `BulkWb` / `StallWatch` / `ChunkTiming` / `CoreSwapFixHelper` / `WgDiag` / `BenchMod` + 新版 `WgCompat` shim（分版）；mixin **全部留分版**。
- **范围 B（A + 探针全量）**：再加 16 个探针文件（差异几乎全是 `Identifier.of`/`getOrThrow` 改名）⇒ 消掉最大宗重复；成本 = 每文件双映射编译核对。
- **范围 C（A + mixin 体抽取）**：把 `NoiseChunkGeneratorMixin` 的主体逻辑抽到共享 `FillDispatch`，mixin 只留注入签名（`populateNoise` 5 参/4 参差异由分版签名承载）。

### D-3 语义统一方向（差异的处置原则，逐项登记后实施）
1. **1.20.1 超前项**（A1a 跳空气、A1b 扫描门控、A2 三维持指纹门、exec、P1、StallWatch、C/bulk）→ 进共享核；**1.21.6 侧默认行为是否同步翻转**由 D-4 决定。
2. **1.21.6 独有项**（`rustFeaturesTakeover()` 谓词、`ChunkTiming` 全分项、carve 计时 mixin、`-PmaxBgThreads`/`-PcaMin` 接线）→ 进共享核（谓词共享、无消费者即无害）；**mixin 与 gradle 接线留分版**。
3. **纯 API 改名**（`Identifier.of` / `getOrThrow`）→ 收进分版 `WgCompat`，共享文件保持单一写法。
4. **反向回灌**（B2 §11 八子项）→ 只登记不实施（不变）。

### D-4 C（bulk 写回）与 A1a/A1b 在 1.21.6 的落地方式
- **(i)（推荐）** 共享代码 + 分版默认常量：`WgCompat.BULKWB_DEFAULT=false`（1.21.6 先走旧逐块路径，行为不变；老路径**保留不删**是既有事实）⇒ 抽取与语义变更**解耦**，抽取本身是等价重构；1.21.6 随后单独翻转 + 自己的 Tier 1-4。
- (ii) 抽取时同步启用 ⇒ 1.21.6 直接换写法，抽取与语义变更耦合在一批 commit，验证面变大、回退粒度变粗。

### D-5 与出货线/工单的时序
- 抽取**不使已发布 1.0.29 工单失效**（工单以已构建 jar 的 sha 为唯一判据）。
- 但**抽取后若需重发 1.20.1**，该次重发 MUST 走「抽取后全量回归 + 三元组重算」，**不得沿用 1.0.29 验证记录**（KB #121 防陈旧书面化）。
- 抽取期间**冻结 1.20.1 jar**（抽取前先建一次 pre jar 并记 sha + 条目级清单，见 §5 V1）。

## 14. 执行期补登（260912-01：wave 0/1 实测后，判据修正）

### 14.1 V1 的适用边界（原 §5 表述过宽，实测后修正）

- **V1-strict（严格字节相等）只适用于「纯移动子集」**：wave 1 已实测 PASS——3 个逐字节相同的类（`CppWorldgen`/`WgDiag`/`BenchMod`）移入 `java-core/` 后，两版 jar **整文件 sha 不变**（条目 1081/1081、1798/1798 全等）。V0（仅加空 srcDir）亦 PASS ⇒ 机制与工具链端到端可用。
- **分叉文件波次（`CppBridge`/`ChunkTiming`/`CoreSwapFixHelper`/`BulkWb`/`StallWatch`）不适用 V1-strict**：共享化必然改变至少一侧的 class 字节（引入 `WgCompat` 间接层、超集代码、分版默认常量）。此时判据拆为三条：
  1. **V1b-1**：**未变更侧**的条目 MUST 逐字节不变（若两侧都变，该文件无「字节锚」，MUST 显式声明并说明为何两侧都必须变）；
  2. **V1b-2**：变更条目 MUST **逐条声明**（文件 + 变更性质 + 依据）并由 judge 人工核对（`jar_manifest_diff.py --expect` 只做归类，**归类 ≠ 声明**）；
  3. **V1b-3**：**任何 class 字节发生变化的版本 MUST 补跑 V2 + V3**（build/run 回归 + 行为门）——「jar 不同」不再蕴含「行为相同」。
- **反向蕴含（省成本判据）**：纯移动波次（jar 字节相同）**V2/V3 被蕴含**（同一执行体 ⇒ 行为必然相同），无需重复跑；该判据已写进 `record §4.1` 防后波次偷懒或重复劳动。

### 14.2 计划期断言失真自查（KB #25 家族，本计划自身一例）

- 原 §5 把 V1 写成「对全范围统一」的判据，**第一波实施即发现其边界**（纯移动 vs 语义统一在产物字节上性质不同）。
- **教训（可复用）**：**结构性重构的等价门必须按「是否改变产物字节」分层**，不能一刀切；「等价重构」与「语义统一」的验证判据不可混用同一条。已记入 record；是否升格为 discovered 条目由知识库步骤（subagent 草稿 + 价值门）判定。
- **对计划的处置**：本 §14 为**追加式补登**（原 §5 正文不改，仅加适用边界指针），符合「判据修正留痕」纪律。
