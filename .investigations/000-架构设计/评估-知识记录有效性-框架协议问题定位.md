# 评估报告：知识/结论记录机制的有效性 —— 框架与协议的问题定位

> **目的**: 回应用户对「结论性内容记录有效性」的怀疑（用户选择 A：现有流程产出大部分是垃圾，尤其结论类）。
> **范围**: 只审查「记录/知识沉淀」相关机制，不审查验证协议主体（anchor/source/staleness 等是 Anchorlaw 的核心价值，不在本次质疑范围）。
> **方法**: 通读 RE Framework `spec/engineering-framework-v1.md`、`dsh/skills/core-knowledge`、`core-artifact`、`core-worker`、`core-judge`；Anchorlaw `spec/protocol-v0.18.md`（§3/§9/§13/§14/§15/§16）；对照 CoreSwap 实际载体（`rust-errors.md`、`docs/`、`knowledge/INDEX.md`、`SUBAGENT-KNOWLEDGE-GUIDE.md`）。
> **一句话结论**: 用户直觉是对的——但问题**不是**「框架要求记录」，而是框架/协议把**记录义务的边界划得太宽且相互矛盾**，导致执行者把预算花在低价值的"结论复盘"上，而真正高价值的"可复用判据"反而散落。真正该改的是 RE 框架 §6 + core-knowledge 的**范围与优先级**，以及 Anchorlaw 的**噪声卡片/产物契约的非区分求全**。CoreSwap 的 drift 是次要放大器。

---

## 0. 先分清三个独立来源（评估的骨架）

记录义务分散在三个机层，各有不同角色：

| 来源 | 内容 | 记录义务的性质 |
|---|---|---|
| **RE 框架 §6 / core-knowledge** | 知识库生长机制 | **最高优先级**——明确"错误 > 正确"，且错误链条详实度最高 |
| **Anchorlaw §3 / §15.2 / §5.5** | 噪声卡片 + 产物契约 + source 落盘 | **验证可追溯性**——记录是为了"能复核"，不是"长知识" |
| **RE 框架 §4.5 第四条 / CoreSwap AGENTS.md 九** | 结论性 docs 必须 subagent 产出 | **流程分权**——防"主会话自评污染" |

关键发现：**这三者内部都对"记录"有强需求，但它们没有区分"为什么记"**。这造成了你感受到的"记录负担"。

## 1. 用户判断的合理性（哪些记录确实低价值）

### 1.1 框架自己就把"错误"定位为最高价值——而"正确结论"不是

`engineering-framework-v1.md` §6 L422-424 原文：

> **优先级：错误信息 > 正确信息。** 错误/失败链条（现象 → 诊断 → 排除 → 发现）是知识库最高优先级资产……

`core-knowledge/SKILL.md` L19-25 原文：

> **错误信息是知识库的最高优先级资产**——正确结论只记录"是什么"，错误链条记录"不是什么 + 为什么"

**框架的原始意图就是"错误 > 正确"**。而我在本 session 做的事（`rootcause-seed-contamination.md` 结论、`cherry-basin-location.md` 纯位置、`block-gap-*.md` 缺口分析）**大多数是"正确结论"类**——这类按框架自己的话，只该"记录是什么"（格式从简），不该占用详实度预算。

**所以用户说"结论性内容不值得记"——框架自己大体上也同意，是执行者（我）没按这个优先级执行。** 这是第一个确认点。

### 1.2 但框架里确实存在"过度记录正确结论"的条款

框架 §6 和 core-knowledge 有个内在矛盾：
- §6 L426 说"任何阶段发现可复用知识 → 立即写入"（笼统，未分"正确 vs 错误"级别）
- §6 L427 触发条件里包含"编译器/语言惯用法"、"算法/协议指纹"、"跨模块通用模式"——**这些是"正确结论"类**，框架也要求记。

`biome_params.json` 里 cherry_grove 的 60 行 ranges、`cherry basin 在 x 64..256` 这种，就是这种"正确结论"。框架对它们的记录要求**没有区分"会不会复用"**，导致我按"发现了就记"机械执行。

**这正是用户直觉的第二层：框架对"正确结论"的记录没设价值门，逼着执行者什么都记。**

## 2. 框架层面的真实设计问题（需要改 RE 框架）

### P1. §6 / core-knowledge 的记录价值门缺失（最高优先级问题）

**问题**: 框架只规定"错误 > 正确"，但**没有定义"什么算值得记录的正确结论"**。§6 触发表（L427）把"语言惯用法/算法指纹/通用模式"一律列为写入对象，无"复用价值"过滤器。

**证据**: `core-knowledge/SKILL.md` L134 载体灵活节明确说"项目可指定独立错误台账载体"，且 L127-135 把"五段式/判错经验/载体灵活/SUBAGENT guide"都标为 **"项目级可选强化（2026-08-15 CoreSwap 提议）"**——**框架自己承认这是 CoreSwap 提议、非框架强制**。这说明框架层对"记录强度"本就打算让项目自定，但 §6 主体部分（L426-430）却用"任何阶段发现可复用知识→立即写入"这种**无差别全量记录**措辞，与"项目可选强化"存在**张力**。

**建议改法（给 RE 框架）**:
- §6 增加**记录价值门**（复用判据）：
  - 只记"若再遇到，我不想重新想一遍"的**判据/经验**（错误签名、判错方法、环境坑）
  - 不记"自推可得"的一次性**结论**（某种子地形、某次跑出的数值）
- 触发表 L427 拆分：高价值（错误/坑/判错经验/反模式）→ 必记；中价值（算法指纹/惯用法）→ 简记；低价值（一次性结论）→ 不记。
- 显式声明："结论性 docs（主题篇/时间线）**不是**知识库的核心资产，无复用价值的结论不写进去"。

### P2. §4.5 / core-knowledge「结论性 docs 必须 subagent 产出」与"记录价值门"冲突

**问题**: `core-knowledge/SKILL.md` L56-65 和框架 §4.5 L320-332 规定**结论性 docs 必须 subagent 产出草稿**（防主会话自评污染）。这个机制**有效但昂贵**——每次结论落盘都需一次 subagent 迭代。如果结论本身无复用价值（P1 的"正确结论"），这个 subagent 产出纯属浪费。

**证据**: 本 session 我写 `rootcause-seed-contamination.md`（错误链）时，按流程应走 subagent；但若按 P1 的分层，这类**结论**根本不该进 docs。

**建议改法**:
- 把"必须 subagent 产出"的强制范围**收窄到 P1 判定的"高价值记录"**（错误链/判据/反模式）。
- 无复用价值的结论 → **不写 docs**（不是"subagent 写"，而是"根本不写"）。
- 保留 subagent 产出路径给真正的知识资产。

### P3. 知识库载体双轨（`discovered/errors/` vs 项目级台账）存在未消除的规则重叠

**问题**: 框架 §6 L423 规定错误进 `knowledge/discovered/errors/error-<NNN>-<slug>.md`；但 §6 L429 + core-knowledge L134 + CoreSwap AGENTS.md 三规定"载体灵活"，允许项目指定 `.investigations/<课题>/<课题>-errors.md` + 速查表。**两条规则并存，未明确"哪个优先"**——CoreSwap 用了后者（`rust-errors.md`），但 `knowledge/discovered/errors/` 目录因此空置，实际上框架默认路径在 CoreSwap 是**死规则**。

**证据**: `knowledge/discovered/errors/` 目录不存在（`Exit code 1`），`knowledge/INDEX.md` 分类入口里**没有任何 errors 类目**——说明框架默认的"错误账本独立文件"路径在 CoreSwap 完全没落地，替换成了项目级台账。这是**规范化代沟**，不是坏设计，但规则文档没说清。

**建议改法**:
- 框架明确"载体选择优先级"：项目级指定载体（如 SUBAGENT-KNOWLEDGE-GUIDE.md）> 框架默认 `discovered/errors/`。并声明"按项目约定写入，不写死目录"（@ L134，框架已部分这么说，但需在 §6 主体对齐）。

## 3. Anchorlaw 层面的问题（需要改协议）

### P4. §15.2「产物必须落盘」与 §5.5「source 必须可查」——可追溯性 vs 知识含量的混淆

**问题**: Anchorlaw 的 §15.2 L1114-1115 说"subprocess MUST 持久化输出为 artifacts（artifacts 是执行的跨会话记忆）"、§5.5 L628 说"source 引用必须能查找到"、§3 噪声卡片 L500 问"这个失败产生了什么新知识？"。这些是**验证可追溯性**——**为了保护"输出可复核"和"测试能重跑"**，不是"为了积累知识"。

**但 §3 噪声卡片的 `discovery` / `curriculum` 字段（L500/L504）把"失败 → 新知识 → 可复用课程"当成了义务**。这会把 Anchorlaw 从"验证协议"悄悄扩展成"知识沉淀协议"——**职责外扩**，引发你感觉的"记录负担"。

**证据**: 协议标题自称"语言无关的**代码验证协议**规范"（L3），核心原则"任何声称必须有可验证的实践锚点"（L5）——是**验证**协议。但噪声卡片的 `discovery`/`curriculum` 字段（L500/504）要求记录**知识**，§15.2 把 artifact 定义为"跨会话记忆"——**验证（可复核）与知识（可复用）两概念未分离**。

**建议改法（给 Anchorlaw）**:
- §3 噪声卡片：把 `discovery`/`curriculum` 字段从"必填语义"降为"可选"，或明确它们**只服务验证回溯**（记录当时为何如此判），不承担"沉淀通用知识"的职责。
- §15.2 把"artifact 是跨会话记忆"改为"artifact 是验证可复核性载体"；知识沉淀移交给独立知识机制（如 RE 框架 §6 或专门知识协议，非 Anchorlaw 职责）。
- 保持验证域的**强记录**（source/staleness/产物健全），这是协议核心价值，**不要削弱**。

### P5. Anchorlaw 的"知识"被 §14 定义为 skill manifest / 模块化（非知识内容）

**问题**: 我把 §14 当知识沉淀看，但它其实是 **Agent Skill Manifest**——定义"技能怎么组织"（L941 "分层、单一职责的技能把协议知识从常驻上下文移到按需 playbook"），**不是"项目知识怎么记录"**。所以 Anchorlaw 本身对"知识内容沉淀"**几乎无要求**（§3 噪声卡片除外），主知识沉淀责任在 RE 框架 §6。

**结论**: Anchorlaw 的问题是**职责混淆**（§3 噪声卡片把验证反思写成知识），不是"要求过度记录"。**这减轻了 Anchorlaw 侧需要改动的范围——只要把 §3 的 discovery/curriculum 定位改清楚即可。**

## 4. CoreSwap 项目级 drift（次要，但真实）

### P6. CoreSwap 把"五段式"当成了"结论复盘"的强格式，而非"错误台账"格式

**问题**: `SUBAGENT-KNOWLEDGE-GUIDE.md` §一 说"错误信息 > 正确信息"，§二 定义五段式（现象/根因/定位/修复/教训）。这是**错误账本的格式**（正确）。但我（执行者）却用它去包装**结论性内容**——`rootcause-seed-contamination.md`（种子污染）本质是"错误链"，用五段式**对了**；但 `cherry-basin-location.md`（位置结论）也强套"证据链/结论"结构，就把五段式**误用**在正确结论上。

**证据**: `SUBAGENT-KNOWLEDGE-GUIDE.md` L16 "排查中遇到的每个错误/踩坑 MUST 按五段式完整记录"——明确是**错误**用五段式，不是结论。我把它套用到结论类，是执行错误。

**建议改法（CoreSwap 侧，不改框架）**:
- 明确五段式**专属错误/坑**；结论类走"简洁结论"格式（是什么），不进五段式。
- 修正 `SUBAGENT-KNOWLEDGE-GUIDE.md` 首行说明："五段式仅用于错误/踩坑，正确结论用单行结论格式"。

### P7. CoreSwap 的 `rust-errors.md`（错误台账）实际是正确载体——但它混写了对齐结论

**问题**: `rust-errors.md` R1-R5 是**五段式错误台账**（正确载体，符合框架"载体灵活"）。但 R1 的"修复"/"教训"段把"对拍 buildNode 用当前 C++ 参照"这种**方法论**也写进去了——这其实是"判错经验"（框架说高价值、该沉淀），**方向对**。问题只是：它和 `rootcause-*.md`/`cherry-basin-*.md`（结论类）**混在同一 `.investigations/rust-density-builder/` 目录**，没有按"错误台账 vs 结论"分文件边界，造成"什么都记"的观感。

**建议改法（CoreSwap 侧）**:
- 明确 `.investigations/rust-density-builder/rust-errors.md` = 错误台账（五段式，错误/坑/判错经验）；`rootcause-*`/`cherry-basin-*` = 结论/发现（简洁格式）——**二者职责已在文档标题写清**，只需在 AGENTS.md 提示"错误台账与结论分文件，勿混"。

| **P1** | RE 框架 §6 + core-knowledge | 加"记录价值门"：只记判据/坑/错误，不记一次性结论；触发表拆分必记/简记/不记 | 中（skell + spec 各加一段） |
| **P4** | Anchorlaw §3 噪声卡片 | 把 `discovery`/`curriculum` 从"知识沉淀义务"降为"验证反思可选"；§15.2"跨会话记忆"改"验证可复核载体" | 小（措辞调整） |

## 7. 结论（直接回答用户）

1. **你的怀疑成立**：目前的记录流程，产出大量"结论类"文档（`cherry-basin-location.md`、`rootcause-*.md` 结论段、`block-gap-*.md`），这些是"正确结论"——框架自己说"正确结论只记是什么、格式从简"，而执行者（我）没按此执行，把它们写成了详实文档。**这部分确实不值。**

2. **但"记录"本身不是问题**：真正高价值的是**错误链/判据/判错经验**（R5"air 区吻合+ground 带全错=参照错"这种签名判据），这些是框架明确要的高优先级资产，也确实有用。

3. **要改的是框架/协议，不是放弃记录**：
   - **RE 框架 §6**：加"记录价值门"，只让高价值（错误/判据/坑/反模式）进知识库，一次性正确结论不记。
   - **Anchorlaw §3**：噪声卡片的 `discovery`/`curriculum` 从"知识沉淀"降为"验证反思可选"——Anchorlaw 是验证协议，不该扩张成知识协议。
   - **CoreSwap**：五段式专属错误；错误台账与结论分文件；清理误用。

4. **不动的部分**：Anchorlaw 验证可追溯性（source/产物契约/健康状态）、RE 置信度状态机、judge 强制触发点、错误优先 + 被排除假说不删——这些是框架/协议核心价值，且正是本次没把"种子污染"误判成"Re没 bug"的真正保障。

> **诚实声明**：本报告为评估（candidate）。§6 P1/P2、§3 P4 涉及框架/协议改动，需你评估后在 RE-Framework / Anchorlaw 仓库层面裁决；CoreSwap 侧 P6/P7 为本地修正，我可直接执行。
