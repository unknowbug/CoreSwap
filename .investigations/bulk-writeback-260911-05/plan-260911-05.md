## 1. 目标与非目标

**目标（按优先级）**
1. **可移植性**：把「写回」从每版本 fork 的 Java 热循环，变成**一份共享实现**（消掉 per-version 的 `writeChunk` 逐块循环 + 其配套诊断 A1a/A1b/WBCHECK/读回自证）。
2. **去掉每块开销**：`98,304 次 setBlockState/chunk`（palette 搜索 + 3 个派生计数更新 + section 锁）→ 整段构建 + 一次数组元素交换。
3. 若第 2 项实测有剩余收益，**再**决定是否把 palette 生成下推到 Rust（阶段 2，见 §3 D2）。

**非目标（本计划不做）**
- 不改 Rust 填充算法、不改数据驱动边界（阶段 1）。
- 不改 stageMask / carver / features 接管语义。
- 不追 wall 级性能结论（见 §2 收益天花板）。

## 2. 证据基线（一手，决定「值不值得」与「怎么验」）

### 2.1 可行性：整段替换**无需新增 mixin**（scout 决定性事实 #1）
- `Chunk.getSectionArray()` **返回活引用**（非 clone）：1.20.1 `Chunk.java:163-165`、1.21.6 `:171-173`（`return this.sectionArray;`）⇒ `chunk.getSectionArray()[i] = newSection;` 即完整替换路径（字段 `protected final` 只约束引用重绑）。
- `ChunkSection(PalettedContainer, ReadableContainer)` 两版**均 public**，且构造器内自动 `calculateCounts()` 重算 3 个派生计数（`ChunkSection.java:27-31`）⇒ **R1（派生计数失真）由走 public 构造器天然规避**；biome 容器可用 `getBiomeContainer()` 原样带入。
- vanilla 自身就有同款先例：序列化读路径 `new ChunkSection(pc, rc)` 后放进 section 数组（1.20.1 `ChunkSerializer.java:93/124`；1.21.6 `SerializedChunk.java:170/211`）。
- 高度图也有现成整段写通道：`Chunk.setHeightmap(Type, long[])` → `Heightmap.setTo` → `arraycopy`（1.20.1 `Chunk.java:175-177`、1.21.6 `:183-185`），**无需 accessor**。

### 2.2 收益天花板 = **6.2%**（且现有最强行为门对本变更「瞎」）
- 1.20.1 一手：`[PERFPROF] n=4096 fill=95.77 scan=0.09 **write=6.39** height=0.42 sum=102.67 ms/chunk` ⇒ write = **6.2%**（`.investigations/vivo-stutter-260911-02/f2-phase1-cost-split.md:10`+`:14-21`；载体 = dev server + Chunky r500 + dll `dd3b645f` + mask=3 + async + 池宽 23）。
- 1.21.6 另有 `write=3.50`（`perf-regression-260910-04/record.md:60`，n=1024）——**与 6.39 不可互引**（不同版本/构建态/池宽，§9.7 载体要素）。
- 1.20.1 侧 `ChunkTiming` **无 write 分项**（`ChunkTiming.java:9-12` 自陈）⇒ 1.20.1 的写回成本只能用 `[PERFPROF]` 类临时计时器复现。
- ⚠️ **`[WG-CONTENT]` 指纹门对本变更不敏感**（scout 决定性事实 #2）：它 hash 的是 **Rust 输出的 `buf`**（`CppBridge.java:381-391`），而 bulk 写回只改 **Java 侧消费** ⇒ buf 不变则 hash 必然相同，**该门不可能检出写回回归**；1.21.6 侧该门还整体缺失。
- ⇒ **结论（须写进结论）**：C 的正当性 = **可维护性/可移植性**，**不是** wall 性能；6.2% 上限会被 ±10% 噪声带淹没（#103），单 run wall A/B 大概率**测不出**（须用配对交错或计数/指纹型判据）。

### 2.3 palette 契约的硬机械约束（决定 D2 是否值得）
- `PaletteProvider.BLOCK_STATE.createDataProvider`：distinct state **≤256** → 局部 palette（ARRAY 4bit / BI_MAP 5-8bit，**palette 列表顺序 = 索引顺序**）；**>256 → `ID_LIST`，其 storage 索引是全局 `Block.STATE_IDS` raw id，且传入的 palette 列表被忽略**（`IdListPalette.java:19-27`）。storage 宽度须用 `dataProvider.bits()` 而非 `getBits()`。
- Rust 侧只有 **block 注册表 raw id**（`blocks.rs:9`），与 `Block.STATE_IDS`（block **state** id 域）**无映射表** ⇒ 若让 Rust 直接产出「可构造的 palette」，须新增 raw-id→state-id 数据源（`data-driven-boundary.md` 全文 55 行**对 palette/位打包/序列化布局零条目**）。
- `worldgen-core` 全树**无任何 palette / 位打包实现**（grep 无命中）。

## 3. 设计决策（**三选一，需你批准**）

| 选项 | 形态 | 收益 | 代价/风险 |
|---|---|---|---|
| **D1（推荐）** | **Java 侧 bulk apply，Rust 零改动**：Rust 仍输出扁平 `int[]`（raw block id，y-major，现有契约不变）；Java 在**共享适配核**内：① 每 section 一遍去重建 palette（raw id → `BlockState`，走既有 `Registries.BLOCK` 缓存路径）② 一遍位打包 ③ `new ChunkSection(pc, oldBiome)` ④ 写回 `getSectionArray()[i]` | 消掉 98,304 次 `setBlockState`（含锁与 3 计数更新）+ A1a/A1b/WBCHECK 整套诊断从分版面消失；Rust/JNI/数据驱动边界**零改动**；MC 编码逻辑留在 Java（换版本只改薄适配） | Java 侧多两遍顺序扫描（**未实测**）；编码分支须覆盖 ARRAY/BI_MAP/**ID_LIST(>256)** 三条路径 |
| **D2（你原表述）** | Rust 产出 section 级 palette + 位打包 data（新 C ABI + 新 JNI + Rust 侧 palette 代码） | 省掉 D1 的**去重扫描**（仅此） | 相对 D1 **被支配**：新 ABI/新 JNI/新数据源（>256 distinct 时需 raw-id→state-id 表）/版本耦合编码（MC 的 bits 规则）进 Rust；且 Java 侧**仍须重打包**（Rust 选的宽度 ≠ `dataProvider.bits()`：ARRAY 固定 4bit、BI_MAP 5-8bit、ID_LIST 用全局 state id） |
| **D3（最小风险降级）** | **不做 C**，改做「共享核抽取」：把现有逐块写回原样抽到共享 Java 模块（两版引用同一实现） | 拿到**同样的可移植性收益**（去重、单一实现），零机制风险 | 保留 6.2% 写回成本；不消掉 per-block `setBlockState` 开销 |

**推荐 D1，并把 D2 降级为「阶段 2（仅在实测支持时才做）」**：理由 = D2 相对 D1 只省一遍去重扫描，却把「MC 版本耦合的编码规则」与「新数据源」引进 Rust，与项目「数据驱动 = 跨版本少改代码」的初衷**反向**；而 D1 已完整达成两个目标（共享实现 + 去块级开销），且**不动 Rust 契约**（风险面全落在 Java 单侧、可用开关回退）。
**D3 作为 D1 的实测回退**：若 D1 的 Java 侧两遍扫描 + 打包实测**不比**逐块 `setBlockState` 便宜，则退 D3（拿可移植性、不碰机制）。

## 4. 接口契约（D1）

### 4.1 Rust/JNI（**不变**）
- `CppWorldgen.fillBlocks(long, int[], int[], int[][], int)`（两版逐字相同，`CppWorldgen.java:71`）；索引布局 `(y - min_y) * 256 + z * 16 + x`（y-major，`blocks.rs:152-159`）；`BlockId = i32` = 注册表 raw id，`AIR = 0`。
- 缓冲区：Java `ThreadLocal<int[]>`（overworld 98304 / nether 65536 / end 32768；`CppBridge.java:38-39`/`:434-435`/`:482-483`），JNI 每次新建 `Vec<Vec<i32>>` 拷回（`jni_bridge.rs:179-227`）。

### 4.2 Java 侧 bulk apply（新，落**共享核**）
```
applySections(chunk, buf, height, minY):
  for s in 0..height/16:
     src = buf[s*4096 .. (s+1)*4096]          // section 内 y-minor 切片（注意布局转换）
     (palette[], indices[]) = buildPalette(src)   // 一遍去重
     states[] = palette.map(id -> STATE_CACHE(id))
     pc = pack(states, indices)                    // 按 distinct 数选 ARRAY/BI_MAP/ID_LIST
     chunk.getSectionArray()[s] = new ChunkSection(pc, oldBiome(s))
```
- **编码选择**：distinct ≤16 → ARRAY(4bit)；17-256 → BI_MAP(ceilLog2)；**>256 → ID_LIST（storage 写全局 `Block.STATE_IDS` raw id，palette 列表被忽略）**。
- **顺序/时机不变**：仍在 `writeChunk` 原位置调用（NOISE 阶段接管点内），高度图仍走原 6 张 `populateHeightmaps`（R4：它经 `chunk.getBlockState` 读活数组，语义跟随）。
- **开关**：`-Dcoreswap.bulkwb=0` → 旧逐块路径（同构建态单变量 A/B 与即时降级）。

## 6. 验证计划（详见 `verify-design-draft-260911-05.md`）

- **Tier 1（主判据，噪声无关）**：写回**之后**逐 chunk 读回全部 section 算 FNV-1a 64（`[WG-CONTENT-WB]`），A/B 两臂**逐 chunk hash 全等**（零差，非「差异小」）。⚠️ 必须与现有 `[WG-CONTENT]`（buf 层）**区分开**——后者对本次变更瞎。
- **Tier 2**：section 派生字段（3 计数、`isEmpty`/`hasRandomTicks`）正确性。
- **Tier 3（端到端）**：两臂各生成同一 region → **用已修好的** `diff_arms_fixed.py` 对拍 ⇒ **diff = 0**（同实现单变量，不是 ≤ 噪声基线）。
- **Tier 4**：同构建态单变量 `-Dcoreswap.bulkwb=0` ↔ 新路径；判据 = **`write` 分项显著下降**（wall 落噪声带内可接受）。
- **前置纪律**：执行体三元组（jar sha / jar 内 dll sha / target dll）；A/B 两臂**对称开启**诊断（避免 index.yaml:1223 口径不对等教训）；§9.7 三要素声明。

## 9. 与「共享核抽取」的排序

- C（D1）**先做**：它把写回循环整体移出分版面，直接缩小共享核的抽取面（抽取面越小，抽取越机械）。

- 纪律不变：C 之前若仍需移植任何 Java 项，移植体 MUST 与 1.20.1 逐行同形。
