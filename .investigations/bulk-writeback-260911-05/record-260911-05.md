## 1. 结论摘要

**D1 落地成功：Java 侧 bulk section 写回（Rust 零改动），在 NOISE 后状态层与老路径逐 chunk 完全等价，写回分项成本下降 49-70%（同 run 同仪器）。**

- **等价性（决定性）**：607 次写回调用 / 607 个 chunk 的**写回后读回指纹逐 chunk 全等**（方块状态层 `hash` 差 0 + 派生字段层 `dh` 差 0），覆盖 607×24×4096 = **59,670,528 个位置**；两臂 chunk 集完全相同（无缺失）。
- **编码四支全绿**：SINGULAR / ARRAY / BI_MAP / **ID_LIST** 各以合成 buf 压测并逐位读回验证（自然生成 `max_distinct=7` ⇒ ID_LIST 支实测不可达，必须刻意压测）。
- **性能**：写回分项（同 run、同仪器、单变量）旧 2,151,591 ns/chunk → 新 **652,202 ns/chunk（−69.7%）**；另一轮为 2,070,297 → 1,052,606（−49.2%）。分项内部：`counts_set` 由 `calculateCounts` 的 72,480 ns/section 降到 **116 ns/section**。
- **Tier 3（region 零差对拍）判据在本 harness 不可达**——见 §5，**降级声明**：全域差分 0.0277% 中，**从未走过本代码路径的 chunk 也有 0.0260%**，故残差是跨 run 固有抖动而非写回差异。
- **C 的价值定位**（须写进结论，防夸大）：**可维护性/可移植性为主**（消掉 98,304 次/块的逐块循环，为共享 Java 适配核与 1.21.6 收敛铺路），性能为**次要附带收益**且**端到端落在 ±10% 机器噪声带内、不予主张**。

### 2.3 机制要点（全部一手源码核对）

- **buffer 契约**：`byte 请求位宽` → palette 段（0：`VarInt rawStateId`；1..8：`VarInt size`+entries；**≥9：无字节**）→ `writeLongArray(storage.getData())`（**带 VarInt 长度前缀**，`readLongArray(long[])` 按长度匹配才复用传入数组，长度不符会**静默丢弃**）。
- **storage 位宽/值域**：0→无（`EmptyPaletteStorage`）；1..4→**恒 4 位**、局部索引；5..8→请求位宽、局部索引；≥9→`ceilLog2(Block.STATE_IDS.size())`、**全局 state id**。
- **零布局转换**：buf 是 y-major ⇒ section s 恰是连续切片 `buf[s*4096, (s+1)*4096)`；`PackedIntegerArray` 线性索引 `(y<<8)|(z<<4)|x` 与切片内布局逐位相同。
- **section 数组**：`Chunk.getSectionArray()` 返回活引用（`Chunk.java:163-165`），且 `ProtoChunk`/`WorldChunk` **均未覆写**（只把数组交给 `super`）⇒ 生成期 ProtoChunk 有效。本实现进一步**原地改旧 section 对象**（`sections[s]` 元素不变，生物群系容器原样保留）。
- **运行时自证**：`Block.STATE_IDS.size()=24137`、`idlist_bits=15`、overworld `max_distinct=7`、`idlist_hits=0`（自然生成从不触发 ID_LIST）。

## 3. 两个错误（错误优先原则：现象 → 根因 → 定位 → 修复 → 教训）

### 3.1 E1：单态 section 触发 `PackedIntegerArray(0, …)` 抛 IAE（539 次）

- **现象**：首轮 A/B 两臂 `[WG-CONTENT-WB]` 行数 **607（旧）vs 68（新）**，新臂日志 539 条
  `java.lang.IllegalArgumentException: The value 0 is not in the specified inclusive range of 1 to 32`（`[CppBridge] DIAG write threw`）。
- **根因**：`bits==0`（section 内只有 1 种状态）时 provider = `SINGULAR`、storage = `EmptyPaletteStorage`（0 个 long），**根本不需要打包**；我却无条件构造 `new PackedIntegerArray(storageBits=0, 4096)`，其构造器 `Validate.inclusiveBetween(1, 32, elementBits)` 直接抛。
- **定位**：比对脚本先暴露「两臂 chunk 集不对称」（607 vs 68）这一**结构性异常**，再查日志拿到异常原文——**先看集合差，再看异常**，比直接翻日志快。
- **修复**：`bits==0` 走独立分支（写 `VarInt stateId` + `writeLongArray(new long[0])`），完全不构造打包数组。
- **教训**：**「按位宽选分支」时，位宽 0 是「无 storage」而不是「0 位 storage」**——把 0 当普通位宽会撞上 MC 的参数校验。凡复刻 MC 的 switch，MUST 逐个 case 过一遍构造器前置条件（本例 provider switch 的第 0 支根本没有 storage 对象）。

### 3.2 E2：`calculateCounts()` 与增量 `setBlockState` 的**计数语义不一致**（会静默改变世界行为）

- **现象**：`ChunkSection(pc, biome)` 构造器（`:27-31`）自动调 `calculateCounts()`，实测 **72,480 ns/section**，占被替换 section 成本的 64%——先只是性能问题。
- **根因**（一手源对读，`ChunkSection.java`）：

  | 计数 | 增量 `setBlockState`（`:70-90`） | `calculateCounts`（`:111-140`） |
  |---|---|---|
  | `nonEmptyBlockCount` | 非空气 +1 | 非空气 +1，且**流体非空再 +1**（重复计入） |
  | `randomTickableBlockCount` | 非空气 ∧ `hasRandomTicks` | 同 |
  | `nonEmptyFluidCount` | **流体非空** +1 | 仅 **流体自身 `hasRandomTicks()`** 才 +1（静水 `WaterFluid.Still.hasRandomTicks()=false` ⇒ 静水 section = 0） |

  vanilla `populateNoise` 走**增量**路径（`:416` `setBlockState(..., lock=false)`），故**增量语义才是生成期 vanilla 语义**（也是老路径语义）。走构造器会让 `hasRandomFluidTicks()`（→ 流体随机刻调度）与 `nonEmptyBlockCount`（→ `isEmpty()`/客户端包 `toPacket:165`）偏离。
  另：三个计数**不入存档**（`ChunkSerializer:310-311` 只写 `block_states`/`biomes`），故 Tier 3 region 对拍看不到它们；唯一可见面 = 生成期到下次存读之间的内存态。
- **定位**：为「能否绕过这 72.5µs」去读 `calculateCounts` 源码时发现语义差异——**性能问题的解法顺带暴露了正确性问题**。
- **修复**：`ChunkSectionAccessor` 直接写三个计数，值在去重遍顺带算（O(distinct)），复刻**增量**语义；原地换容器（不新建 section、不调 `calculateCounts`）。
- **教训**：**同一语义在 vanilla 内部有两套实现时必须逐条对表**（本例增量 vs 全量重算）。「构造器会自动算好」是危险的直觉——它算的是**另一套定义**。凡"顺手用现成 API 代替手工维护"，MUST 先核对两套实现是否定义等价。

## 4. 验证证据（Tier 1-4，含 §9.7 可比性三要素）

### Tier 1（方块状态层，决定性）
- 载体：同 JVM 内、写回**之后**读回全部 section 算 FNV-1a 64（`[WG-CONTENT-WB] hash=`，`BulkWb.readbackHash`）。
- 覆盖面：**607** 次写回调用（441 个 Chunky chunk；重复接管存在）/ 24 section 各 / 4096 位置 = **59,670,528 位置**。
- 判据与结果：**逐 chunk hash 全等，差 0**；两臂 chunk 集相同（`only_old=0, only_bulk=0`）；`nz`（非空气计数）亦差 0。
- 可比性：同构建态、同 dll（`838e8979`）、同 seed/区域、背靠背两臂，**唯一变量 = `-Dcoreswap.bulkwb`**。
- ⚠️ **与 `[WG-CONTENT]`（Rust buf 层指纹）不同层**：后者算的是 Rust 输出的 buf，buf 不变则 hash 必相同 ⇒ **对 Java 侧消费的变更不敏感，不可能检出写回回归**。C 的等价性只能由本门承载。

### Tier 2（派生字段层）
- 载体：同一条 `[WG-CONTENT-WB]` 行的 `dh=`（三个计数的逐 section 序列）。
- 结果：**逐 chunk 全等，差 0**。该门**能**检出 E2 那类「状态层等价但派生层不等价」的偏差（本块正是先看到该形态才去查语义）。

### 编码分支自检（覆盖 ID_LIST）
- `-Dcoreswap.bulkwbtest=1`：合成 buf 四例（distinct = 1 / 3 / 20 / **300**），各逐位读回 4096 位置比对 `CppBridge.stateById`：

- 必要性：自然生成 overworld `max_distinct=7`、`idlist_hits=0` ⇒ **不刻意压测则该分支「全绿但未覆盖」**。

## 6. R8 / R9 论证（judge 前置）

### R9（并发/锁语义）——**结论：新路径不比老路径更弱，且在锁粒度与原子性上更强**
- `PalettedContainer` 的锁是 `LockHelper`（`net/minecraft/util/thread/LockHelper.java`）：**真锁**（`Semaphore(1)`+`ReentrantLock`），冲突时阻塞并抛「Accessing … from multiple threads」crash；`swap`/`set`/`readPacket`/`writePacket` 各自 `lock()/unlock()`。
- vanilla 形态：`populateNoise` 先给生成 range 内**全部 section 上锁**（`:342-346`），填块用 `swapUnsafe`（`:416`，不逐块加锁），完成后统一解锁（`:351-355`）。
- **老 CoreSwap 路径**：mixin 在 `populateNoise` HEAD cancel ⇒ **vanilla 的上锁段整体被跳过**（本块之前既如此，C 未改变）；然后每块调 `ChunkSection.setBlockState(x,y,z,st)`（4 参 = `lock=true`）⇒ **每个非空气块一对 `LockHelper` 操作**（每 chunk 数万次），且逐块变异**共享的活容器**。
- **bulk 路径**：同样跳过 vanilla 上锁段；但 (a) `readPacket` **自带 lock/unlock**（`:204/213`）⇒ 每 section 一对（**24 次/chunk**，比老路径少 3-4 个数量级）；(b) 填的是**尚未发布的私有容器**，最后以**单次引用写**发布 ⇒ 并发读者只会看到「旧（全空气）」或「新（完整）」两个状态，**不存在部分写可见窗口**（老路径存在数万个中间态窗口）。
- 残余风险（诚实声明）：`sections[s]` 的容器引用非 `volatile`，跨线程可见性依赖既有的 chunk 发布/同步机制——与老路径相同（老路径也写非 `volatile` 的容器内部状态），且 chunk 在 NOISE 阶段尚未发布给其他线程。**未做**并发压力下的可见性专项验证（列为未验证项 R9-b）。

### R8（`BelowZeroRetrogen`）——**结论：本 harness 不触发，C 无新增暴露**
- 一手源：1.20.1 的 `BelowZeroRetrogen` 只提供 (a) `getBiomeSupplier`（`populateBiomes` 的生物群系包装，`:102-112`）与 (b) `isColumnMissingBedrock`（缺失基岩列）；flag 仅由**旧存档 chunk NBT** 携带（`ChunkSerializer:185/281-284`）并在加载时置上。
- 本 harness 每臂删除 world 重新生成 ⇒ 无 legacy chunk ⇒ flag 恒不置。
- C **不动生物群系容器**（原地改 section 保留 `old.getBiomeContainer()`）、**不动 FEATURES 阶段**（基岩由 feature 放置，非 NOISE）⇒ 即便触发也无新增暴露面。
