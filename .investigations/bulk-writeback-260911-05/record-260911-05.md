### 2.3 机制要点（全部一手源码核对）

- **buffer 契约**：`byte 请求位宽` → palette 段（0：`VarInt rawStateId`；1..8：`VarInt size`+entries；**≥9：无字节**）→ `writeLongArray(storage.getData())`（**带 VarInt 长度前缀**，`readLongArray(long[])` 按长度匹配才复用传入数组，长度不符会**静默丢弃**）。
- **storage 位宽/值域**：0→无（`EmptyPaletteStorage`）；1..4→**恒 4 位**、局部索引；5..8→请求位宽、局部索引；≥9→`ceilLog2(Block.STATE_IDS.size())`、**全局 state id**。
- **零布局转换**：buf 是 y-major ⇒ section s 恰是连续切片 `buf[s*4096, (s+1)*4096)`；`PackedIntegerArray` 线性索引 `(y<<8)|(z<<4)|x` 与切片内布局逐位相同。
- **section 数组**：`Chunk.getSectionArray()` 返回活引用（`Chunk.java:163-165`），且 `ProtoChunk`/`WorldChunk` **均未覆写**（只把数组交给 `super`）⇒ 生成期 ProtoChunk 有效。本实现进一步**原地改旧 section 对象**（`sections[s]` 元素不变，生物群系容器原样保留）。
- **运行时自证**：`Block.STATE_IDS.size()=24137`、`idlist_bits=15`、overworld `max_distinct=7`、`idlist_hits=0`（自然生成从不触发 ID_LIST）。

## 3. 两个错误（错误优先原则：现象 → 根因 → 定位 → 修复 → 教训）

### 3.1 E1：单态 section 触发 `PackedIntegerArray(0, …)` 抛 IAE（539 次）

- **现象**：首轮 A/B 两臂 `[WG-CONTENT-WB]` 行数 **607（旧）vs 68（新）**，新臂日志 539 条
  `java.lang.IllegalArgumentException: The value 0 is not in the specified inclusive range of 1 to 32`（`[CppBridge] DIAG write threw`）。
- **根因**：`bits==0`（section 内只有 1 种状态）时 provider = `SINGULAR`、storage = `EmptyPaletteStorage`（0 个 long），**根本不需要打包**；我却无条件构造 `new PackedIntegerArray(storageBits=0, 4096)`，其构造器 `Validate.inclusiveBetween(1, 32, elementBits)` 直接抛。
- **定位**：比对脚本先暴露「两臂 chunk 集不对称」（607 vs 68）这一**结构性异常**，再查日志拿到异常原文——**先看集合差，再看异常**，比直接翻日志快。
- **修复**：`bits==0` 走独立分支（写 `VarInt stateId` + `writeLongArray(new long[0])`），完全不构造打包数组。
- **教训**：**「按位宽选分支」时，位宽 0 是「无 storage」而不是「0 位 storage」**——把 0 当普通位宽会撞上 MC 的参数校验。凡复刻 MC 的 switch，MUST 逐个 case 过一遍构造器前置条件（本例 provider switch 的第 0 支根本没有 storage 对象）。

### 3.2 E2：`calculateCounts()` 与增量 `setBlockState` 的**计数语义不一致**（会静默改变世界行为）

- **现象**：`ChunkSection(pc, biome)` 构造器（`:27-31`）自动调 `calculateCounts()`，实测 **72,480 ns/section**，占被替换 section 成本的 64%——先只是性能问题。
- **根因**（一手源对读，`ChunkSection.java`）：

  | 计数 | 增量 `setBlockState`（`:70-90`） | `calculateCounts`（`:111-140`） |
  |---|---|---|
  | `nonEmptyBlockCount` | 非空气 +1 | 非空气 +1，且**流体非空再 +1**（重复计入） |
  | `randomTickableBlockCount` | 非空气 ∧ `hasRandomTicks` | 同 |
  | `nonEmptyFluidCount` | **流体非空** +1 | 仅 **流体自身 `hasRandomTicks()`** 才 +1（静水 `WaterFluid.Still.hasRandomTicks()=false` ⇒ 静水 section = 0） |

  vanilla `populateNoise` 走**增量**路径（`:416` `setBlockState(..., lock=false)`），故**增量语义才是生成期 vanilla 语义**（也是老路径语义）。走构造器会让 `hasRandomFluidTicks()`（→ 流体随机刻调度）与 `nonEmptyBlockCount`（→ `isEmpty()`/客户端包 `toPacket:165`）偏离。
  另：三个计数**不入存档**（`ChunkSerializer:310-311` 只写 `block_states`/`biomes`），故 Tier 3 region 对拍看不到它们；唯一可见面 = 生成期到下次存读之间的内存态。
- **定位**：为「能否绕过这 72.5µs」去读 `calculateCounts` 源码时发现语义差异——**性能问题的解法顺带暴露了正确性问题**。
- **修复**：`ChunkSectionAccessor` 直接写三个计数，值在去重遍顺带算（O(distinct)），复刻**增量**语义；原地换容器（不新建 section、不调 `calculateCounts`）。
- **教训**：**同一语义在 vanilla 内部有两套实现时必须逐条对表**（本例增量 vs 全量重算）。「构造器会自动算好」是危险的直觉——它算的是**另一套定义**。凡"顺手用现成 API 代替手工维护"，MUST 先核对两套实现是否定义等价。

### 3.3 E3：「607 vs 441」误推为「重复接管存在」（judge S10① 要求按五段式补记）

- **现象**：record 早期草稿在覆盖面行写「**607** 次写回调用（441 个 Chunky chunk；**重复接管存在**）」——把 Chunky 日志的 `Processed: 441 chunks` 当成「写回 chunk 数」，并用「同一 chunk 被接管两次」解释 607−441 = 166 的差额。
- **根因（机制层）**：两处错。① **口径错位**：`Processed` = Chunky 任务的 chunk 数；**接管数** = 经 `populateNoise` 且形状/settings 匹配的 chunk 数（服务器自生成的邻近 chunk 也走该路径）；**世界 chunk 数** = region 文件里的 chunk 数（本块 3190，含 1854 个未生成内容的部分生成 chunk）。三者是三套口径。② **未测先解释**：「重复接管」是**推断**出来的机制，而不是坐标级测出来的事实。
- **定位（怎么发现的）**：judge 要求全量复算 ⇒ 主会话实测 `wbc-c-old.txt` 607 行**唯一坐标 = 607 / 重复坐标 = 0** ⇒ 「重复接管」为伪。进一步核 Chunky 的 `center` 语义：`chunky center -48 -11` 是**方块坐标**（`-48/16 = -3`、`-11/16 = -1`）⇒ 目标 chunk `(-3,-1)`，半径 160 块 = 10 chunk ⇒ 21×21 = **441** ✔；且与实测接管包围盒（x ∈ [-15,9]、z ∈ [-13,11]）**中心完全吻合** ⇒ 差额 166 = 服务器自生成的邻近 chunk（推断，未逐 chunk 证明来源，见 §7 遗留 8）。
- **修复**：record §4 覆盖面行改判 + 加口径澄清（「Chunky 的 center 是方块坐标」）；本记录 §1 同步。
- **教训（可复用判错经验）**：**「两个集合数量不等时，先测『交集 / 差集 / 重复』三件事，再谈机制」**——用「重复」解释差额却未做去重计数，是典型的未测先解释。判错签名：**差额 = 推断的机制**（而非测出来的机制）。

### 3.4 E4：过程失败两条（跑完对照 run 却不回写结论；把「判据未满足」写成「不可判」）

- **现象**：22:06–22:11 跑了 3 个同实现对照 run（old×old2×old3）并把输出落在 `.tmp/`，但 record / verdict / `.artifacts/index.yaml` **三处结论载体仍写「残差非写回引起 / Tier 3 不可判」**；对照证据**未入 `evidence/`、未被引用**；且**预注册判据（`verify-design-draft:29-33` 的 `diff = 0`）未满足**这一事实**未被登记**。
- **根因（机制层）**：① 对照 run 是「顺手补跑」的，跑完后**没有回到结论载体核对「新证据是否改变结论」**——缺一个「新证据 → 三处载体回写」的强制步骤（证据只落在 gitignored 的 `.tmp/` 里，等于不存在）。② 把**「判据不可达」与「判据未满足」混为一谈**：前者是**测量能力**问题（必须先证明「同实现噪声底包含交付对」），后者是**结论未达成**；按前者写，等于用降级措辞掩盖了 FAIL。
- **定位（怎么发现的）**：judge 独立复算 4 个已归档世界（不采信我的转述），指出**交付对是 4 对中差分最高的一对、且超出集中在切片 A** ⇒ 与三处措辞直接矛盾；并指出 `bulk × bulk`（变更臂自身的底）是**唯一**能把「实现差异」与「运行期抖动」分开的对照，而本块缺失。
- **修复**：① 本记录 §5.4 改判为「**判据未满足（FAIL）+ 未归因**」，两候选并列；② 补跑 `bulk × bulk` 判决实验（§5.4 表：交付对落在 bulk 臂自身区间内 ⇒ 无系统性差异证据，但登记「离散度上升」弱信号）；③ 全部对照输出 + 脚本 + 原始日志摘要入 `evidence/` 并列入 §9；④ verdict + `index.yaml` 同步改判。
- **教训（可复用判错经验）**：① **任何在结论定稿后新产生的证据，MUST 触发一次「三处结论载体回写核对」**（record / verdict / index.yaml），否则证据等于不存在；② **判据只有「满足 / 未满足」两种终态**——「不可达/不可判」必须先**证明测量不可分辨**（同实现噪声底包含交付对）才可写，且即便写了也 MUST **同时登记预注册判据未满足**；③ 变更臂自身的同实现对照（`new × new`）与未变更臂的对照（`old × old`）**不能互相替代**——前者界定「变更带来的抖动」，后者只界定「基线抖动」。

## 4. 验证证据（Tier 1-4，含 §9.7 可比性三要素）

### Tier 1（方块状态层，决定性）
- 载体：同 JVM 内、写回**之后**读回全部 section 算 FNV-1a 64（`[WG-CONTENT-WB] hash=`，`BulkWb.readbackHash`）。
- 覆盖面：**607** 次写回调用 = **607 个互不重复的 chunk 坐标**（实测**无重复接管**；构成 = Chunky 441 + 服务器自生成 166）/ 24 section 各 / 4096 位置 = **59,670,528 位置**。
  - ⚠️ 口径澄清（本记录定稿前修正）：Chunky 的 `center` 是**方块坐标**，`-48,-11` 块 = chunk `(-3,-1)`——与实测接管包围盒（x ∈ [-15,9]、z ∈ [-13,11]）中心一致；`Processed: 441` = 21×21 ✔。故「607 vs 441」的差额是**服务器自生成的邻近 chunk**，**不是**重复接管（早前草稿的「重复接管存在」为误，已改）。
- 判据与结果：**逐 chunk hash 全等，差 0**；两臂 chunk 集相同（`only_old=0, only_bulk=0`）；`nz`（非空气计数）亦差 0。
- 可比性：同构建态、同 dll（`838e8979`）、同 seed/区域、背靠背两臂，**唯一变量 = `-Dcoreswap.bulkwb`**。
- ⚠️ **与 `[WG-CONTENT]`（Rust buf 层指纹）不同层**：后者算的是 Rust 输出的 buf，buf 不变则 hash 必相同 ⇒ **对 Java 侧消费的变更不敏感，不可能检出写回回归**。C 的等价性只能由本门承载。

### Tier 2（派生字段层）
- 载体：同一条 `[WG-CONTENT-WB]` 行的 `dh=`（三个计数的逐 section 序列）。
- 结果：**逐 chunk 全等，差 0**。该门**能**检出 E2 那类「状态层等价但派生层不等价」的偏差（本块正是先看到该形态才去查语义）。

### 编码分支自检（覆盖 ID_LIST）
- `-Dcoreswap.bulkwbtest=1`：合成 buf 四例（distinct = 1 / 3 / 20 / **300**），各逐位读回 4096 位置比对 `CppBridge.stateById`：
  `[WG-BULKWB-TEST] PASS … SINGULAR / ARRAY / BI_MAP / ID_LIST` 四支全绿。
- 必要性：自然生成 overworld `max_distinct=7`、`idlist_hits=0` ⇒ **不刻意压测则该分支「全绿但未覆盖」**。

### Tier 4（写回分项，同 run 对称计时）
| 轮次 | 旧逐块（ns/chunk） | bulk（ns/chunk） | 变化 |
|---|---|---|---|
| 第 1 轮（accessor 前，ctor 路线） | 2,070,297 | 1,052,606 | −49.2% |
| 第 2 轮（accessor 后，定稿） | 2,151,591 | **652,202** | **−69.7%** |

- 载体：两臂**同一仪器**（`System.nanoTime()` 只包住写回调用本身；旧路径 `[WG-PERBLOCK]`，新路径 `[WG-BULKWB] ns/call(total)`）。
- 分项（定稿轮）：`build=75,666 ns/section`（含 `readPacket=5,963`）、`counts_set=116 ns/section`；`sections_replaced=4856`、`air_sections_skipped=9712`（合计 14,568 = 607×24）。

## 6. R8 / R9 论证（judge 前置）

### R9（并发/锁语义）——**❌ 原结论「新路径不比老路径更弱，且在锁粒度与原子性上更强」已被 judge（S1/A12）推翻；原文保留不改，更正如下**
- **事实部分（judge 逐条复核成立）**：`LockHelper` 是**真锁**（`Semaphore(1)`+`ReentrantLock`），冲突时阻塞并抛「Accessing … from multiple threads」crash；`swap`/`set`/`readPacket`/`writePacket` 各自 `lock()/unlock()`；vanilla `populateNoise` 先给生成 range 内**全部 section 上锁**（`:342-346`）、填块用 `swapUnsafe`（`:416`）、完成后统一解锁（`:351-355`）；mixin 在 HEAD cancel ⇒ **该上锁段整体被跳过**（本块之前既如此，C 未改变）；老路径每非空气块调 `setBlockState(x,y,z,st)`（4 参 = `lock=true`）。
- **更正（judge S1 核心）**：新路径 `readPacket` 锁的是**刚构造、尚未发布、其他线程不可达的私有容器**（`BulkWb.java:265-267` 在 `:171` 发布**之前**）⇒ 它**对共享容器不提供任何互斥**。老路径锁的却是**已发布的活容器**，其锁**兼作「多线程访问同一容器」的 crash 检测器**（`LockHelper.crash`）——该检测能力在 C 之后**被移除**。
- 故「锁次数更少 ⇒ 并发语义更强」**不是同一件事的强弱**；且 `sections_replaced` 实测均值 = **8.0 次/chunk**（4856/607），「24 次/chunk」只是**上界**（= 24 section 全替换时才成立）。
- **正确表述**：新路径的正确性**完全外移到「每 chunk 单写者」这一外部保证**（老路径也依赖该保证，但其锁附带检测）。该外部保证本块**未验证**（R9-b），且 `plan §10.3` 自认 MUST 的前置「是否有消费者在 NOISE→LIGHT 之间缓存 `ChunkSection` 实例/容器」**本块未收口**（见 §7 遗留 3）。
- **仍然成立的子结论（方向性）**：发布原子性——`PalettedContainer.data` 是 `volatile`（`:36`）且 `readPacket` 在发布前完成全部内部写，读者只见「旧（全空气）」或「新（完整）」；但 `sections[s]` 容器引用本身**非 volatile**，x86 TSO 下实践安全、**形式上仍是 data race**。

### R8（`BelowZeroRetrogen`）——**结论：本 harness 不触发，C 无新增暴露**
- 一手源：1.20.1 的 `BelowZeroRetrogen` 只提供 (a) `getBiomeSupplier`（`populateBiomes` 的生物群系包装，`:102-112`）与 (b) `isColumnMissingBedrock`（缺失基岩列）；flag 仅由**旧存档 chunk NBT** 携带（`ChunkSerializer:185/281-284`）并在加载时置上。
- 本 harness 每臂删除 world 重新生成 ⇒ 无 legacy chunk ⇒ flag 恒不置。
- C **不动生物群系容器**（原地改 section 保留 `old.getBiomeContainer()`）⇒ 无新增暴露面。
- **❌ 原文「C 不动 FEATURES 阶段（基岩由 feature 放置，非 NOISE）」理由不准，已被 judge（I10/A13）更正**：retrogen 的方块改写发生在 **NOISE 阶段的 `thenApply`**（`ChunkStatus.java:99-108`：`replaceOldBedrock` → `BelowZeroRetrogen.java:67-74`；`fillColumnsWithAirIfMissingBedrock` → `:76-88`），**不是 FEATURES**，且它**恰好写进 C 刚重写过的那些 section**。更正后的结论仍然成立但理由不同：该改写走 `chunk.setBlockState(..., false)` **逐块路径**，**不依赖容器的构造方式** ⇒ C 无新增暴露面（`plan` 原话反而更准）。
