# jungle-l 错误台账（260906-06 工作块）

## E11: popseed_check2 用 java-LCG 公式绑定 population 行——E10 归属反转

- **现象**：260906-06 基线重采中，目标 chunk (29,-16) 两条 population 行并存（-4568…/-2605…）；按 E10 判据（java-LCG 复算命中 = 正确 seed FEATURES pass），-2605 应为特征生成 pass，但该 pass 语义与 mega 全无矛盾，且 -4568 在同 run 各 chunk 恒为「第一条」。
- **根因**：`setPopulationSeed` 有**两个调用点**、两个不同的 baseRandom：`generateFeatures`（Xoroshiro128PlusPlusRandom）与 `populateEntities`（CheckedRandom=48 位 java LCG）。popseed_check2.py 的 java-LCG 复刻命中的是**实体生成 pass**，不是特征生成 pass。E10 据此把真 FEATURES pass 标成「污染」。
- **定位**：日志统计 529/625 chunk 双 pop → 不可能同为确定性单调用 → 一手 yarn 源码 grep setPopulationSeed 调用点（ChunkGenerator.java:344 / NoiseChunkGenerator.java:462）→ ChunkRandom.next(bits) 基类分流（:31）→ Xoroshiro 复刻逐位命中「第一条」pop（-4568734542690011764，含 MC-239059 低位符号扩展坑——首版复刻用无符号 j 拼接致高位似近低位全错）。
- **修复**：新判据 = Xoroshiro 公式复算（.tmp/jungle-l-260906/pop_feature_xoroshiro.py）绑定 FEATURES pass；java-LCG 行仅作 chunk 锚点。
- **教训**：①「复算逐位吻合」必须先证**公式覆盖正确的调用点**——同参数不同随机源的双调用点会让错误的公式也「逐位吻合」另一个 pass；② MC-239059（nextLong 低位符号扩展）复刻时是高位近/低位远的特征签名；③ 交接结论验证纪律再次生效——E10 的复算判据本身未经「调用点覆盖面」核对（发现 #43 家族：对拍/复算必须附覆盖面声明）。

## E12: 采集脚本漏 -P sysprop 通道 + daemon 吞 env——[SEEDLOG]/MJT0 全零

- **现象**：首跑 j5_java_baseline_260906-06.ps1 退出 0、forceload 正常，但 population=0、MJT0=0。
- **根因**：脚本只设 env（WG_SEEDLOG/WG_TREEDIAG），而 gradle daemon 复用吞掉新 env（#32）；且照抄 wgdiag_firstrun.ps1 时漏掉 `-PseedLog=1 -Ptreediag=1`（build.gradle:81-82 的 findProperty→vmArg 映射，#8 家族）——env/sysprop 双通道同时失效。
- **定位**：日志无任何 [SEEDLOG] 行（门未开）而非打点异常；对照 260906-01 成功 run 的命令行找回 -P 通道。
- **修复**：gradle --stop 杀 daemon + 补 -PseedLog/-Ptreediag；重采 1154 population 行。
- **教训**：诊断开关生效验证 = 输出行为化（#37）——「脚本跑了」不等于「门开了」，先验 1 行样本再等全量。
