## E6: Rust 侧首采 MJT0=0 —— `-DWG_TREEDIAG` 忘设进程 env（sysprop≠env 二犯 ⚠️）

- **现象**：j5_rust_run.ps1 首跑「成功」退出（exit 0、forceload 正常），但核验 MJT0=0 / TH=0 / CNT=0。
- **根因**：脚本只设 `JAVA_TOOL_OPTIONS=-DWG_TREEDIAG=1`（JVM sysprop），Rust dll 的 `treediag_enabled()` 读的是**进程环境变量** `WG_TREEDIAG`——与 260905-13 E1 同一根因的另一面（那次是 mixin 读 sysprop 给了 env 名，这次是 dll 读 env 给了 sysprop 名）。**E1 五段式已记、knowledge #25 已记、NEXT_SESSION 纪律要点已重申，仍然二犯。**
- **定位**：核验零输出 → 读 placement.rs:283-286 `std::env::var("WG_TREEDIAG")` 逐行核对。
- **修复**：脚本补 `$env:WG_TREEDIAG = "1"`。
- **教训**：**记录在案 ≠ 防住再犯**——教训必须转化为开工前置动作：写任何采集脚本前先跑「门控接线四查」（通道域/名字逐字/映射行/行为化哨兵），本块写脚本时没执行。二犯自检：通道域（sysprop or env）在**读写两侧**分别确认，不能因为一侧对过就推另一侧。

## E7: 「不带 -PcppVanilla = Rust 全接管」当公理 —— stageMask 默认 0b011 跳过 features（#53 家族）

- **现象**：补了 env 后重跑，MJT 行出现（20372 行）但**全是 Java mixin 标签**（[MJTT]/[MJTG]，Rust 标签 [MJTL]/[MJTI]/[MJTF]/[MJTB]=0）——"Rust 侧" run 实际由 Java 执行特征阶段。
- **根因**：CppBridge.resolveStageMask() 默认 `0b011`（bit0=SKIP_CARVER bit1=SKIP_FEATURES，260905-13 双跑缺陷修复）→ replace 模式下 carver/features 由 Java vanilla 执行。我断定「Rust 接管」前没核 stage mask 默认值，**#53「门控默认值当公理」家族**（该条原文管 env 开关默认方向，本例是同族扩展：接管范围默认值）。
- **定位**：worker 解读发现 tag 集与方案不符 → 主会话核查 `CppBridge` init 日志（stageMask=3 可见！init 行就打印着）→ resolveStageMask 源码逐行。
- **修复**：采集脚本加 `-Dcoreswap.rust.stages=all`（mask 0，b2b3 同款全接管）。
- **教训**：①CppBridge **init 日志行自带 stageMask 值**——"Rust 侧"判定应先读 init 行再信脚本参数表；②#53 三查升级：接管类判别实验先核「接管范围」（stageMask/开关/目录三处），不是只核开关存在性。

## E8: gradle JavaExec stderr 合并转发到 stdout —— Rust eprintln 在 .err 假空

- **现象**：查 Rust 采集输出只看 `.log.err`（Start-Process -RedirectStandardError），为空/仅 feature-loader 行；实际 20372 行 [MJT*] 在 **stdout** 日志里。
- **根因**：gradle daemon 捕获 JavaExec 子进程的 stdout/stderr 后统一转发到 gradle 客户端 **stdout**（console=plain），Rust dll 的 eprintln（JVM 进程 stderr）随之进 stdout 日志。
- **定位**：E7 排查中在 stdout log 搜 [MJT] 命中 20372 行。
- **修复**：不修（行为可用）；核验脚本改为两侧日志都搜。
- **教训**：gradle run 系采集「stderr 文件」不承接子进程 stderr——**落盘文件 ≠ 流向直觉**，采集核验先做小样本流定位（grep 一次两个文件）再定核验通道。

## E9: mixin INVOKE 注入带额外参数 → InvalidInjectionException；LocalCapture 前缀 capture → LVT incompatible（预案命中，低损）

- **现象**：首轮启动 Blocks.<clinit> 失败（InvalidInjectionException: wg$mjti 描述符多一个 int）；改 LocalCapture.CAPTURE_FAILHARD 后二轮 LVT incompatible at opcode 46。
- **根因**：①纯 @Inject 无 locals 时 handler 只能收方法参数+Circular；②CAPTURE_FAILHARD 要求局部变量**全列匹配**，前缀 capture（只取 i / i+f）不成立。
- **修复**：按 j5-rng-trace-plan §5.2 预案回退最低保障集（MJT0/MJTD/MJTT/MJTG/MJTX 纯 HEAD/RETURN），删除两个 capture 注入点。
- **教训**：方案 §5.2「最低保障集」预案使两次失败零数据损失——**风险预登记是有效防线**（对比 E6 无预案裸奔二犯）。

> **⚠️ E11 部分取代（260906-06，§15.4）**：本条「正确 pop=-2605116321200055220（popseed_check2 复算吻合）= 正确 seed FEATURES pass」的归属判断**反转**——java-LCG 公式命中的是 populateEntities（CheckedRandom）pass；真 FEATURES pass = pop=-4568734542690011764（Xoroshiro 公式逐位命中，generateFeatures 调用点）。取代详情：.investigations/jungle-l/260906-06-errors.md E11 + j5-baseline-260906-06.md 核心发现 1。本条其余事实（同 run 双 pop 并存、实机 464,71,-252 无树、第四查纪律方向）不受影响——「实机零 mega」与今日服务器 pregen 零 mega 相互印证，但机制解释由「seed 污染」修正为「双调用点归属错绑 + Java 自身执行序依赖」。

## E10: J5「Java 2 棵 mega」基线被 seed 污染 —— 同 run 双 seed 并存 + 日志无 worldSeed 明文未被识别为采集缺口（260906-05 补录）

- **现象**：260906-01 的 j5-java-mjt.log 采集（gradle runServer + WG_SEEDLOG + diagchunk=29,-16 mixin）中，「Java 目标 chunk 2 棵 mega（(464,71,-252)/(479,71,-249)，h=27）」的 [MJT0]（L7972）属于 pop=-4568734542690011764 的生成 pass；而 worldSeed=8576294172403134396 的正确 populationSeed=-2605116321200055220（L12598）在同一日志同一次 run 内并存，正确 seed 生成中该 chunk **零 mega**。用户 2026-09-06 实机 vanilla（同 seed 新建存档）确认 464,71,-252 无树（479,-249 为橡树）。基于「Java 2 棵 vs Rust 0 棵」的 J5 placement 分歧基线因此**整体作废**——j5-trace-verdict-260906-01 §1/附录与 j5-gate-convergence-260906-05 事实 1 中「与 Java 同位同高」的对照对象不成立（Java 树 A 属旧 seed pass）。
- **根因**：①同一次 run 内并存两次不同 worldSeed 的 chunk 生成（疑似 level.dat 残留旧 seed + mod 嵌套管线双跑——「发现 #11 内层全管线 × 外层分步拦截」家族；旧 seed 具体值未反推成功，候选穷举未中，@anchor.idk 挂起）；②seed 三查在 260906-01 只核对了「目标 seed 数字在方案文件/命令行」，没有核对「日志内本次生成实际用的 populationSeed」——日志里根本没有 worldSeed 明文（grep `8576...` 零命中），这个缺口当时未被识别为采集有效性缺口，被污染的 mega 清单径直进了 J5 基线。
- **定位**：用户实机人眼验证（正确 seed vanilla 存档，464,71,-252 无树）与「Java 2 棵 mega」基线直接矛盾 → 主会话用 populationSeed 公式（ChunkRandom.setPopulationSeed；注意 nextLong 两段均为**有符号 int** 相加，第一版复算脚本符号处理 bug 曾误判「不匹配」，修正后 .tmp/jungle-l-260906/popseed_check2.py 复算 seed 8576294172403134396 @ chunk start (464,-256) pop=-2605116321200055220 与 L12598 逐位一致）→ 反查日志内 SEEDLOG population 值，发现同 chunk 两个 pop 并存（L7972 pass 用 -4568734542690011764，≠ 正确 seed 的 pop）。
- **修复/收尾**：①J5 基线重采——正确 seed 下 vanilla Java 的 5×5 mega 清单，用户实机核对 Rust native 预测位（(445,71,-222)/(469,71,-230)/(477,71,-234) 等 11 棵清单）；②后续 Java 探针采集有效性判据升级：[SEEDLOG] population 值必须与「目标 worldSeed + chunk 坐标」的独立复算值**逐位比对**（可复用 popseed_check2.py），不一致即废，与既有「seed 三查」并列为第四查。
- **教训**（高价值，三条）：
  1. **seed 三查第四形态**——「日志里没有 worldSeed 明文」本身就是采集有效性缺口；populationSeed 反推比对（≤一轮成本）应成为 Java 探针采集的**标准核验项**，不能只核对方案文件/命令行里的 seed 数字。
  2. **同 run 多生成 pass（嵌套管线双跑 #11）会让「同 chunk 两种生成结果」并存**——任何从日志抽取的「Java 侧事实」必须先绑定其所属 pass 的 pop 值；无 pop 绑定的事实不可作为对比基线。
  3. **用户实机人眼验证是成本最低的基线矛盾探测器**（本例一轮识破整个错误基线）——凡是单点可肉眼核验的地物结论，交叉核对优先级应高于继续堆日志分析。
