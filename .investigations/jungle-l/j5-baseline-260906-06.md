## 核心发现 1：setPopulationSeed 双调用点——E10 归属反转（candidate）

- **机制**（一手 yarn 源码核对，1.20.1 build.10）：
  - `ChunkGenerator.generateFeatures`（:344）：`setPopulationSeed(worldSeed, x, z)`，ChunkRandom 的 baseRandom = **Xoroshiro128PlusPlusRandom** → 产 pop_A；
  - `NoiseChunkGenerator.populateEntities`（:462）：同名方法同参数，但 baseRandom = **CheckedRandom**（48 位 java LCG）→ 产 pop_B。
  - `ChunkRandom.next(bits)` 分流（:31）：CheckedRandom 基类走 LCG，Xoroshiro 基类取 `baseRandom.nextLong() >>> 64-bits`；`nextLong` 走 BaseRandom 默认 = `(next(32)<<32) + next(32)`，**低位 int 符号扩展相加（MC-239059）**。
- **数值验证**（pop_feature_xoroshiro.py，Xoroshiro 复刻逐位命中）：
  - (464,-256) → **-4568734542690011764** = FEATURES pass（即 E10 认定的「污染 pop」）✓
  - (464,-256) → -2605116321200055220 = populateEntities pass（popseed_check2 的 java-LCG 公式命中的是它）✓
  - (224,-384) → -220628286890839268 ✓ 同规则。
- **推断（candidate）**：E10 的归属判断**反转**——「污染 pass」实为真 FEATURES pass；popseed_check2.py 用 java-LCG 公式，绑定的是实体生成 pass。**但它不改变 E10 的事实核**：260906-01 的 2 棵 mega 出自 FEATURES pass（pop=-4568…）属实；而今日同 seed 服务器 run 的 FEATURES pass 在目标 chunk **零 mega**，用户实机（正确 seed）也零 mega →「同 seed 不同 run 的 Java 自身即 placement 非确定」这一 E10 方向性结论反而被强化（跨 run/跨执行序依赖，与 workflow-patterns #49/#18 同族第三形态）。
