## 1. 假设陈述 + 机制链条

假设：pregen 侧 = gradle runServer 纯 vanilla 载体（.investigations/jungle-l/j5-baseline-260906-06.md:4「载体：gradle runServer vanilla」），实机侧 = 带 mods 的运行时。环境组件可通过四条机制改变 worldgen 输出：

- **M1 内容/数据 mod**：任何含 datapack（改 placed/configured feature JSON、biome、noise_settings）的 mod 直接改树链（count/rarity/spread）→ 落点集整体漂移。Fabric 与 Forge 双加载器并存时 datapack 合并顺序更不可预测。
- **M2 接管 mod（最强形态）**：CoreSwap 自身 Rust 接管 mod（worldgen mixin 侧，#55 证据链中的 NoiseChunkGeneratorMixin）若装在实机端 → 「实机树」由 Rust 生成、「pregen 树」由 Java 生成——**两执行体不同，交叉表 2/11 分歧就不是「Java 自身非确定」的证据，而是执行体差**。注意这与基线结论 2 的表述直接冲突：j5-baseline-260906-06.md:21 把 (469,71,-230) 记为「用户实机 **vanilla** 世界有」，:17 强化「同 seed 不同 run 的 Java 自身即 placement 非确定」——若 M2 成立，该推论的前提（实机=Java vanilla）被推翻，须按 §15.4 走取代记录而非改写原文。
- **M3 mixin 补丁**：即使不接管 worldgen，环境里任何 mixin/注入（性能优化 mod、Connector 转译的 Forge mod）可能改变 chunk 生成时序/特征执行序——而基线结论 2 已证 Java mega 放置依赖「邻 chunk 生成时序/邻域状态」（j5-baseline-260906-06.md:23「can_replace 读取邻 chunk 实况」）——时序型 mixin 足以改变落点，不需改 RNG。#55（workflow-patterns.md:995-1019）证明 Connector 生产环境与 dev 行为可静默分歧（SRG 命名/refmap），「装了但看起来正常」不等于「行为与 vanilla 一致」。
- **M4 版本/加载器 drift**：1.20.1 内小版本差（.1 vs .x 数据包修订）或 loader 注入改变类加载初始化序——先验低，登记不钻。

- S3：#50 家族先例——同 seed 同存档内装饰来源可因环境/时序分裂成两个域（workflow-patterns.md:869-875），「环境组件改变装饰输出」在本项目有实锤先例。

**反对/弱化**：
- O1：其余 9/11 点严格一致（j5-baseline:47）——若装内容 mod 改树链，通常预期更大面积漂移，2/11 局部分歧更像执行序噪声。但 mega tree 落点对邻域状态敏感（基线结论 2），局部敏感 + 全局对齐也可由 M3 时序型解释，故 O1 不构成强反对。
- O2：用户表述为「**可能的** Forge via Sinytra Connector」——Connector 在场性未确认；Fabric loader 本身不改 worldgen（纯加载器无 mixin 时零影响）。
- O3：260906-05 实机对拍当时被记为「用户实机 vanilla 世界」（j5-baseline:21）——若当时已核实为 vanilla，与今日「带 mods」表述存在张力，需环境清单定分止争（可能：世界生成时无 mod、后来装了；或当时口头 vanilla = 未核）。

## 3. 判别实验设计（最便宜先行）

- **E1（零成本，需用户/主会话转交）**：实机实例 mods 目录清单 + latest.log 头部 mod 列表（Fabric 启动日志逐行列 loaded mod）+ F3 左下环境行。判据：空 mods 目录（仅 fabric loader）→ B2 的 M1/M2 消亡、只剩 M3-弱 → 假设降权；出现任何 worldgen/datapack 类 mod → B2 升权；出现 CoreSwap worldgen mod → **M2 坐实路径**，直接进 E4。
- **E2（近零成本，随 E1）**：确认实机存档的生成时间线 vs mod 安装时间线——分歧区域 chunk 是否在装 mod 之前生成（level.dat/region 文件 mtime vs mods 安装时间）。若树在 pre-mod 期生成，环境差不是当前分歧的因。
- **E3（一锤定音，需主会话/用户执行）**：裸 vanilla 客户端（官方 launcher 纯 1.20.1，无 mods）同 seed 定位同区域，/forceload 或飞行加载 5×5 chunk 后记录 11 点 mega 有无。判据：裸 vanilla 与 pregen 一致（2 分歧点同 pregen）→ **实机环境差坐实，B2 confirmed 路径**；裸 vanilla 与实机一致 → B2 证伪，分歧回到执行序/生成次序解释（基线结论 2 方向）。
- **E3'（等价替代，若 E1 发现 CoreSwap mod）**：实机卸载该 mod 后复跑同区域——实机集应翻转为 pregen 集；或直接对照 ruston 清单：实机 11 点与 ruston 重合率显著高于与 pregen 重合率 → M2 坐实（当前样本 5 棵 vs 11 点，判别力弱，仅初筛）。
- 执行归属：E1/E2 需主会话向用户索取；E3/E3' 需主会话或用户跑客户端（subagent 沙箱无 shell，命令级验证必须主会话——AGENTS.md 八.12）。

## 4. 解释力与替代解释

解释力：B2（含 M1-M3）可完整解释双向 2/11 分歧；M2 形态还能额外解释「实机 Y 点恰在 ruston 集」。但**基线结论 2 的执行序依赖是已获数据支撑的竞争解释**（j5-baseline:22-23：Java 服务器 pregen 与实机同为 0 棵 @ 目标 chunk、can_replace 读邻 chunk 实况、§9.7 执行序口径声明）——B2 与执行序假设**不互斥**：环境差可改变时序，时序差产生落点差，最终落盘裁决应表述为「实机集 ≠ pregen 集的因 = 环境（B2）和/或执行序（B3），E3 的裸 vanilla 复跑同时判别两者」（裸 vanilla 客户端的生成次序与服务器 pregen 也不同序，故 E3 需配对解读：裸 vanilla≈pregen → 环境因；裸 vanilla≈实机 → 次序因；三者互异 → 双因并存）。
其他替代：单点人眼误差（j5-baseline:50 已列；但双向 2 点同时误判先验低）、存档版本迁移差（1.20.1 内 upgrade 不改 feature 落点，先验极低，登记）。
