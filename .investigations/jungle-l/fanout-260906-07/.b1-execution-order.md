## 1. 假设陈述 + 机制链条

**假设 B1/R1**：Java vanilla 的 mega jungle tree 放置判定会读取 3×3 ChunkRegion 内邻 chunk 的**实况方块/高度图**；邻 chunk 自身 FEATURES 阶段「已跑/未跑」取决于执行时序（pregen 的工作线程调度序 vs 实机渐进 forceload 序），因此同一 seed、同一 chunk 的 mega 集不是唯一确定的——存在执行序依赖。

机制链条（yarn 1.20.1 build.10 一手源码，.tmp/jungle-l-260906/mcsrc/）：
1. **每 chunk 独立跑特征**：`ChunkGenerator.generateFeatures`（ChunkGenerator.java:334-364）按 chunk 调用，`setPopulationSeed`(:344) + 逐 placed feature `setDecoratorSeed(l, m, k)`(:364)——RNG 流本身是纯函数（seed 唯一确定），**不引入时序依赖**；时序依赖只能来自世界读。
2. **ChunkRegion = 3×3 实况视图**：构造时持有 chunks 列表 + placementRadius（ChunkRegion.java:57-81，注释明确「neighboring chunks which can be accessed for block placement」；:87-96）。`getBlockState`(:167-168) 直接 `getChunk(...).getBlockState(pos)` 真读 chunk 实况；`getTopY(OCEAN_FLOOR)`(:422-423) = `sampleHeightmap+1` 也是实况（trees_jungle 的 heightmap 是 OCEAN_FLOOR 非 WG 型，见 .b1-attempt-count-candidate §1.5）。
3. **邻 chunk 状态是「时序变量」**：`getChunk` 的 status 门（ChunkRegion.java:129-137）只查 `isAtLeast(EMPTY)`——3×3 邻 chunk 作为 ProtoChunk 必在 region 内（FEATURES 的依赖图保证），**但其自身 FEATURES pass 是否已执行取决于调度序**：未跑 → 读到裸地形（无先前树/植被抬高的地表、无占位方块）；已跑 → 读到含其特征的实况。
4. **mega 判定吃这些读**：placed_feature `mega_jungle_tree_checked.json` 仅 `block_predicate_filter(would_survive jungle_sapling)`；trunk generate 逐块 canReplace/soil 判定走 `getBlockState`，跨 chunk 枝/叶写入走 `setBlockState`（ChunkRegion.java:290-321，对非 LEVELCHUNK 的 ProtoChunk 直写 chunk 实况 + pending NBT）——本 chunk 树写进邻 chunk 的方块与后跑邻 chunk 自己的树可能相互覆盖/影响。
5. **时序 → 判定输入 → 树集**：上述读的输入随执行序变化 → would_survive / heightmap y / canReplace 的接受集变化 → mega 集非确定。

## 2. 在盘证据：支持 / 反对

**支持点**：
- **双向分歧多点实证**：j5_cross_260906-06.py L5-14：11 点真值 + pregen 15 棵中 (469,71,-230) 实机Y/pregenN、(505,72,-261) 实机N/pregenY——**双向**（j5-baseline-260906-06.md L44-50），排除了「pregen 单侧缺失」类系统性解释，正是时序型差异的形态。
- **pregen run 内 chunk FEATURES 完成序确实是调度序而非空间序**（j5-java-baseline-260906-06.log [SEEDLOG] population 行，本次 grep 核实；judge 勘误注：population 行打印的是 **chunk 起始 block 坐标**，下文"chunk 448,-256"等实为 block 原点，对应 chunk (28,-16)，数值与结论不受影响）：chunk 448,-256 @L140269(18:38:04, Worker-17)、464,-240 @L199703(18:38:06, Worker-14)、**目标 chunk 464,-256 @L201357(18:38:06, Worker-18)**、464,-272 @L206203(18:38:06, Worker-5)、480,-256 @L257092(18:38:07, Worker-8)、496,-272 @L359167(18:38:09, Worker-13)——目标 chunk 的东邻(480,-256)与南邻(464,-272)的 FEATURES 都**晚于**目标 chunk 跑；而 496,-272（含 505,-261 分歧点）**很晚**(18:38:09) 才跑、其多数邻 chunk 先跑完。即 pregen 内「本 chunk 跑特征时各邻块处于何种特征状态」逐 chunk 不同，且与实机加载序必然不同。
- **Rust 侧证明「attempt 通过性」是分歧层**：j5-rust-camin-260906-06.err L602-608（[CNT]50→[SQ]→[TH]19@[432,65,-273]→soil=false 仍 [MJT0]/[TREESET] 成功）、L754-755（[TH]19@[442,64,-286]→[TPFAIL] id=8）、L785-786（[TH]27@[433,65,-273]→[TPFAIL] id=82）——同一 TH 值在「成功/失败」间摆动，失败原因（id=8/82 的占位方块）正是「读到的实况方块」类判定；这与「邻 chunk 实况状态参与判定」的机制同构。
- **同 seed 不同 run 的 Java 自身已见非确定方向性**（j5-baseline-260906-06.md L17：260906-01 的 2 棵 mega 出自 FEATURES pass，今日同 seed pregen 目标 chunk 零 mega）。

**反对点 / 未闭合**：
- Java 侧日志**只有 chunk 级 [SEEDLOG] population 行，无 per-attempt 打点**——无法直接证明分歧两点位（469,-230 ∈ chunk 29,-15；505,-261 ∈ chunk 31,-17）的失败/成功原因具体读到过哪块邻块状态。机制链第 4 环（mega 判定跨 chunk 读）在 mega 路径上是**静态推断**，未运行时取证。
- 2/11 分歧的实机侧无时序日志（人工飞行加载顺序未知），「实机序 ≠ pregen 序」目前是构造性论证而非观测。
- 替代解释未排除：单点人眼误差（对拍清单来源为用户人工飞行）、实机环境差异（归 .b2）。

## 3. 判别实验设计（主轴：Java [SQ]/[CNT] 全序列 vs Rust ca_min=on 逐 attempt 对齐）

**E0（零成本，在盘，主会话可先做）**：从 j5-java-baseline-260906-06.log 抽 5×5 相关 9 chunk（chunks 27..31 × -18..-14 → 432..496 × -288..-224）的 [SEEDLOG] population 行，构建「pregen run 内 3×3 FEATURES 完成序矩阵」——对每个 chunk 标注其 8 邻在本 chunk 跑特征前已完成的个数。预期信号：矩阵非平凡（0~8 混合分布），且 (29,-16)/(31,-17) 两 chunk 的邻完成态差异显著。此矩阵同时是 E1 的对照基准。

**E1（核心判别，需主会话跑）**：Java 侧最低保障 mixin 打点（沿用 .b1-attempt-count-candidate §4 的 Java 探针设计，本候选只重申判据字段）：`RandomFeature#generate` 每抽选 [SEL]、`HeightmapPlacementModifier#getPositions` 返回 k [HMY]、`would_survive` 结果 [WS]、`MegaJungleTrunkPlacer#generate` 入口/放置失败（对应 Rust [TPFAIL]）——每行带 chunk + pos。Rust 侧复用现有 [SQ]/[CNT]/[TH]/[MJTD]/[TPFAIL]（ca_min=on，载具 j5_tree_trace）。对拍判据：
- 若两侧 [CNT]/[SQ] 序列逐项相同（RNG 相位一致 → .b2 的相位差排除）而**终局分歧 attempt 的拒绝字段坐标/读取坐标落在本 chunk 之外（跨 chunk）**→ B1 直接支持且定位到具体门。
- 若 [SQ] 序列第 i 项起分叉 → 相位差先行，B1 降级为待相位修复后复测。

**E2（Java 内部判别，最强且便宜，需主会话跑）**：同一 seed、同一 Java 服务器，仅改加载序跑两次 pregen：① `forceload add` 一次性 5×5（现有口径）；② 分两批 `forceload add`（先 chunks 27..28 列，再 29..31 列，间隔若干秒）。比对两次 run 的 mega 集与 [SEEDLOG] 完成序。
- **预期判别信号（假设成立）**：两 run mega 集不同（至少分歧点位之一翻转），且翻转可由 E0 矩阵的邻完成态差异预测。
- **证伪判据**：两 run mega 集逐位相同（Java 对执行序不敏感）→ B1 被直接证伪，2/11 分歧的解释权移交 .b2（实机环境差异/RNG 口径）；辅以 E1 中 [SQ] 分叉在先 → 相位差优先。

## 4. 解释力评估

**成立时**：2/11 双向分歧自然解释——时序差可双向起作用：pregen 中目标 chunk(29,-15)【judge 勘误：469,-230 属 chunk (29,-15)，本文初稿误写 (29,-16)】跑特征时东/南邻尚未跑（§2 证据），其 mega 读到裸地形；实机渐进加载时同位邻块可能已带特征 → (469,71,-230) 类「实机Y/pregenN」。反向地，496,-272 在 pregen 里极晚才跑、其邻域已布满特征，实机则相反 → (505,72,-261) 类「实机N/pregenY」。同时解释「不存在唯一 Java 基线」（j5-baseline-260906-06.md L23 的推论），并要求 Rust 对比必须声明执行序口径（§9.7 扩展）。

**不成立时（E2 证伪）**：替代解释按优先级：① 实机环境差异（版本/优化 mod/Sinytra Connector 改写 worldgen 或块更新语义）——移交 .b2，其机制同样可解释双向分歧；② 实机侧观测误差（人工飞行 11 点真值的单点人眼误差，可解释 1-2 个点但双向各一点较牵强）；③ RNG 相位差（[SQ] 序列分叉，属 .b2 域，但 .b2 当前定位是环境差——若 E1 显示相位分叉则需重划 .b2 范围）。
