### §2.2 主会话观察中的错误/需修正项（本节为交付要求重点）

1. **【修正】观察 3 的「随机概率 ~0.25」量化不成立为单一数字**：0.25 隐含「483 每 run 出现率 p=0.5 + 两 run 独立可交换」两个未证假设。实测 modded 载体 run 对分歧率范围 **46%–81%**（f3r1↔f3r2=25/31≈81%；f3r1↔260905-13=11/24≈46%，见 §3.2 非可交换性），both-N 概率随所采 p 与 run 对统计不同落在 **~0.04–0.64** 区间，~0.25 只是对通道①最不利的取值。应改述为「双缺在通道①框架下不异常但非零信息量」。
2. **【修正·新实证】「共享点位 h 全部逐位相同」需限定范围，且存在反例**：主会话观察 2 对 **Java 共享点位**成立（439 h23/443 h28/456 h14/451 h26/511 h16/500,-226 h11 均复核逐位同）。但 **modded 共享点位存在 h 反例：500,75,-234 在 260905-13 modded 为 h19（stagemask3.log L425957），在 f3r2 为 h13（L376480）**——同 seed 同 x,z，两 dll 版本的 modded run 树基高差 6 格。这是 dll 版本间**局部地形差的直接数据层实证**（该点不在 Java E2a 集内，故不与观察 2 的字面表述冲突，但直接动摇其背后的「地形跨版本等价」含义），见 §4.3/§5。
3. **【澄清·证实】观察 4 的 carver 疑问已闭合：native j5_tree_trace **跑 carver**，且跑的是 Rust carver + Rust 特征**：`worldgen_handle.rs` L725-727 `flags & FLAG_SKIP_CARVER == 0` 即执行 `apply_carvers`（native 从不 set_flags → flags=0）；L562-564 flags=0 时 `apply_features` 也执行。故 native 臂 = Rust 地形+Rust carver+Rust 特征**三种全 Rust**，与 vivo（Java carver+Java 特征）只共享地形层。「native 483 Y h18 → Rust 地形满足放置条件」只能证 **Rust 谓词** 通过，**对 Java 谓词在 Rust 地形上能否通过零证明力**——主会话的谨慎是对的，且比对原生反证力的削弱比其表述更强。
4. **【勘误·表述歧义】「f3r1 前三棵 MJT0 与 stagemask3.log 逐位相同」仅对区域过滤前缀成立**：过滤后前三棵（439 h23/447 h13/435 h23）两 log 逐位同 ✅；但**全日志前缀第三棵即分叉**（f3r1: 417,71,-178 h28 @L15190 vs stagemask3: 423,71,-211 h14 @L8408）——spawn 窗口全局序列 run 间即漂移（与 run 级非确定一致）。引用该论证时应注明「区域过滤口径」。
5. 观察 1、观察 3 的数据面（交集 6 点、483 2/2 N、469 翻转）**全部核实无误**。

## §3 通道①（Java 特征流执行序差 = run 级非确定在 modded 载体的表现面）

### §3.1 直证证据

- modded 载体 run 级非确定**直证成立**：同 dll 同 seed 同协议两 run，区域集交集仅 6/31。此为通道①在本载体的存在性直证（数据层）。
- 机制同源性：modded 载体特征层 = 纯 Java vanilla 装饰器（F3 判定，mixin 只拦 NOISE/SURFACE），Java 侧 run 级非确定（E2a：基线 vs E2a 交集 7/27）的机制（worker 调度序 → 邻块实况差 → mega 翻转）**原样适用于 modded 载体**。
- Java 侧 483 稳定性：pregen×2 + 客户端 3/3 Y——483 在**纯 Java 世界**属稳定核。

### §3.2 量化（范围声明，不用单一数字）

- run 对分歧率样本（区域集 union 口径）：f3r1↔f3r2 = 81%；基线↔E2a（Java）= 74%；**f3r1↔260905-13 = 46%**。
- **非可交换性发现**：跨 dll、跨月的一对 modded run（905-13↔f3r1）共享度（54%）远高于同 dll 同日的 f3r1↔f3r2（19%）。若各 run 为同机制独立采样，成对共享度应相近——实测否。含义：mega 集由 chunk 完成序的**路径依赖**主导，run 间不是逐点独立抛硬币，单点概率模型（含 ~0.25）在此仅能作粗界（该区间以其自身批判的独立性假设为前提）。此非可交换性本身是通道①机制（调度序路径依赖）的旁证，但同时使「483 双缺的通道①概率」无法精确量化。

### §3.3 通道①的短板

- 纯通道①解释 483 需假设 483 在 modded 载体的每 run 出现率显著低于其在纯 Java 的稳定性（3/3）——因为 Java 代码相同，该降低只能来自**输入状态分布不同**（地形不同 → 谓词通过率不同），这已在向通道②借机制。
- 通道①对「905-13 Y → 今 2/2 N」的 dll 版本相关性无解释（§5）。

## §4 通道②（Rust 地形输入差致 Java 放置谓词系统性失败）

### §4.1 证据

1. **native 反证被本轮源码核实削弱**（§2.2-3）：native 483 Y h18 只证 Rust 谓词通过；Java 谓词（can_replace 的地表方块/上方空气输入，经 Java carver 与 Java surface 细节视角）在 Rust 地形上的通过性**无任何直接观测**。N-B 提出的「native Rust 地形 + Java 特征探针」判别臂本轮**仍未实施**（f3 两臂仍是完整 vivo 载体，两通道纠缠如旧）。
2. **今 dll 的 483 处地形无直接观测**：h 值只在放树的 run 可观测（树基高），483 在 f3r1/f3r2 均未放树 → 今日地形在 483 柱的表面高度/方块状态**是盲区**。所有「h18 逐位相同」的证据都来自放树臂（Java/native/905-13），不能外推到今日 modded 的 483 柱。
3. **1.0.26 发布自身的降级声明**（RELEASE-1.0.26.md §5）：「overworld 侧既有 A/B 存档回归尚未在新 dll 重跑（共享改动静态恒等 + nether 回归已补，风险低）」——overworld 地形在 1.0.26 dll 上无回归级验证，地形版本变量**未被既有验证闭合**。

### §4.2 执行体语义澄清（本轮源码核实，影响全部历史 native 引用）

- `j5_tree_trace.rs`：从不 `set_flags` → flags=0 → `worldgen_handle.rs` L725（carver）与 L562（features）全执行。
- 因此 T4 的 native off/on 两臂（含 483 Y h18）是「全 Rust」臂；「native off ≈ Rust 地形代理」的口径在 feature 层不成立。§9.7 已声明不可比，本轮给出代码级依据。

### §4.3 483 双缺 + 260905-13 Y → 今 N 的 dll 版本间翻转如何解释（任务核心问题）

通道②参与时的解释链（自洽且有一处实证支点）：

1. 905-13（旧 dll febe913e，2152960B）modded Y h18 = **Java 谓词在旧 dll 地形的 483 柱上通过**（单样本直证）。
2. **500,75,-234 柱 h19→h13**（§2.2-2）证明新旧 dll 地形存在**局部柱级差异**（同 seed 同载体同点位树基高差 6 格；候选机制：1.0.25/1.0.26 对 overworld 的共享改动（插值 cell 参数化/long 回绕加固/heightmap 哨兵）局部改写 density/surface 输出——机制未核实，draft）。
3. 若 483 柱同批受影响 → Java 谓词输入（地表方块/上方空气）改变 → 今日**系统性** N，2/2 双缺获得「非偶然」解释；通道①噪声叠加其上。
4. 纯通道①对「为什么恰好换了 dll 才开始双缺」无言——905-13↔f3r1 高共享（54%）说明两版本地形**大面等价**（否则共享点 h 也应大面积漂移，实测共享点 h 逐位同），**但不能排除柱级局部差**（500-234 即实例）。

反方向权重（支持纯通道①）：905-13↔f3r1 的 54% 共享 + 共享点 h 全同表明地形版本间**大面恒等**；483 若为柱级差则是一个「恰好影响判别焦点」的巧合——先验不高，但 500-234 的存在证明「柱级差」不是零概率事件。

## §5 第三互斥候选：dll 地形版本差作为独立变量

- **地位升级**：经 §4.3-2 的 500-234 h 差实证，该候选**不再是纯假设**，而是「已证实存在（至少一处柱）×影响面未测」的活跃变量。它与通道②的关系：通道②的载体即此变量（地形输入差的主要来源就是 dll 版本差），本文将二者合并陈述；若主会话认为需单列（例如 1.0.25→1.0.26 与 905-13 所用更旧版本之间的多次变更），应 fan-out 分解「哪次变更改了地形」。
