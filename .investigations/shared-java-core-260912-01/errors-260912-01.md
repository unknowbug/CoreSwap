## E1（最高价值）跨臂对照的 dll 血统污染 —— 整轮 V3 对照判定作废一次

**现象**
- 同一「同配方」对照的两臂，实际执行的引擎不同：post 臂 `[CppBridge] dll=` 自证行 = `838e89794a54e19d…`，pre 臂 = `dd3b645f2c79d2cb…`。
- 若不核对，两臂的指纹差异会被误归因为「Java 代码变更」，得出**相反的错误结论**（或掩盖真差异）。

**根因**（三环相扣）
1. `target/release/worldgen.dll` 当时是**早前 A/B 实验暂留在 target 的非权威产物**（`838e8979…`）——`target/` 被当成了实验暂存区。
2. A/B 驱动 `.tmp/vivo-stutter-260911-02/ab-threads/run_ab.ps1` 收尾无条件 `Copy-Item $bak $targetDll`，把 `.tmp/.../worldgen-target.bak-597e12ed`（= **1.0.28 引擎** `597e12ed`）写回 target。
3. 我在 `git worktree`（pre 树）里跑 `gradle :build`，构建链的 dll 同步把 target 拉回**权威** `dd3b645f`（= 1.0.29 发布票记录值）⇒ 两臂各自读到不同 dll，且**都不是我打算跑的那个**。

**定位**（怎么发现的）
- 起于「按纪律逐臂核对执行体自证行」：`[CppBridge] dll=… sha256=…`（不是看 target 文件 sha——那正是被污染的对象）。
- 反查：`Get-FileHash target/release/worldgen.dll` + `git ls-files *.dll` + 发布票 `.artifacts/releases/RELEASE-1.0.29.md` 的 `dll sha256: dd3b645f…`（权威锚）。
- 交叉锚：1.21.6 侧 `worldgen1216.dll` = `abd7d889…`，jar 内 dll 与 target 一致 ⇒ 用「票 / target / jar 内」三元组才锁定权威值。

**修复**
- 权威 dll 另存 `.tmp/shared-java-core-260912-01/w2/dll-canonical-1.20.1.dll`；
- **覆盖 harness 的备份文件**（原备份另存 `…bak-597e12ed.historical-597e12ed`），使收尾 restore 退化为 no-op；
- 两臂**重跑**（旧判定作废），重跑后两臂自证行同为 `dd3b645f`。

**教训**（可复用判据）
- **跨臂/跨 run 对照前 MUST 逐臂读「执行体自证行」核对**，不得只看 target 文件 sha，也不得只看「我传了什么参数」。
- **构建产物目录不是存档目录**：`target/release`、`build/libs` 都可能被实验/收尾逻辑改写；权威锚 = 发布票里的三元组。
- 交付侧同族（首例）：A/B 驱动带 `restore=<pre-sha>` ⇒ 交付/发版前 MUST 重核 target dll sha（**build-tooling #59 首例**）。本事故是**第二实例**，且污染对象从「交付产物」升级为「对照实验本身」。
- 已并入知识库：`knowledge/discovered/build-tooling.md` **#59（合并两实例）**（见 `knowledge-draft-260912-01-discovered.md`）。

## E2 fresh `git worktree` 不能当「条目级」基线 —— CRLF 物化导致全量伪差异

**现象**
- 用 `git worktree add .tmp/w2/pre-wt ce5286b` 建 pre 树并以它构建的 jar 作为 V1b 基线，条目级比对输出：`worldgen-data/**` 下 `placed_feature/*`、`processor_list/*`、`structure_set/*` 等**几乎全部文本条目显示差异**（外加 `[UNEXPECTED]` 洪泛），看起来像「Wave 2 大规模改了数据文件」——**完全虚假**。

**根因**
- `core.autocrlf=true`：`git worktree`/`git checkout` 把 LF 资源**物化为 CRLF**（git 在 checkout 时即会打印 `LF will be replaced by CRLF` 警告）；主工作树的同名文件是 LF ⇒ 同一逻辑内容、不同字节 ⇒ 条目 sha 全不同。
- 深层原因：把「同一物理工作树外的检出」当作「同字节基线」，混淆了**版本一致**与**字节一致**。

**定位**
- 差异面「全量且集中在文本资源、class 条目零差异」是签名式信号（代码差异不会只落在 JSON 文本上）。
- 决定性反证：`post2`（同树构建）vs 冻结 pre（同树构建）= 仅目标条目差异；`post3` vs `post2` = 仅 1 条 dll。⇒ 伪差异只出现在**跨树**比对上。

**修复**
- **放弃**用 worktree 产物做条目级基线；条目级 V1b 继续用**同一主工作树**构建的 `post2/post3` 与冻结 pre 比对。
- worktree 仅用于**运行期**判据（V2/V3 的 pre 臂）——类文件与运行行为不受 CRLF 影响（JSON 解析对换行不敏感）。

**教训**
- **条目级（字节）基线 MUST 来自同一物理工作树的构建**；跨树/跨机比对只可用于类文件或运行期判据。
- 判据信号：若差异「全量落在文本资源」⇒ 先怀疑换行/编码/物化，再怀疑内容。
- 已并入知识库：`build-tooling #60 简记`。

## E3 `javap` 方法级对拍的三个陷阱 —— 差点产出 4 处伪「语义变更」

**现象**
- 初版方法级对拍把 1.20.1 `stateById` 报为「30/30 指令但 6 行不同」、`lambda$static$0` 报为「98→97 指令、46 行不同」，看起来是 4 处语义变更；源码逐字对照证明它们**完全相同**。

**根因**（三个独立陷阱）
1. **`lambda$static$N` 按序号命名**：pre/post 的同一序号可能对应**不同 lambda**（合并后 lambda 增删导致重排）⇒ 按名对拍 = 拿 A 比 B。
2. **按行 zip 对拍在指令数变化处级联误报**：一处插入/删除会让其后所有行错位配对，「differing lines」被系统性高估（把「一处真差异」放大成「几十行差异」）。
3. **常量池序号 / `ldc`↔`ldc_w` / 分支偏移**是编译环境伪差，未归一化时淹没真差异（归一化后仍可能残留序号伪差，需源码或调用点复核）。

**定位**
- 交叉证据链：`javap -c -p` 归一化对拍 → 报差异 → **回源码逐字对照**（`git show ce5286b:... > pre.java`）→ 源码相同 ⇒ 判定为伪差。
- 后续（judge 独立复算）用「文本逐字 + `-v -p` 属性分类」三重判定，比 zip 计数更可靠。

**修复**
- 对拍规则改为：① 常量池/偏移归一化 ② **不用 zip 计数作为结论**（只作线索）③ `lambda$*` 不按名对拍，须靠源码或调用点 ④ 关键方法**回源码逐字对照**交叉确认。
- 结论里如实写明「`lambda$static$0` 差异不构成证据」（本波 record §4.6 已作废该证据）。

**教训**
- **`javap` 差异计数 ≠ 语义差异**；反编译/字节码工具的输出必须先过「归一化 + 源码交叉」两道，才可作为结论。
- 已并入知识库：`build-tooling #61 简记`。

## E6 把「多重集相等」误读为「序列相等」—— 顺序判据从未成立（judge 增量复审 D2 证伪）

- **现象**：记录 / 知识库 / 时间线 / 主题篇多处写「两族指纹 **multiset 与 sorted-sequence 双判全等**」「同实现跨 run 在本层**零噪声**（pre-r1 vs pre-r2 全等已证）」。judge 增量复审独立复算 6 臂 × 2 族的**原始行位置**矩阵后**证伪**：post vs pre-r1 `494/504`、post vs pre-r2 `504/509`、bulklog vs post `509/507`、perblocklog vs perblock `499/497`、**pre-r1 vs pre-r2 `495/503`（同 jar 重复跑）**、post vs perblock `486/488`（跨形态）⇒ **没有任何一对臂的原始序列相同**；多重集侧 12 对全部 `multiset_eq=True / onlyA=onlyB=0`，且 6 个 `fp-1.20.1-*.txt` 的 **sha256 全同 = `4b10f2be…`**。
- **根因（机制）**：① **判据越界**——「多重集相等」只证集合相同，却被读成「顺序也相同」；② **顺序本身不确定**——异步流水线（`form async`）下 chunk 完成顺序由调度决定，**同一份 jar 重复跑也不同** ⇒ 顺序在原理上不构成稳定的可判量（「两形态速度不同」是**不完整**归因）；③ **测量方法掩盖**——早期把指纹行**按 chunk 坐标排序后**比对，排序抹掉顺序信息，于是「相等」是排序的函数、不是数据的事实。
- **定位（怎么发现）**：judge 增量复审 D2 用「**不排序**的原始行位置矩阵」复算（`recompute_seq.py`；原始输出 `.tmp/w2-judge-delta/recompute-output.txt`）；触发点 = 主会话在 §4.7.9 写入「同形态同速臂之间序列全等」这一**未经复算**的推断（且把它写进了 KB/时间线）。
- **修复（改了什么）**：全库统一改为「**判据只用 multiset；序列不承载判据**」（原句按 §15.4 追加校正、**不删原文**）：`workflow-patterns` #14 补充案例（来源/观察/判据 3）、`docs/07` 判据与结论行、`docs/10` V2/V3 段、`INDEX.md` 合并行、record §4.7.2 V3 判据 + **§4.7.9 顺序口径整段重写** + §9.7 表 W 行、`NEXT_SESSION` 纪律 3b。
- **教训（判错经验）**：**「相等」判据 MUST 声明比较算子的定义域**——「多重集相等 / 排序后相等 / 原始序列相等」是三件不同的事；**任何「跨 run 零噪声」的声称 MUST 用同一算子在 ≥2 次重复跑上实测**（本轮同 jar 重复跑立即证伪）；**排序是信息销毁操作**，用排序后的数据去证「顺序性质」= 自证循环。
