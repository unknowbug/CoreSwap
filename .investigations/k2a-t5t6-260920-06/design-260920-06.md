## 0. 课题一句话

T5「chunk level ≤ 32 ⇒ light() 被调；level 33 档目标 = INITIALIZE_LIGHT 停在 light() 之前」目前是 I-静态推演（design-260920-05 §1.1 T5）。本实验对**受控单 chunk** 先施加**负臂票据**（目标档恰停 INITIALIZE_LIGHT）观测 light() 不被调，再**升档正臂票据**（目标 FULL）观测 light() 被调——单 run 双相、同 chunk 成对日志，把 T5 从 I 升档（升/降/证伪由数据说话）。

## ⚠️ 头号发现：level 33 负臂前提被一手源证伪（负臂必须用 34）

用户与架构计划给的负臂 = level 33（「level 33 档目标 = INITIALIZE_LIGHT」）。**一手核对结果：这一步 off-by-one**：

- `ChunkLevels.getStatus(level)`（.tmp/scout-260905-08/mcsrc/net/minecraft/server/world/ChunkLevels.java:11-13）：`level < 33 ? FULL : byDistanceFromFull(level - 33)` ⇒ **level 33 → byDistanceFromFull(0)**。
- `byDistanceFromFull(0)` = `DISTANCE_TO_STATUS.get(0)` = **FULL**（ChunkStatus.java:303-308 + 203-216：表首项 = FULL，第 2 项 = INITIALIZE_LIGHT）。
- 即 **level 33 档目标 = FULL**（LIGHT 在 FULL 之前必须完成 ⇒ light() 会被调）；**恰停 INITIALIZE_LIGHT 的档 = level 34**（byDistanceFromFull(1) = INITIALIZE_LIGHT，ChunkStatus.java:203-216）。

佐证旁证：`ChunkLevels.FULL = 33` 常量本身（ChunkLevels.java:6）与 `getType`：`level <= 33 → ChunkLevelType.FULL`（ChunkLevels.java:25）——33 属 FULL 族。design-260920-05 §1.1 T1 行（level≥33 → byDistanceFromFull(level−33)）与源一致，但其 T5 行「level 33 档目标 = INITIALIZE_LIGHT」是推演链套用出错（把 33 当成了第一个非 FULL 档）——**取代登记候选**：T5 表述应改为「level ≤33 ⇒ light() 运行；level 34 档 = INITIALIZE_LIGHT 停在 light() 之前」（§15.4 取代链，由本实验运行时数据 + judge 后落）。本实验设计据此：**负臂 = 34，正臂 = 33**。

## §2 双臂定义

### 2.1 臂定义

| 臂 | 票据 level | 目标档（一手推演） | 预期观测 |
|---|---|---|---|
| **负臂（相 N）** | **34** | INITIALIZE_LIGHT（A4） | 目标 chunk **无**任何 light 行为化日志（A6 两种行均 0），chunk status 停在 INITIALIZE_LIGHT |
| **正臂（相 P）** | **33** | FULL（A5） | 目标 chunk ≥1 条 light 行为化日志；status 推进至 FULL |

**正臂选 33 不选 22/32 的理由**：① 贴界最小差分——N=34 vs P=33 只差 1 级，任何「边界语义错位」都会被这一对臂直接暴露（22/32 的正臂离边界远，边界错位测不出）；② level 33 恰好同时验证头号发现 A5（byDistanceFromFull(0)=FULL）本身；③ level 22 已被上块海量实测间接背书（A8），再测一遍信息增量低。level 32 作为预登记降级变体 D-B32：若正臂 33 出现异常（如 chunk 停 LIGHT 不进 FULL），换 32 复跑一轮分辨「33 档位异常」vs「正臂机制整体失效」。

**负臂选 34 的理由**：一手源 A4（byDistanceFromFull(1)=INITIALIZE_LIGHT）。若用户坚持负臂 33，则按 A5 该臂实为正臂复制品，实验自动退化为单臂——此点已在上文头号发现中显式登记，需用户在设计定稿时拍板确认 34 口径。

### 2.2 chunk 选点

**cx=160, cz=96**。理由：
1. 位于 face bbox [13,-25]..[332,212]（record-260920-05 实测口径）内——与 face 判读系同一区域族，便于后续复用；
2. 距 spawn 票据中心 (0,0) Chebyshev 距离 = 160 ≫ 45（INACCESSIBLE，A7）——**排除 ambient spawn ticket 已把该 chunk 拉到 FULL 的污染**（否则负臂天然失效）；
3. 非 260920-05 网格 waypoint（waypoint x ∈ {14+20k}，160 不在内）——无历史票据残留叠加面；
4. 单 chunk + ring 副作用面 ≤ 23×23（A7），内存/时长代价可忽略（对 #213 hold-all OOM 教训的预算性规避，见 §6）。

### 3.2 判别判据（读法写死）

**日志行锚（产生代码点，一手）**：
- light 调用行为化行 = `[WBQ] ev=enter cx=<cx> cz=<cz>`（ServerLightingProviderMixin.java:1062，light() HEAD）与 `[FP-LIGHT] ev=call t=.. cx=<cx> cz=<cz> ..`（FormProbe.java:111-113，Rust 接管成功）。
- 票据档位直读（非参数自述，#118 式硬门）= `[FP-EDGE] ev=probe phase=<N|P> .. lvl=<L> status=<S>`：probe 代码点在 server 线程直读两个**运行时状态**——① `ChunkTicketManager` 票位 holder level（`getChunkHolder(pos)` 反射调用，ChunkTicketManager.java:106 定义/515-519 消费同式）或等价 `cm.getChunk(cx,cz,EMPTY,false)` 非 null 途径；② `chunk.getStatus().getId()`（Chunk 运行时状态字段）。`lvl=` 是读数不是 `addTicketWithLevel` 参数回显。

- **判据 N（负臂）**：目标 chunk (160,96) 上，`[WBQ] ev=enter cx=160 cz=96` = 0 且 `[FP-LIGHT] ev=call cx=160 cz=96` = 0（phase=P 之前的全窗）；**且** `ev=probe phase=N` 行满足 `status=minecraft:initialize_light`（=INITIALIZE_LIGHT 档自证「到达 LIGHT 前置但不过」）。两者同时成立 ⇒ N PASS。
- **判据 P（正臂）**：目标 chunk 上 `[WBQ] ev=enter cx=160 cz=96` ≥1 或 `[FP-LIGHT] ev=call cx=160 cz=96` ≥1（全窗任意时刻）；**且** `ev=probe phase=P` 行 `status=minecraft:full`。⇒ P PASS。
- **硬门 mismatch 即 VOID**：probe 行 `lvl=` 值 ≠ 预登记档位（N=34/P=33）⇒ 票据未如预期生效，全采集 VOID（exit 1），不进判读、不冒充 PASS/FAIL。`[WBQ]` 行与 `[FP-LIGHT]` 行互为 #81 成对互证（enter 有而 call 无 = init0/degrade 分账面已有既有 ev 覆盖，判读时按 WbQualStats 7 类终态归账）。
- **读法矩阵（预登记，防事后挑读）**：
  - N PASS + P PASS ⇒ T5 修正后表述（level ≤33 ⇒ light 运行；34 档停 light 前）获运行时直接证据，candidate 升档交 judge。
  - N FAIL（负臂观测到 light 行）⇒ **T5 证伪 ⇒ 立即 fan-out 两互斥候选**（.b1 = 静态链 A4/A5 有误（DISTANCE_TO_STATUS/传播语义另有机制）/.b2 = 日志打点窗口问题（如异步竞态打点滞后）），禁止主会话自推（架构计划分叉处置条款）。
  - P FAIL（正臂无 light 行且 status 非 full）⇒ 票据升 FULL 后 light 仍不跑 = 独立异常，登记 + fan-out（.b1 = GRACE/域批封板竞态 /.b2 = 目标 chunk 生成侧异常），同禁自推。
  - N PASS + P FAIL、或双 FAIL ⇒ mixed，全量落盘 judge 强制复核（MUST）。

## §6 风险与降级变体

1. **R1 头号风险 = 用户原判负臂档位错**（本档头号发现）：若仍按 33 施加负臂，A5 推演 ⇒ 该「负臂」目标 = FULL，light 必被调 → N FAIL → 触发 fan-out 空转一轮。处置 = 设计定稿时拍板 34 口径（本档显式请求用户确认，§2.1）。
2. **R2 T6 传播非 Chebyshev 线性加距的暴露面**：A2 传播器语义是 I。若实为其他度量（欧氏/曼哈顿/塔式传播），症状 = 环档分布读数（§3.3）与 A7 表错位；对 N/P 主判据无影响（票位自身档 = ticket level + 0，任何度量下成立——A1/A2 票位语义）。T6 的判读独立降权登记，不绑定主判据。
3. **R3 OOM/时长预算**：本实验常驻生成面 = 票位 + 环 ≤ 23×23 = 529 chunk 量级（A7），vs 上块 hold-all 臂 318×236≈75k chunk（#213 OOM 实锤面）低 2 个数量级 ⇒ 无 OOM 险。预算：boot+Done ~60-120s（转引上块）+ SETTLE 25s + N 相 30s + P 相 30s + 尾窗 60s ⇒ deadline **900s**（只松不紧）。GRACE_MS=10s（LightDomainBatch.java:21，record-260920-05 直读已核）≪ 30s dwell，封板竞态余量充足。
4. **R4 P 相依赖 N 相遗留**：N 相 chunk 已生成到 INITIALIZE_LIGHT，P 相升档只需跑 LIGHT 及以后任务——这是设计意图（双相共享生成面，压缩变量），但意味着 P 相不重验「从零 FULL 推进」。降级变体 D-Independent：P 相换邻近独立点 (162,96)（Chebyshev 距 2，仍在 34 票 CARVERS 环内需先加票再判）——仅当判读出现 mixed 且嫌疑指向「N 相遗留污染」时启用，启用时先重登记再跑。
5. **R5 probe 直读的时机竞态**：`ev=probe` 在 server 线程 tick 内直读，若目标 chunk 任务仍在异步执行，status 可能尚未推进到目标档（假阴性读数）。缓解：probe 前置等待 = 该 chunk `cm.getChunk(cx,cz,<对应档>,false)` 返回非 null 后再读（阻塞式到位确认，server 线程合法调用同 vanilla tick 语义）；此实现细节属 T2 收敛闭环，判据面只认 probe 行自证值。
