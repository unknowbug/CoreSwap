## 1. 结论（candidate 建议）

**b1 成立**：R1/R2 裸引用 + `getStatus().isAtLeast(FEATURES)` 轮询形态，其对 bulk 写回（NOISE 段）的可见性/holds-before 义务**已被 `ProtoChunk.status` 的 volatile 字段语义独立覆盖，不需要 join future，也不依赖 ChunkHolder future 完成语义**。CoreSwap 未新增 data race 缺口。sentinel 的「读者不登记」是**检测面缺口（OQ-4）**，不是**内存可见性缺口**——两者必须分开裁决。

四件套（参照 workflow-patterns #143 单写者论证）在读者形态下的「可见性链」件：

1. **写侧程序序**：BulkWb 原地换容器 + 三计数 plain 写，发生在 `populateNoise` HEAD-cancel 接管内 = NOISE `doWork` 内，程序序先于该 future 完成。
2. **发布点（release）**：`ChunkStatus.runGenerationTask` 的 `thenApply` 在 `doWork` 完成后调 `protoChunk.setStatus(this)`（mcsrc ChunkStatus.java:359-363）；`ProtoChunk.status` 是 **volatile** 字段（ProtoChunk.java:42, :215-216）⇒ volatile 写 = release，把 doWork 线程的全部 plain 写（含 `wgSetBlockStateContainer` + 计数）发布。若 thenApply 落在与 doWork 不同的线程，CompletableFuture 完成语义补足该段 HB。
3. **读侧门（acquire）**：`wgLightNeighbor` 对 volatile `getStatus()` 的读（Mixin:313）= acquire；门过（≥ FEATURES > NOISE）⇒ NOISE 的 release 集合全可见；门不过 ⇒ 返 null 跳过（Mixin:314-316），**读到旧值只导致 skip/回退，不导致撕裂读**。
4. **单调性与冻结期**：status 只前进（runGenerationTask :361 设前有 `isAtLeast` 守卫；无任何回退写点）；FEATURES 之后的任务（INITIALIZE_LIGHT/LIGHT/…）**不写 block 容器**（只写 nibble/light-on 标志）⇒ 门过即读面冻结，读者与写者无并发写窗口，race 结构上不存在，HB 只是兜底。

## 3. OQ-5 回答（b1 视角）

`readPacket`→`writePacket` 读容器内部的「半构造 data」窗口**不存在**，两层独立保证：
- **主保证（b1）**：读者被 status 门挡在 FEATURES 之后（E5），而 `data` 换新发生在 NOISE（E3/E4）并由 volatile status 发布（E1/E2）——门过即见完整新容器（或完整旧容器，若门在写前通过但门过即意味着 NOISE 已发布，故实际只见新）。
- **兜底保证（vanilla 固有）**：`PalettedContainer.data` volatile（E7）——即使有未过门的读者（R4 传播形态），读到的也是完整旧或完整新的 Data 引用，record 内部不可变，无撕裂。07 篇 :1285 的「读者只见旧或新」论证对 R1/R2 同样成立且更强（多一层 status 门）。
- P-β 空节瞬态计数（W5）：`sec.isEmpty()` 读的 nonEmptyBlockCount 在 BulkWb.java:207 plain 写、由同一 volatile status 发布——计数器是**观测**瞬态的工具，不是正确性问题。
