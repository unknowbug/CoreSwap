> 错误优先原则：本文件只记「为什么错」；验证通过的正确结论走 verdict/知识库。

## E1（**最高价值**）— 照抄 vanilla 的分段锁语义 ⇒ 非可重入 `LockHelper` **同线程自锁死**

**现象**（2026-09-10 20:26–20:52，`oa-r1` / `os-r1` **两臂都**）：Chunky 任务启动后**零进展**——
`chunky progress` = `Processed: 0 chunks (0.00%), Rate: 0.0 cps, Current: 0, 0`；服务器 CPU 增量 **0.1 s/12 s（≈0.01 核）**；
`run\world\region` mca mtime 停在任务起始时刻；**等 40 min 也不会自己好**（不是慢，是停）。

**根因**：本块首版按 vanilla 1.20.1 `NoiseChunkGenerator.populateNoise`(:337-346) 形态加了 sections **外层锁**
（`ChunkSection.lock()`），而本工程写回路径**自带逐次锁**：

```
CppBridge.writeChunk:519   sec.setBlockState(x, sy, z, st)
  → ChunkSection.setBlockState(x,y,z,state)            // 4 参重载 → lock=true
  → ChunkSection.setBlockState(x,y,z,state,true)
  → PalettedContainer.swap(x,y,z,value)                // ★ this.lock(); try{…} finally{ this.unlock(); }
  → LockHelper.lock()                                  // ★ 非可重入 Semaphore（acquire 阻塞）
```

⇒ 同线程在**已持有**该 section 信号量时，写回内部的 `swap()` 再次 `lock()` → **永久 park**。
vanilla 能加外层锁，是因为它自己的 fill 在持锁后改用 `setBlockState(..., lock=false)`（`swapUnsafe`，**不加内层锁**）；
本工程写回用的是**加内层锁**的重载 ⇒ 两者不可混搭。

**定位方法（决定性、可复用）**：沙箱 `jstack`/`jcmd` **全拒访**（JVM attach 被拦，exit 1）⇒ 自建**门控停滞看门狗**
（`StallWatch.java`，`-Dcoreswap.stallwatch=30`，默认关）把 `Thread.getAllStackTraces()` 打进日志；从 dump 直接读出阻塞链：

```
net.minecraft.util.thread.LockHelper.lock(LockHelper.java:42)
net.minecraft.world.chunk.PalettedContainer.lock(PalettedContainer.java:45)
net.minecraft.world.chunk.PalettedContainer.swap(PalettedContainer.java:142)   ← 内层锁
net.minecraft.world.chunk.ChunkSection.setBlockState(ChunkSection.java:63)
wg.bench.CppBridge.writeChunk(CppBridge.java:519)
wg.bench.CppBridge.fillChunk(CppBridge.java:394) → …wgDispatch…wgPopulateNoise(NoiseChunkGenerator.java)
net.minecraft.world.chunk.ChunkStatus.runGenerationTask(ChunkStatus.java:357)
```

**辅助判据（无 dump 也成立）**：**同步臂与异步臂都卡** ⇒ 与「异步分派 / 完成跳回」无关（该变量被排除），
嫌疑收敛到**两臂共有**的新增项（= 外层锁）。

**修复**：删除外层 sections 锁（`wgLockSections`/`wgUnlock` 整段移除，分派器退化为 `completedFuture(work.get())` /
`supplyAsync(work, WG_FILL_POOL)`）= 1.21.6 R3 的已验证形态；锁语义交由写回路径自带的逐次 `swap()` lock/unlock 承担。

**教训**：
1. **照抄参考实现的「锁语义」前，必须先核自家写路径的锁语义与可重入性**——vanilla 的「外层锁 + `lock=false` 写」是**成对契约**，
   只搬可见的一半 = 自锁死。同族：跨实现搬运必须成对核对（签名迁移 #25/#55 = workflow-patterns 域；参数映射 = build-tooling #8/#19/#47 域）。
2. **同线程自锁死 ≠ 互等死锁**——判别签名 = **双臂都卡 + CPU ≈ 0 + dump 里同一把锁出现两次（持锁帧 + acquire 帧）**。
3. **卡死 ≠ 慢**：先量 CPU 增量与进展探针（本项目 `chunky progress`），再谈性能；把「0 进展」当「生成慢」会污染整块结论。
4. **沙箱禁 attach 时，把线程栈变成日志内证据**（门控看门狗，默认关、间隔可调；见 workflow-patterns #114）。

## E2 — 裸 `gradle runServer` 在 1.20.1 多项目构建**级联** `:content-test:runServer`（真实接线坑，**非**本块卡死根因）

**现象**：1.20.1 臂日志出现 `> Task :content-test:runServer`（**两次**），随后
`Failed to start the minecraft server … testcontent.TestContentMod.<clinit> … IllegalStateException: This registry can't create intrusive holders`；
该子工程服务器**共用同一个 `run` 目录 / 同一个 world**。1.21.6 臂日志只有 `> Task :runServer`。

**根因**：仓库根执行**裸任务名** `gradle runServer` 会匹配所有子工程同名任务；`content-test` 子工程是独立 loom 工程，
其 `runServer` 必然失败（测试内容 mod 不能独立启动），且与主服务器抢同一世界目录。

**定位方法**：`Select-String -Pattern '^> Task'` 列 gradle 实际任务（级联任务是一行显式日志，**不看必漏**）；对照 1.21.6 臂确认差异。
**修复**：驱动改用**根项目限定名** `gradle :runServer`。
**教训**：多项目构建里任务名必须限定到根项目；与 `-P` 映射作用域（build-tooling #47）、缺映射静默不生效（build-tooling #8）同族——
**「我以为我跑的是那个任务/参数」的接线错觉**，任务级证据（`^> Task`）是唯一便宜自证。
**同形不同因留档**：该级联一度被当作 `Processed` 恒 0 的嫌疑根因，最终由 E1 的 dump 定因 ⇒ **同形现象必须各自独立证据**。

## E3 — Chunky 1.3.146 任务状态**跨 run 持久化**，残留任务使下一臂 `chunky start` 静默不开始

**现象**：`os-r1`（第二轮回）`chunky start` 回
`[Chunky] A task was already started for this world. … type '/chunky confirm'`——该臂因此**根本没有新任务**，
最终同样表现为「Processed 恒 0」（与 E1 **现象同形、机制不同**；不复核就会误判为同一根因）。

**根因**：Chunky 把任务落到 `run\config\chunky\tasks\<namespace>\<dim>.properties`（实测 `chunks=0, cancelled=false`），
**删 `run\world` 不会清它**；驱动原来只删 world。
**修复**：驱动每臂开跑前 `Remove-Item run\config\chunky\tasks -Recurse -Force`。
**教训**：**「清环境」清单要覆盖工具自己的状态目录**（不只世界目录）——否则「上一臂的残留」会伪装成「本臂的失败」
（残留态造假象：build-tooling #18 导出产物家族 / workflow-patterns #49 完成度伪差家族，本项为其「工具状态目录」形态）。

## E4 — 手写 NBT reader 与已验证版不一致 ⇒ 静默少解析（7703 → 760，**不报错**）

**现象**：本块首版对拍工具 `diff_1201.py`（为 1.20.1「无 xPos」改造而手写）在自比（同一目录比自身）时输出
`A chunks=760 common=760 blocks=2744320 diff=0 (0.0000%)`——**完全不报错**，看起来像「工具正常、两臂零差」。

**根因**：手写 `payload()` 时把 **TAG_Byte(1) 读成 8 字节**（`r.i8()`）、**TAG_Byte_Array(7) 读成 i4 长度**，
与 260910-05 已验证版（`diff_arms.py:15-36`：tag1=`u1()`、tag7=`n(u1())`）不一致 ⇒ 解析失步 ⇒ 大量 chunk 被
`try/except: continue` 静默丢弃（7703 → 760）。

**定位方法**：**自比 + 计数**（同一目录比自身：`common` 必须 ≈ 该臂实际生成/写盘 chunk 数，且 `diff` 必须为 0）；
以及**灵敏度正对照**（两个已知不同的臂必须报非零差）。
**修复**：`payload()` 与已验证版**逐行对齐**。
**⚠️ 本条后半句已被 E5 更正**（「标签 7 读 i4 长度」当时被当作正确写法——规范读法确实是 i4，但那时的**对齐动作本身**把上游 E5 缺陷一并继承；
真正的结论见 E5：对齐是必要非充分）。
**教训**：解析器「能跑出数字」不等于「解析对了」——**先跑自比（0 差 + common 非空）与正对照（已知不同必报非零）**，
再信任何差异百分比（workflow-patterns #12/#13 家族：空集/零比对数先疑工具）。

## E5 — **继承自 260910-05「已验证」工具**的 NBT 规范错：TAG_Byte_Array 长度按 1 字节读 ⇒ 静默丢 0.6% chunk

**现象**：把 E4 修正为「与 260910-05 逐行对齐」后，自比通过、正对照正常，看似无问题。但写知识库时的**读码复核**发现
`diff_arms.py` / `diff_1201.py` 的 `t==7`（TAG_Byte_Array）分支读 **`u1`（1 字节）长度**，而 NBT 规范是 **TAG_Int（4 字节）**。

**根因**：tag 7 在本工程的 region 数据里**真实出现**（两载体合计 **9046 次**，`.tmp/tag7_scan.py` 普查）；读错长度即失步。
用两种读法对同一 region 目录（`region-os-r1`）实测：

| 读法 | 解析成功 | 解析失败 | 唯一 chunk 键 |
|---|---|---|---|
| 旧（tag7 = u1，260910-05 口径） | **7703** | **46** | 7703 |
| 新（tag7 = i4，规范） | **7749** | **0** | 7749 |

⇒ 旧读法**静默丢弃 46/7749 = 0.6% 的 chunk**（`try/except` 吞掉，不报错）；键集无丢失（`only_old=0`），
但**分母与「有效可对比地形集」被低估**。**失步签名**：普查中出现非 NBT 合法 tag 号（15/16/18/32/64/…/255）。

**影响面**（复审 C1 实测，**比「丢 0.6% chunk」严重得多**）：同输入自比（`region-os-r1`）下，旧读法把 **section 并集 85,047 → 规范 185,976（×2.187）**、
**块分母 348,352,512 → 761,757,696（×2.187）**、**sections/chunk 11.04 → 24.00**（24 = 1.20.1 overworld 的合法结构值，旧读法只摸到真实空间的 **45.7%**）；
且新旧映射**非单调**（正对照 0.0351%→0.0325% 略降，而跨形态 0.0648%→0.0298% 近半）⇒ **禁止按固定比例折算**。具体：
① 本块 §4.2 的 region 旁证数字（已用规范读法**重跑**，见 verdict §4.2 修订值）；
② **已 confirmed 的 260910-05（1.21.6）`common` 与差异百分比同口径严重受影响**（不是 0.6%，而是分母体系不同）——
已在该判决 §8 以**补充收敛（E5）**记录（原文不删不改），**复算登记为显式待办、禁按比例打折**；
③ 定性结论（如 end「0 块差」）是否翻转**须复算后才能判**（不再作「量级不变」的推断）。
④ 修订前的工具版本（`u1` 版）**未归档**（`diff_arms.py` 原件仍在 260910-05 归档内 ✓，本块首版 reader 未留档）⇒ 「×2.187」只作口径量级说明，**不可当可复算系数**。

**定位方法**：**不要只与「已验证版本」对齐——还要过规范**。具体：① tag 类型普查（统计各 tag 出现次数）；
② 出现任何非 NBT 合法 tag 号即失步证据；③ 关键冗余量核对（解析数 vs region 槽位数 vs 生成器自报 chunk 数）。
**修复**：`t==7` 改为 `n = r.i4(); return r.n(n)`；重跑全部对拍。
**教训**：**「与已验证版逐行对齐」是必要条件而非充分条件**——被继承的工具缺陷会随「对齐」动作一起继承；
**自比 0 差 + 正对照非零**只能证明「工具自洽」，不能证明「解析符合规范」。工具复核必须加一条**规范/冗余量核对**。
