## P0 交接假设廉价独立验证（开工前置，MUST）

**待验假设（NEXT_SESSION 260903-04 draft）**：「双线程同 handle Mutex=0.61× ⇒ GPU 异步流水（Mutex 未真串行化 GPU）」。

**验证方式**：静态源码核对（gpu_ffi.cpp / gpu_density_engine.cpp / vulkan_runtime.h）。

**证据链**：
1. `gpu_density_engine.cpp:106-118` `fill()` 全程持 `std::lock_guard(im.fillMtx)`——CPU 拆分、upload、dispatch、readback 全在锁内。
2. `vulkan_runtime.h:119-120` `dispatch` = `vkQueueSubmit` 后立即 `vkWaitForFences(VK_TRUE, UINT64_MAX)`——**同步阻塞等待 GPU 完成**。
3. `vulkan_runtime.h:125` readback = `vkMapMemory` + memcpy（host 可见内存直接拷贝）。
4. `gpu_ffi.cpp:8` 注释明确 shim 不加锁、互斥策略在调用方。

**结论（candidate，待 judge）**：❌ 推翻——同一 handle 的 fill 是**完全同步串行**执行（锁 + fence 阻塞 + 直接 map 读回），不存在跨线程 GPU 流水重叠。0.61× 并行加速不能用「Mutex 未真串行化」解释，必有其他原因（候选：①探针计时口径混杂（含非 GPU 段/线程启动）②驱动 fence 等待行为与其他段重叠——**待 P4 廉价复测**；此残留异常不阻塞接线）。

**对接线设计的影响**（本包采纳）：
- 多线程共享同一 handle **无 GPU 并行收益**（全串行），生产接线按「GPU 提交单线程化」设计：GPU 角点源由单一提交点供数（或每线程独立 handle，后置评估），不投入双线程共享 handle 的并发优化。
- create 75s → handle 级缓存照计划（once_cell 进程级）。

**状态**：**candidate**（judge 260903-05 通过，产物 `.artifacts/lossless-accel/route2-p0-judge-260903-05.md`）。
**验证分层声明**：本次为静态源码核对 = **Degraded 静态审查级**（非 trace/probe 数据层）；confirmed 前须补数据层验证（fence 实测计时 / 双线程 trace）。
**judge 修正**：0.61× 异常候选扩为 ≥3 类互斥候选（①探针计时口径 ②fillMtx 锁竞争+CPU 段调度/cache 干扰 ③dispatch 每次重建 command pool+fence 固定开销在小批量放大 ④测量探针污染——项目已知系统性风险）；处置改两步走：P4 先用无探针整批 wall + 调用计数验 0.61× 真伪，再按结果 fan-out。边界保留：「每线程独立 handle」是唯一真 GPU 并行路线，不沉默丢弃；dispatch 资源复用/批量合并入接线待办。

## P1/P2 设计定案（260903-05）

### 语义钉子（P2 前置调查）
- `wg_fill_density` / `fillOneChunkCore` 的 C++ GPU 消费方式 = **逐块** finalDensity（98304 点/chunk，4096/批），shader 内含 interp_N（每 interp 节点 8 角点+三线性在 GPU 内完成）——GPU 每点输出 = 生产级 per-block finalDensity（f32），e2e 3.128e-07 已验证（worldgen_api.cpp:841 注释 + gpu-corner-probe）。
- **否决「角点 + Rust 侧插值合并」方案**：combine 外层非线性，插值合并 ≠ Java 语义（违背 lossless）。接线形态 = 逐块批量（对齐 C++ GPU 分支）。
- 性能诚实预期：5µs/pt × 98304 ≈ 0.49s/chunk，**当前慢于 Rust CPU 路线**（~10ms 级）。本包交付「语义无损 + 可切换通路」；性能改善靠 dispatch 资源复用/批量合并（judge 低垂果实，后续工作包）——这正是双线路并存可切换架构的价值。

### 实现（P1 抽象 + P2 接线）
- 抽象层：复用既有 `DensitySource`/`ChunkDensitySampler` trait（terrain.rs:179——本就是 MOD 扩展点），不新建 trait；路线①（CpuBackend/DFC/Transpiler）与 GPU 是该 trait 下的并列实现，env 切换。
- 新模块 `WorldgenRust/src/gpu_ffi.rs`：LoadLibrary(gpu_ffi.dll) 动态 FFI + 进程级 handle 缓存（Mutex<Option<(seed, handle)>>，create ~75s 一次付；seed 变更销毁重建）+ `GpuDensity`（sample_chunk = 整 chunk 24×4096 批量 → slices[98304]；sample_interp = 索引直读 lx+lz*16+ly*256）。
- 门控：`WG_GPU_DENSITY` env（优先级 gpu > dfc > transpiler > macro），默认关（零退化铁律）；spv 路径 = WG_GPU_SPV env 或 wgDir/../../cpp/worldgen/gpu-assets/final_density.spv（对齐 C++ 约定）。
- graceful fallback：GpuDensity::new 失败（dll 缺失/create 异常/spv 缺失）→ None → 回退既有链路；fill 失败 → chunk 级回退逐点路径。
- 并发：C++ fill 内部 fillMtx + fence 同步 = 全串行（P0 结论），Rust 侧 Mutex 仅保 handle 表正确性；GpuHandle 新类型 unsafe impl Send。
- 装配点：worldgen_handle.rs 两处 fill 分支（fill_chunk_blocks + diag_pre_surface_column）。
- 编译：cargo check/build --release 全绿（260903-05）。

### P2 验证结果 + 重大发现（260903-05）
- **语义 PASS**：gpu_fill_probe 整 chunk 98304 点 major_diff(>1e-4)=0，max_diff=5.729e-6（f32 ULP 级）——Rust FFI 逐块批量 = DFC-CPU 逐点，语义无损对齐。create 74.6s 一次付符合预期。
- **性能吻合 D24 历史结论（非新异常）**：实测 25.4s/chunk（258µs/pt）与 gpu-accel-errors.md:604 的 C++ I6 实测（24 chunks 11 分钟 ≈ 27s/chunk，被主动终止）完全一致。GPU 逐块方案在 C++ 侧已被 D24 定性不可行（8672 floats/点 split 表带宽死局），I6 代码仅保留为开关默认关。
- **含义**：本包 P2 交付的逐块 GPU 通路 = 语义无损、可切换、但性能与 C++ 侧同 Dead（已验证通道本身 + handle 缓存 + fallback 全链路工作）。
- **路线②真正可行形态（本次钉定）**：shader 输出 **5 channels @ cell corners**（valBuf 布局中 channels 本来就在，需 gen/FFI 改动暴露）→ GPU 算 1225 角点/chunk（corner-probe 实测 5µs/pt ≈ 6ms/chunk，22-39× 加速域）→ Rust 侧 trilerp 5 channels + compute_final_density combine（代码已有，transpiler 路径同款）= **精确 Java 语义**（channels 线性插值+外层逐块 combine 正是 Java NoiseChunk 语义）。这是「角点 + Rust 插值」的**合法版本**（插值发生在 combine 之前，非线性红线不触）。
