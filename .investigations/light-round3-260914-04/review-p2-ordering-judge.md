## 2. 排序意见

### 2.1 矛盾点裁定

- **A-① 与 C 的吸收边界**：.b1 说"A-① 被 C 完全吸收"；.b3 说"A 的 opacity 表内联仍独立有效"。**.b3 正确、.b1 表述过强**：C 形态下 Java 预编码 palette 项为 rawId|lum，Rust 解码得到 v 后仍需按 rawId 查 opacity 表（mod.rs:230-232 现路径不变）——lookup 仍在，直接索引改造（A-①）在 C 下依然适用。矛盾实质但影响小（~10 行改动，两种排序都不吃亏）。
- **A-② 与 C 正交**：两份一致（sky_fall 融合与输入形态无关），无矛盾。
- **B 是否跳过**：.b3 主张 B 仅作 de-risk 可被"C 的 Java dump 对拍"吸收；.b2 主张 B 改动面最小可先做降险。实质分歧 = 验证价值是否需要 B 的独立交付承载。裁定：**b3 论证更充分**——B 独立收益建立在不稳的 0.3s 减法口径上（可能≈0），而其验证价值（accessor 链 + 位序）可由 C 的 §2.3 dump 对拍完全替代；且 B 先行会产生一次多余 e2e 迭代。若计时探针实测 Java 段 ≥0.5ms/chunk 则反转（b2 自己预埋了该开关）。

### 2.2 推荐实施序

**P0 探针轮（前置，一揽子）**：b2 Java 段 chunk 级计时 + b3 writePaletteIndices/bits dump + b1 非 air 格/15-区间计数器，同轮实机跑（主会话执行，输出落 cmd-output/）。
**P1 = C（吸收 A-① 与 B 的共享件）**：上限最高（1-2s），四层改动一次到位，golden 单元对拍（dump 期望值 vs Rust 解码器）压位序风险；旧 ABI 并存回退已设计。
**P2 = A-②（sky_fall 融合，C 形态下仍有效）**：独立 commit，劣化哨兵回退。
**P3 = B**：仅当 P0 计时推翻减法口径（Java 段 ≥0.5ms/chunk）才独立实施；否则并入 C 已覆盖，跳过。
**不建议**：A 排 C 前（A-① 重复劳动 + A 上限最低）。
