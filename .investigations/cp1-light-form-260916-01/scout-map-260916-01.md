## A. vanilla 1.20.1 光照增量调度同位形态参照

（源根 = `versions/1.20.1/data/mc_src_extract/net/minecraft/`，下略 `mc:`）

### A1. 触发点（谁提交）

| 触发 | 入口 | 引证 |
|---|---|---|
| 方块变化（运行时） | `WorldChunk.setBlockState` → `lightingProvider.checkBlock(pos)` | `mc:world/chunk/WorldChunk.java:272` |
| 生成期方块写入 | `ProtoChunk.addBlockState`（同款 checkBlock） | `mc:world/chunk/ProtoChunk.java:131` |
| chunk 管线两步 | `ChunkStatus.INITIALIZE_LIGHT` → `lightingProvider.initializeLight(chunk, bl)`；`ChunkStatus.LIGHT` → `lightingProvider.light(chunk, bl)` | `mc:world/chunk/ChunkStatus.java:237-247` |

### A2. 异步化外壳（关键形态①）：公开入口只入队、从不内联执行

- `ServerLightingProvider.doLightUpdates()` 直接调用即抛异常：`"Ran automatically on a different thread!"`（`mc:server/world/ServerLightingProvider.java:54-56`）——vanilla 结构性禁止同步执行。
- 所有公开方法（`checkBlock:59-67` / `setSectionStatus:86-94` / `propagateLight:97-104` / `setColumnEnabled:107-114` / `enqueueSectionData:117-125` / `setRetainData:141-149`）一律 `enqueue(...)` 进 `ChunkTaskPrioritySystem`，并落入 `pendingTasks` 缓冲（`enqueue:127-138`）。

### A3. 执行器与线程（关键形态②）

- 专用 FJP：`Util.MAIN_WORKER_EXECUTOR = createWorker("Main")`（`mc:util/Util.java:89`）= `ForkJoinPool(clamp(cores-1, 1, max.bg.threads))`，线程名 `Worker-Main-N`（`Util.java:182-206`）。与 260915-03 判读一致（Util.java:183；common pool 参数不接线，#153）。
- 两个 mailbox actor：`TaskExecutor.create(executor, "worldgen")` 与 `TaskExecutor.create(executor, "light")`（`mc:server/world/ThreadedAnvilChunkStorage.java:184-189`）——"light" actor 是**单 mailbox 任务队列**，跑在上述 FJP 工作线程上。
- 优先级排序器：`chunkTaskPrioritySystem` 的 `controlActor`（`TaskQueue.Prioritized(4)`，"sorter"，跑在同一 FJP，`ChunkTaskPrioritySystem.java:36`）。

### A4. 调度优先级与去重（关键形态③）

- `ServerLightingProvider.enqueue` 每条消息携带 `(chunkPos, chunkStorage.getCompletedLevelSupplier)`（`:127-137`）→ 排序键 = **chunk 票据等级（动态）**。
- `ChunkTaskPrioritySystem.updateLevel`：票据等级变化时对所有队列 `updateLevel(旧等级, pos, 新等级)` 重排（`ChunkTaskPrioritySystem.java:100-107`）——即 **FIFO 之上叠加持续重排**（这正是 R3「vanilla 持续重排」形态的源码锚点）。
- 分发：`enqueueExecution` 从 `LevelPrioritizedQueue.poll()` 取出**同 chunk pos 的一批任务为 Stream** 顺序 ask 到 light actor（`:138-150`）。
- **@anchor.idk（去重语义）**：`LevelPrioritizedQueue` 的重复 pos 合并/累加精确语义本次未逐行读（该类在 `server/world/` 提取树中是否存在也待核）；只可断言「按 chunk pos 分桶、桶内顺序执行」，不可断言「同 pos 重复任务去重」。

### A5. 泵与同步点（关键形态④）

- 泵 1：`ServerChunkManager.MainThreadExecutor.runTask()`——每次主线程轮任务先 `lightingProvider.tick()`（`mc:server/world/ServerChunkManager.java:586-592`）。
- 泵 2：`ThreadedAnvilChunkStorage.tick` 内 status 推进时 `updateChunkStatus(pos)` + `lightingProvider.tick()`（`ThreadedAnvilChunkStorage.java:537-538`）；主循环入口 `ServerChunkManager.tick(shouldKeepTicking, tickChunks)` → `TACS.tick`（`ServerChunkManager.java:332-342`）。
- `ServerLightingProvider.tick()`：`(pendingTasks 非空 || hasUpdates) && ticking.compareAndSet(false,true)` 才投递到 light actor（`ServerLightingProvider.java:186-193`）——**同一时刻至多一个 runTasks 在飞（AtomicBoolean 单飞门）**。
- 批粒度：`pendingTasks` 攒到 **1000** 立即 runTasks（`:34,134-136`）；`runTasks` 单批最多处理 1000 条，**先跑全部 PRE_UPDATE 段 → 一次 `super.doLightUpdates()`（全队列增量 BFS 排空）→ 再跑 POST_UPDATE 段**（`:195-218`）。即引擎侧批粒度 = 「≤1000 条 pending 任务共享一次 doLightUpdates 排空」，BFS 状态跨任务累积在持久 LightStorage 里。
- 同步点：`light()` 的 POST 段（`chunk.setLightOn(true)` + `releaseLightTicket`，`:179-183`）作为 chunk LIGHT→FULL future 链的完成门；增量 checkBlock 无每点同步（主线程零等待，效果由泵节奏 + 优先级重排承载）。

### A6. 引擎增量形态（关键形态⑤）

- 持久共享存储：`LightStorage` + per-provider `blockPositionsToCheck` 队列（`ChunkLightProvider.checkBlock` 只入队，`mc:world/chunk/light/ChunkLightProvider.java:121-123`）；`doLightUpdates` 清空待查点后跑增/降两路传播（`:144-160`，`method_51570`/`method_51567`），跨 chunk 读世界由 2 槽 chunk 缓存支撑（`:94-113`）。
- 结论：vanilla = **种子化增量 BFS + 跨 chunk 共享持久存储 + 票据级优先级重排 + 单飞批泵**（与 07 篇形态审计 L5/L6 判定的错配对象一致）。

## B. Rust 现役形态盘点

### B1. 现行路径（light 接管，方案 B）

- **接管点**：`@Inject(method="light(Lnet/minecraft/world/chunk/Chunk;Z)...", at=HEAD, cancellable)` 于 `ServerLightingProviderMixin.wgLightRustTakeover`（`versions/1.20.1/java/src/main/java/wg/bench/mixin/ServerLightingProviderMixin.java:424-513`）；门控 `-Dcoreswap.light.rust`（`:63`），fallback = vanilla 永久回退（`:137-142,479-486`）。
- **调用线程**：继承 vanilla `light()` 任务线程 = worldgen 生成 mailbox → `Worker-Main-N` FJP（B1 臂实测 23 个 Worker-Main 线程各 135-200 次调用，`.investigations/form-audit-260915-03/record-260915-03.md`；与 vanilla light actor 同池不同队列——vanilla 光照走 "light" actor 专属队列，接管后走 worldgen 生成链自带线程面）。
- **同步性**：**整链同步内联**于调用任务：收集 3×3 方块（ThreadLocal 缓冲 ~7MB/线程，`:158,257-328`）→ JNI `lightComputePacked`（候选 C）/`lightCompute`（`:445-466`）→ 同线程 `enqueueSectionData` ×24×2 写回（`:493-494`）→ `setLightOn(true)` + `wgReleaseLightTicket`（`:497-499`）→ cancel 原方法跳过 vanilla `propagateLight`（`:44-48`）。**每 chunk 一次 JNI 往返 + 一次全量重算，无队列、无批泵、无优先级、无去重**。
- **批粒度**：per-chunk 3×3 域全量重算（`worldgen-core/src/light/mod.rs:162-174` ABI 契约；`light_compute_inner:278-470` = fill → block BFS → sky 直落+seed BFS → export 五阶段，全部在单次调用内、以 blocks9 快照为输入、输出即中心 chunk 终值）。**无跨 chunk 持久 LightStorage、无增量传播、邻域重叠部分每次 ×9 重复算**（07 篇 L4/L5/L6 与 260915-01 判定引用一致）。
- **JNI 边界**：`versions/1.20.1/rust/src/jni_bridge.rs:344-415`（lightCompute）/ `:421-486`（lightComputePacked，`light_decode_packed` 拆帧后走同一 `light_compute` 内核，`mod.rs:193-263`）；`catch_unwind` → rc=-3，JNI 边界禁 panic（`jni_bridge.rs:279,389,486`）。
- **锁面**：`LightEngine.scratch: Mutex<Scratch>`（CP-3，260915-02 落地；`mod.rs:64-69,115`），锁在 `light_compute_inner:293` 获取并**持有至整次重算结束**——当前形态下该 Mutex 把全部并发 light 调用**整段串行化**（poison 不 panic，恢复续用，`:67-68`）。

## C. CP-3 Mutex scratch 并发面交互清单（#150 耦合铁律核对）

### C1. CP-3 引入的锁面（现役）

| 锁 | 位置 | 持有时长 | 竞争者 |
|---|---|---|---|
| `LightEngine.scratch: Mutex<Scratch>` | `worldgen-core/src/light/mod.rs:69`；锁定于 `:293`，持锁贯穿 fill/block/sky/export 全阶段 | **单次 light_compute 全程（~92.5ms 量级）** | 所有并发 light JNI 调用（23 Worker-Main 线程） |

- 事实判定（引用 #150）：在 CP-3 之前，「光照车道串行化」事实上充当了 `RefCell scratch` 的锁；CP-3 Mutex 化后该保护显式化，但**持锁时长 = 整次全量重算**，等于把串行化从「隐式车道」换成了「显式整段互斥」——任何 CP-1 修复若不改变「scratch 全局唯一 + 全程持锁」结构，增量/批化收益都会被锁重新串行化吃回。

### C3. 三候选修复形态各自的并发面触碰清单

**(i) 3×3 域批中心化**（按域去重重叠邻域、域级算一次共享结果）：
- 新增「域 → 计算结果」共享缓存 ⇒ 触碰 C2 第三行同构面（谁写/谁读/clear 波及，#110 三面核对 MUST）；
- scratch 必须从「全局唯一全程持锁」改为「域内可分区」或「per-domain 缓冲」，否则中心化批量提交使 Mutex 持锁窗口变长（整批串行）；
- 与 Java 侧 ThreadLocal 收集缓冲（mixin :158）的批次归属须重排（当前按 chunk ThreadLocal，域批后同一 3×3 数据被多 chunk 引用 ⇒ 缓冲生命周期跨调用）。

**(ii) vanilla 形态复刻**（持久 LightStorage + 种子化增量 BFS + 异步 light actor + 批泵）：
- LightStorage 成为**跨线程持久可变状态** ⇒ 新增真正的共享锁/单写者设计（vanilla 的保护 = 单飞门 CAS + light actor 单 mailbox，`SLP:186-193` + TACS:184-193——复刻时该两件是锁语义本体，不可省）；
- #150 耦合铁律正中此臂：增量车道若恢复串行化，其下被掩盖的并发缺陷必须同批修复（现役唯一已知被掩盖面 = 原 RefCell scratch，已被 CP-3 Mutex 显式化——复刻臂下 Mutex 应收缩为 storage 级，scratch 转 per-call/per-thread）；
- 与 vanilla 同位需对齐泵语义（主线程 tick 泵 + 票据级优先级）——工程量最大，碰 Java 侧调度面最深。

**(iii) 混批 JNI**（一次 JNI 调用带 N 个 chunk）：
- Rust 侧循环 N 次 `light_compute` ⇒ **Mutex 顺序获取释放 N 次**，串行化面不变、JNI 往返降 N 倍（对 ~10× 绝对等待中「每 chunk 成本差」分量直接作用；对 G3 时机形态漂移**不作用**——重算时机分布未变）；
- 缓冲所有权变化：N 份 blocks9 输入 + N 份输出的一次性传输 ⇒ Java 收集侧 ThreadLocal 结构与生命周期重排（同 (i) 第三条）；
- fallback 粒度变粗（整批 rc 语义需分 chunk 错误定位），JNI 错误面重设计。

### C4. 给 fan-out 三 worker 的输入要点

- **worker.b1（候选 (i) 域批中心化）**：起点 = mod.rs `light_compute_inner` 五阶段划分（:278-470）+ 域重叠 = 3×3 邻接 chunk 集合交叠度（生成序近邻 chunk 域重叠 ≥1 列带）；输入要点 = C3(i) 三触碰面 + #110 缓存三面核对判据 + G3 漂移归因须论证「重算时机分布改变」（(i) 只在确能合并重叠域时才改时机）；输出 .b1 候选 + 批度上限核算（#22 免凑数：乘数须独立实测来源）。
- **worker.b2（候选 (ii) vanilla 形态复刻）**：起点 = A 节五关键形态（A2 外壳/A3 执行器/A4 优先级/A5 泵与批/A6 存储引擎）逐一同位清单 + C3(ii) 锁语义本体（单飞门 + light actor + LightStorage）；输入要点 = G1 drift 5.83% 与 vanilla 0.84% 基线（form-audit-260915-03 interpretation §1.7）、L5/L6 错配定义（07 篇 :1540,1546）；输出 .b2 候选 + 同位覆盖面声明（哪些 vanilla 形态项复刻、哪些让位）。
- **worker.b3（候选 (iii) 混批 JNI）**：起点 = jni_bridge.rs lightCompute/LightComputePacked ABI（:344-486）+ mixin 收集/写回（:424-513）+ T_fill 分布（92.5ms，§15.4 现行口径）；输入要点 = C3(iii) 三触碰面 + 「绝对等待 ~10× 归因分解：per-chunk 成本差 × 排队深度」（interpretation §1.3 传导）——b3 只作用于前者；输出 .b3 候选 + 批宽 N 敏感性（JVM↔Rust 缓冲拷贝量随 N 线性）。
