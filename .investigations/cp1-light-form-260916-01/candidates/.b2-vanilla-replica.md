## 1. 形态描述：按 vanilla 形态复刻的分层方案

原则：**不做 per-chunk 3×3 全量重算 + 同步内联**，把 Rust 光照引擎改回 vanilla 的「种子化增量 BFS + 持久共享存储 + 异步 light actor + 批泵 + 票据级优先级」五形态，按「最小复刻集 → 完整复刻集」两阶段推进。

### 1.1 最小复刻集（Phase A——先消除 L1/L2 + L5/L6 主错配）

| 层 | 归属 | 复刻内容 | vanilla 同位锚 |
|---|---|---|---|
| 异步外壳 | **Java 侧** | mixin 不再 HEAD cancel 同步内联，改为：`light()` 提交任务到 **light 专属 mailbox actor**（新建 `TaskExecutor.create(worker, "coreswap-light")`，跑在既有 `Util.MAIN_WORKER_EXECUTOR` FJP 上）；公开入口只入队不执行；调用 future 在 light 完成后回填 | SLP:54-56（同步即抛）、TACS:184-189 |
| 批泵 | Java 侧 | `ServerLightingProvider` 复刻 pendingTasks 缓冲 + `ticking` AtomicBoolean **单飞门 CAS** + ≤1000 攒批/排空驱动；泵源 = 既有 `ServerChunkManager.tick` 挂点（现成 FormProbe mixin 面）+ status 推进点 | SLP:34,131-138,186-193,195-218；SCM:586-592 |
| 持久 LightStorage | **Rust 侧** | JNI 层从「无状态 light_compute(blocks9)」改为「**跨调用持久 LightStorage 句柄**」：新 ABI `light_session_begin/seed/flush`（handle 持有 block/sky light 数组 + 待查种子队列，生存期 = server 实例，随 world unload 释放）；增量 BFS 增/降两路复用现役 BFS 内核，输入从 3×3 快照改为种子点集 | ChunkLightProvider:121-160、A6 |
| 种子化入口 | Java→JNI | `checkBlock` 类单点/小批种子经队列透传（packed long 批量，非逐点 JNI），JNI 侧并入待查队列，**不触发立即重算**——执行时机由批泵统一排空 | WorldChunk:272 / ProtoChunk:131 |
| JNI 边界重画 | 边界 | 从「1 chunk = 1 JNI = 1 次全量」改为「**N 个种子/section 状态 = 1 次 JNI 排空**」：`light_pump(seed_batch) → (dirty_sections, light_data)`；写回沿用 `enqueueSectionData` 通道但只写 dirty section。错误语义按 session 记账（rc=-3 时整 session 标脏 → 下轮全量重建 fallback，避免 per-seed 错误定位复杂化） | jni_bridge.rs:344-486 现役参照 |

Phase A 不复刻：票据级优先级重排（提交序 FIFO 承载）、去重精确语义、`light()` POST 完成门细化（保持现役 light ticket 释放点）。即 Phase A 已经消灭「邻域 ×9 重复算」（L5）与「无共享存储」（L6），并把执行搬离调用任务线程（L1/L2）。

### 1.2 完整复刻集（Phase B——对齐调度时机形态）

| 层 | 归属 | 内容 |
|---|---|---|
| 票据级优先级 | Java 侧 | enqueue 消息携带 completedLevelSupplier；复刻 `ChunkTaskPrioritySystem` 的 updateLevel 持续重排 + 分桶 poll（R3 已裁「优先级在驱动窗内否定」⇒ Phase B 排后，先量化 FIFO 下残余漂移再决定是否上） |
| 完成门同位 | Java 侧 | `light()` POST 段改由 light actor 回调触发 `setLightOn(true)` + releaseLightTicket，使 chunk LIGHT→FULL future 链与光照实际完成时机绑定（G3 时机形态的 vanilla 同位） |
| 去重 | Java 侧 | chunk pos 分桶执行（桶内顺序）；重复 pos 合并语义带保守假设（见 §2 idk 处理） |

### 1.3 Rust 侧锁语义（Phase A 即位，见 §3）

`scratch: Mutex` 收缩：storage 由 **session 单写者**保护（light actor 单消费者 + 单飞门保证至多一次 pump 在飞 ⇒ LightStorage 天然单线程访问域，无需粗 Mutex）；scratch 从全局 Mutex 改 **per-call/per-thread**（增量排空时 engine 局部缓冲）。原 CP-3 Mutex 保留为 fallback 全量重算路径的守护（fallback 时 session 不可用，走现役路径）。

## 2. 与 vanilla 1.20.1 六维逐项对照表

| 形态维度 | vanilla（scout 引证） | 本方案 Phase A | Phase B | 错配消除判级 |
|---|---|---|---|---|
| 触发粒度 | per-block 种子入队 + per-chunk 两状态步 | checkBlock 类种子经队列入 JNI 会话（per-block 粒度保留）；chunk 两状态步沿用接管点 | 不变 | 触发粒度对齐 |
| 执行位置 | light 专属 mailbox actor，调用方零阻塞 | ✅ light actor + 专用队列，同池 FJP | 不变 | L1/L2 消除 |
| 引擎状态 | 持久共享 LightStorage + 增量增/降 BFS | ✅ Rust session 持久 storage + 增量 BFS | 不变 | L5/L6 消除 |
| 批粒度 | ≤1000 任务共享一次 doLightUpdates 排空 | ✅ ≤1000 种子/任务单飞 CAS 批排空 | 不变 | L4 对齐 |
| 优先级 | 票据级动态重排 + 分桶 poll | ❌ FIFO（显式让位） | ✅ 复刻 | R3 裁定：驱动窗内已否定 ⇒ 让位有据（C-3 范围限定：boot 段未覆盖，Phase B 前置补测） |
| 同步点/完成门 | POST 段为 chunk 完成门；主线程仅泵 tick | 泵 tick 同位；完成门仍按现役接管点时机 | ✅ POST 完成门同位 | G3 时机形态主错配在 Phase B 才完全对齐（见 §4） |

**scout 3 项 @anchor.idk 在本方案中的处理**：
1. **去重/合并精确语义（A4/C5-1）**：Phase A 不需要（FIFO + 分桶即可，不依赖合并语义）；Phase B 前置动作 = 读 `mc:server/world/LevelPrioritizedQueue` 一手源补证；补证前 Phase B 实现按**保守假设**（不合并、同 pos 桶内顺序全执行——保守方向是"多做不少做"，只损性能不损正确性）。
2. **mc_src_extract 版本完整性（C5-2）**：本臂静态引证全部取自 scout 已与 260915-01/03 judge 行号交叉一致处；Phase A 实施前追加一次 DataVersion 抽查（廉价，一次 grep 级核对）。
3. **light() 由 worldgen 还是 light actor 分发（C5-3）**：Phase A 自建 "coreswap-light" actor，不继承 vanilla 拓扑 ⇒ 该 idk 对本臂降为**参考项非阻塞项**；Phase B 对齐完成门时才需追 ChunkHolder future 链接线（届时先读源补证）。

## 3. #150 耦合面分析（正中此臂）

**#150 判定引用**：事实串行化会掩盖其下并发缺陷；解除串行化与被掩盖缺陷修复 MUST 同批；防御性修复可先行、解粘不得先行（INDEX #150）。

### 3.1 被掩盖并发缺陷清单（现役形态下）

| # | 被掩盖面 | 现状 | 本臂下暴露方式 |
|---|---|---|---|
| 1 | 原 `RefCell scratch`（CP-3 前隐式锁） | 已被 CP-3 `Mutex` 显式化，但持锁 = 整次 92.5ms 重算（mod.rs:69,293） | Phase A 改增量排空后，若 scratch 仍全局唯一，pump 内串行化会把增量收益吃回——**Mutex 收缩为 fallback 路径守护 + scratch per-call 化同批落地**（防御性修复先行于 Phase A 合入） |
| 2 | LightStorage 跨线程可变状态 | 现役无此状态（无状态 per-chunk） | Phase A 新增 ⇒ 必须同批立「单写者」论证（见 3.2），不得靠"现在没人并发写"的偶然 |
| 3 | 写回 `enqueueSectionData` 线程面 | 现役在调用任务线程内联写回 | Phase A 移入 light actor 完成 → 写回线程面变化，与 #152 阶段推进链标脏纪律交叉：dirty section 写回须在 status 链可见点之后核对 |

### 3.2 单飞门 + actor 锁语义设计（本臂核心安全论证，Degraded 静态）

- **单写者构成**：LightStorage 只被 `runPump` 访问；`runPump` 只在 `ticking.compareAndSet(false,true)` 胜出后投递，且 light actor 为单 mailbox（任务顺序消费）⇒ 任一时刻至多一个排空在飞 ⇒ storage 访问串行且由**结构**（CAS + 单 actor）保证，非靠锁。
- **§143 四件套适用**：唯一写者 = 胜出 CAS 的 pump 投递链；happens-before = actor mailbox 消费序；残留边界 = **session 生命周期与 server reload 交错**（world unload 时若有 pump 在飞 → 显式 drain/失效句柄，实现时登记）；未来代码义务 = 任何绕过 enqueue 直调 storage 的新路径即破坏论证（代码注释 + review 清单登记）。
- **同批防御性修复**：① scratch per-call 化（消除 #150-1）；② fallback 全量路径保留 CP-3 Mutex 不动（fallback 与 session 路径互斥由 session 有效标志承载）；③ poison 语义沿用现役（恢复续用）但 session 层加一致性版本号，rc=-3 整 session 标脏。

## 4. 预期指标：G3 drift 与 A1 P50 作用机制与量级推演

> 推演假设显式声明（#149：禁引绝对秒数作判据；以下全部为**方向 + 相对量级推演**，非预测值）：

**假设 H1**：G3 drift 5.83%（G1 Mutex dll 臂）主因 = 接管后光照重算时机从「light actor 队列排空」变为「worldgen 生成链内同步内联」，改变了 chunk 完成序与 light 可见时机的相对分布（scout B2 表「同步点」行判定；interpretation §1.7）。
**假设 H2**：A1 绝对首载等待 ~10×（near P50 513-1069ms vs 40-70ms）≈ T_fill 92.5ms × 排队深度（260915-03 判读自洽链），分解为「per-chunk 成本差」×「排队深度」两分量。

**作用机制推演**：
- **Phase A → A1**：直接作用于两分量——① 增量 BFS 消灭 ×9 邻域重复算 ⇒ per-chunk 光照成本理论降幅上界 ~9×（仅邻域重叠全命中时，实际待批度核算，#22 免凑数：须独立实测重叠度）；② 排空从「每 chunk 一次」变「≤1000 一次」⇒ 排队深度分量随批化下降。推演量级：A1 朝 vanilla 带收敛的主要杠杆，预期收敛到与 T_fill 新分布自洽的带内（**不可预登记具体 ms 判据**，按 #154 全域声明：以「对 vanilla 比值下降幅度」为方向判据 + 复测时预登记具体阈值）。
- **Phase A → G3**：**部分作用**——执行位置搬离调用链改了时机分布，但完成门仍非 vanilla 同位 ⇒ drift 预期**下降但不归零**。
- **Phase B → G3**：完成门同位后时机形态对齐，G3 预期收敛向 vanilla 0.84% 基线带（引用基线须带 §9.7 口径：form-audit-260915-03 同载体）。
- 若 Phase A 后 G3 无改善 ⇒ H1 证伪信号，drift 归因须重开 fan-out（预演登记，#153）。

## 5. 风险与验证设计

| 风险 | 等级 | 缓解/验证 |
|---|---|---|
| 行为等价：增量 BFS vs 全量重算终态差异（增/降两路边界、跨 chunk 2 槽缓存语义复刻失真） | 高 | **行为等价门**：确定性区域 dump 载体（#52/#115 形态）——同 seed 固定 region，Phase A 臂 vs 现役臂逐 chunk 指纹 + 逐 section light 值比对；噪声锚取同配置 run-to-run 实测基线（#111），跨实现口径分形声明 |
| 并发缺陷（storage 单写者论证漏洞 / unload 竞争） | 高 | stallwatch 看门狗（#114）+ 多轮并发 bench 交错配对（#103）+ session drain 压测（反复 load/unload） |
| 批泵驱动不足（tick 泵在 boot 段不跑 → 任务堆积） | 中 | 驱动窗探针预演（复用 FormProbe 虚拟玩家票据驱动 #155）+ boot 段覆盖补测（CP-4 C-3 教训：boot 段未覆盖即预演旁证失败） |
| A/B 污染 | 中 | **同构建态单变量 A/B**（#150 判据家族）：同 dll（Phase A 增量路径需重编 → 退化为同构建双 flag 臂：`light.session=0/1` 同一 binary 两路径），交错配对、每臂正负成对行为化自证（bulk `[WG-BULKWB] calls=` 形态，#139①） |
| 自证硬门 | — | 覆盖点在构建上游 + `executed != want ⇒ VOID` 硬返回（#118）；臂标签显式清单禁 glob（#140） |
| 旁证臂（#153 预演） | — | 预演「旁证失败后结论可信度」：若票据驱动旁证臂失败 ⇒ 本臂对「驱动窗内优先级收益为零」的继承（C-3）失效，Phase B 优先级项自动升回必做——立项时即把该失败路径的应对排入计划 |
| 工程量最大（scout C3(ii)：碰 Java 调度面最深） | 高 | Phase A/Phase B 分段验收：Phase A 独立可交付（L5/L6/L1/L2 四维已消除即可量化收益），Phase B 只在 Phase A 判读后立项——避免一次合入无法归因 |
