## 1. 形态描述：跨 JNI 批次合并策略

### 1.1 现役形态（对照基线）

per-chunk 1 JNI：mixin `wgLightRustTakeover`（ServerLightingProviderMixin.java:424-513）在 `light()` 任务线程内，每 chunk 收集 3×3 blocks9 → JNI `lightCompute`/`lightComputePacked` 单次往返 → 同线程 24×2 section 写回。**每 chunk = 1 次 JNI 跨界 + 1 次全量重算**，无队列、无批、无优先级（scout B1）。

### 1.2 候选 (iii) 形态：Java 侧收拢、一次 JNI 下发 N chunk

**合批位置：Java 侧收拢（方案 A，本臂选定）**。理由：Rust 侧无法自发合批（调用驱动在 Java future 链），且 JNI 降往返数的目标只有「多 chunk 一次跨界」才能达成。

- **粒度**：批单元 = chunk（保持 per-chunk 3×3 域全量重算语义**不变**——本臂不改引擎内核，只改传输层）。每批携带 N 组 `(chunkPos, blocks9)`，Rust 侧循环 N 次 `light_compute`，一次返回 N 组 `(out_block, out_sky, out_flags)`。
- **触发条件（合批窗口）**：利用生成管线天然的近邻提交序——同一 worldgen mailbox 工作线程在一段连续窗口内提交的 light() 请求收集成批。具体两种触发形态（实现择一，待 Phase 2 细化）：
  - (T1) **显式微批**：mixin 侧不立即 JNI，入 per-thread 待批队列；队列达 N（批宽上限）或「同 chunk 即将被依赖」（下一个 chunk 的 3×3 域需要本 chunk 结果）时 flush。风险：引入人为延迟窗口，改时机分布（见 §4 G3 声明，需谨慎）。
  - (T2) **贪心就地批（推荐）**：不改提交时机——当调用线程发现其 ThreadLocal 收集缓冲中已有 ≥2 个**相邻**（3×3 域重叠）的就绪 chunk 时合并下发；单 chunk 到来时退化为现役 1-chunk 调用。批度由提交序自然涌现，不加等待。
- **批宽上限 N**：缓冲拷贝量随 N 线性（JVM↔Rust 双向：输入 N×49132 int + 输出 N×49192 B ≈ N×0.39MB 单批）。N 上限核算（#22 免凑数）：**未实测，立项时以 per-call 拷贝耗时占 92.5ms 的占比实测后定**；静态上界受 JNI 本地引用/数组尺寸约束，**@anchor.idk**：单次 JNI 调用 JVM 侧临界区（GetArrayElements 类 pin/copy）在 HotSpot 上的实际拷贝带宽未测，N 的量级（4/8/16）留待探针。
- **缓冲区设计**：
  - Java 侧：现役 ThreadLocal blocks9 缓冲（~7MB/线程，mixin:158）扩展为 per-thread 批缓冲（N×blocks9 扁平 int[] + N×输出 byte[]，或单一大扁平数组 + 偏移表）。生命周期仍是「单次 light() 调用内」，**不跨调用持有**（避免 (i) 臂的跨调用缓冲归属问题；T1 才引入跨调用窗口，故推荐 T2）。
  - Rust 侧：新 ABI `lightComputeBatch(handle, n, offsets[], blocks9_flat[], out_flat[], out_flags_flat[], rcPerChunk[])`；tl 缓冲（LIGHT_B9 等）循环复用，逐 chunk decode→compute→写回扁平输出；`rcPerChunk[n]` 记录每 chunk 独立 rc（0/-1/-2/-3），**整批 rc 只表批级传输错**（-1/-4），chunk 级失败不污染同批其他 chunk（scout C3(iii) fallback 粒度要求）。
  - packed ABI 批化：同构扩展（meta/palette/storage 逐 chunk 拼帧 + offsets），**可后置**——先做 blocks9 批版收敛量级，packed 批版作为二期（避免一次引入两个变量）。
- **与现役 per-chunk 1 JNI 的差异（一句话）**：引擎内核、同步内联位置、时机分布全部不变；只把「N 次 JNI 往返 + N 次 JNI 拷贝」压成「1 次往返 + N 份连续拷贝」，并为每 chunk 独立报错。

### 1.3 本臂作用域边界（scout 已指出，正面承认）

本臂**只降 per-chunk 绝对成本中的 JNI 往返/拷贝分量**（~10× 绝对等待中的「每 chunk 成本差」分量之一部分），**不作用 G3 时机漂移**（§4），**不作用 L5 ×9 冗余**（3×3 域重复算结构不变——那是 (i) 臂的目标）、**不作用 L1/L2 执行位置错配**（仍同步内联于调用任务线程）、**不作用 R3 优先级缺失**。

## 3. #150 耦合面分析：与 CP-3 Mutex scratch 交互 + 批缓冲并发面

### 3.1 Mutex scratch 持锁窗口（scout C1/C3(iii) 核对）

- 现役：`scratch: Mutex<Scratch>`（mod.rs:69）在 `light_compute_inner:293` 获取，**持锁贯穿单次重算全程**（~92.5ms 量级），把所有并发 light 调用整段串行化。
- 本臂下：Rust 侧循环 N 次 `light_compute` ⇒ **Mutex 顺序获取/释放 N 次，每次持锁窗口不变**（scout C3(iii) 判定，本文核对成立）——**串行化面结构性不变**，锁不是瓶颈恶化点也不是改善点。
- 关键推论（#150 正面处理）：**批化收益不被 scratch Mutex 吃回的前提 = 锁内工作量不变**。本臂满足（每 chunk 锁内工作量与现役逐 chunk 完全相同），因此本臂**不需要**动 scratch 结构——但同批必须声明：若未来 CP-1 主案（如 (i)/(ii)）改变「scratch 全局唯一全程持锁」结构，本臂 ABI 可直接受益（锁外循环 + 批传输已就位），无耦合债务。
- **#150 同批修复判定**：scout C1 指出「解除串行化的修复与被掩盖缺陷修复 MUST 同批」。本臂**不属于解除串行化的修复**（串行化不变），故**不触发 #150 同批铁律**；但 CP-3 Mutex 已显式化该保护（260915-02 落地），#150 的盘点动作已由 CP-3 完成——本臂继承其结论即可，无新增被掩盖面。

### 3.2 批缓冲的并发面

| 缓冲 | 并发域 | 保护 | 与现役差异 |
|---|---|---|---|
| Java per-thread 批缓冲（N×blocks9 + 输出） | 单调用线程（T2） | ThreadLocal（现役同构） | 尺寸 ×N；无新共享状态 |
| Rust tl 缓冲 LIGHT_B9/OB/OS/OF | 单 JNI 调用线程 | thread_local（现役同构） | 循环复用 N 次；无新共享状态 |
| 批输出扁平数组（Java 侧） | 单调用线程 + 写回同线程 | 无需锁（同线程生产消费） | 无新并发面 |
| scratch Mutex | 跨线程 | 现役不变 | 持锁次数/窗口均不变 |

- **T1 变体额外并发面（若选显式微批）**：per-thread 待批队列引入「chunk 就绪时刻 ≠ JNI 提交时刻」窗口 ⇒ 同 chunk 可能被两个批次争用（3×3 域重叠 chunk 被相邻线程的批同时引用）⇒ 需要批间去重或提交序列化 = **新增跨线程协调面**。**这是推荐 T2 的第二理由**（第一理由：不改时机分布，不给 G3 引入新漂移源）。
- 挂起线程行为：批内任一 chunk rc=-3（panic 兜底）时，批继续跑完其余 chunk、逐 chunk 上报 rc（不整批 abort）——避免「一批一崩全链卡死」的可用性回归（崩溃铁律：rc 与 stderr 诊断行都落）。

## 4. 预期指标

### 4.1 A1 P50 作用机制与量级推演

- 传导链（scout C4 / interpretation §1.3）：A1 near P50 513-1069ms ≈ **per-chunk 成本（T_fill P50 92.5ms busy 口径）× 排队深度**。本臂作用于分子：
  - per-call 92.5ms 的构成 = fill（density 采样）+ block BFS + sky + export + **JNI 往返/双向拷贝**。fill 等**计算分量不变**；削减的只有 JNI 往返段（两次跨界切换 + 3 次数组拷贝的固定开销摊薄到 N chunk）。
  - **量级推演（Degraded，仅机制说明非判据）**：若 JNI 固定段占 per-call 的 f，批宽 N 下 per-chunk JNI 段 ≈ f/N；总 per-chunk 成本 ≈ 92.5×(1−f) + 92.5×f/N。f 未实测（**@anchor.idk**：92.5ms 内 JNI 往返/拷贝与引擎计算的占比无直接计时数据——现役无此拆分探针）。**上界**：f<1，故削减上限 = JNI 段全额，对 92.5ms 至多按比例收缩，**对 ~10× 差距最多削减一个份额，不可能单臂收敛 A1**（若 fill 主导，收益可能只有个位数百分比）。
  - 二阶效应：排队深度在 per-chunk 成本下降后**同比例缩短等待**（串行车道上等待 ≈ 深度 × 单成本），这是本臂对 A1 的主要放大道——但深度本身也被生成管线其他阶段（density 等）决定，非本臂可控。
- 立项时 MUST 先跑「JNI 段拆分计时」（单变量：现役 per-call 内粗分跨界段 vs 内核段，env 门控 chunk 级判一次，防 #136 热路径污染）确定 f，f 过小则本臂降级为「已评估·不实施」（#135 形态）。

### 4.2 G3 drift：预期不收敛（正面声明）

- G1 drift 5.83%（vanilla 基线 0.84%）的源 = **时机形态**（执行位置内联于调用任务、无 light actor、无泵节奏，scout B2 ⑥ 行 + 探针②判定 (i) 时机形态主导）。本臂**不改任何执行时机**：T2 贪心批的提交/完成时刻分布与现役逐 chunk 相同，仅每次往返更短。
- 结论：**G3 drift 预期不收敛**——立项验收若含 G3 判据，本臂**不应作为该判据的臂**。
- **「G3+A1 双收敛」定位评估（如实）**：若用户目标是双收敛，本臂**只宜作补充臂而非主案**——它对 G3 贡献≈0，对 A1 贡献有上界且依赖未实测的 f。双收敛主案形态上只能落在 (ii) vanilla 形态复刻（同时治理执行位置/泵/持久存储 ⇒ G3 时机 + A1 增量化双作用），(i) 若能合并重叠域亦部分作用 A1 + 可能波及 G3。本臂的价值 = 在主案落地前后作为**低成本、低风险的成本削减补充**（ABI 独立、不碰调度面、可与主案叠加），以及作为「JNI 段占比」的测量载体（拆分探针本身就有立项信息价值）。

## 5. 风险与验证设计

### 5.1 风险清单

| 风险 | 机制 | 缓解 |
|---|---|---|
| 批 ABI 引入传输 bug | 扁平化/offset 错位 ⇒ 输出整体移位（#151/#26 家族签名：Missing index/部分成功掩盖全流错位） | 行为等价门逐 chunk 指纹（下） |
| 批宽 N 拷贝量反噬 | N×0.39MB 单批拷贝若 JNI 带宽不足，批化反慢 | f 拆分探针先行 + N 敏感性扫描 |
| T1 时机污染（若误选） | 合批等待窗改完成时刻分布 ⇒ G3 新漂移源 | **选型锁 T2**；若评 T1 须先过 G3 A/B |
| panic 面扩大 | 批循环中一处 unwrap/越界 ⇒ -3 面 ×N | 沿用 catch_unwind + 逐 chunk rc；JNI 边界禁 panic 不变 |
| 并发面回归 | 误引入跨线程批队列（T1 形态） | T2 下零新共享状态（§3.2 表） |

### 5.2 验证设计（同构建态单变量 A/B，#150 纪律）

1. **行为等价门（先于性能）**：同 seed 同区域，现役 1-chunk 臂 vs 批臂，**逐 chunk 输出指纹全等**（[WG-CONTENT] 层 FNV-1a 位置敏感指纹，#115/#138 分档——本臂改传输不改内核，结构性应输出逐位同，等价门 = 二值强判据）。注意两层指纹分工（#14/#131）：等价门取 Rust 输出层即可证内核输入等价，Java 写回层用现有 WBCHECK 路径复跑确认。
2. **同构建态单变量 A/B**：同一 dll + 运行时 flag 切换（batch on/off），零重编；每臂**正负成对计数自证**（batch 臂 `[LightBatch] calls>0 && single calls=0`，off 臂反向——#118/#139① 自证硬门）；`executed != want` ⇒ 臂判 VOID。
3. **自证硬门**：dll 覆盖点在构建上游（target/release）+ 备份回读校验 + 每臂清解压缓存（#118）；替换生效自证进门禁，不许人工挑臂。
4. **f 拆分探针（前置）**：现役 per-call 内粗分「JNI 段 vs 内核段」，env 门控 chunk 级判一次；f 决定本臂继续/降级（#135 已评估·不实施出口）。
5. **旁证臂预演（#153）**：立项时预演「旁证失败后结论可信度」——本臂旁证（如 N 敏感性扫描）失败时，f 拆分探针仍是独立主判据载体，不形成单点依赖；1.20.1 主 worker = 专用 FJP（#153 死参数教训：并发度判据看调用方池宽，不看引擎参数）。
6. **判据预登记**：与采集脚本同批定稿，覆盖实数轴全域或显式灰区归属（#154/#150）；禁引绝对秒数作判据（#149），性能判据用相对量（批/单臂同 run 族 wall 比值 + 噪声带，交错配对防首跑预热 #103）。
7. **Degraded 边界**：本设计案全程 Degraded 静态推演；以上 1-5 全部须主会话运行时执行，任何「预期收益」在探针 f 出来前不得进入验收判据。

## 6. 诚实声明

- **Degraded**：本文为纯静态推演 + 已有 behavior 级数据引用，无任何运行时验证；所有量级（92.5ms、10×、5.83%）为 260915-03 口径引用，与本文自身验证分层无关。
- **@anchor.idk ①**：92.5ms per-call 内 JNI 往返/拷贝段与引擎计算段的占比（f）无实测数据——本臂预期收益量级**无法在 f 测得前给出数字**，只能给上界结构。
- **@anchor.idk ②**：单次 JNI 大数组传输在 HotSpot 上的实际带宽/pin 行为未测，批宽 N 上限核算缺独立来源（#22）。
- **@anchor.idk ③**：T2 贪心批在真实生成序下的**自然批度分布**（平均批宽、批命中率）未测——若生成序实际近邻度低，多数调用退化为 1-chunk，本臂退化为无操作（此为立项后第一个廉价探针）。
- **局限正面声明**：本臂不作用 G3、不作用 L5 ×9、不作用 L1/L2、不作用 R3；六维对照零维完全对齐。若 CP-1 目标 = 形态对齐 + G3 收敛，本臂只宜作补充。
