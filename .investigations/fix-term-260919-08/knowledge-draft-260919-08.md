### A7.【compiler-idioms】本块-7：Python dict 赋值评估序坑——`d[k()] = payload()` RHS 先求值，错在解析器却表现为「数据 malformed」

- **五段式**：
  - **现象**：比较器第 1 轮 `IndexError: index out of range` 于 `u1()`（log L4-25）；修复后第 2/3 轮 `[VOID] malformed 75.1323%`——r3 臂 7100/9450 chunk 全部 `truncated NBT at offset 47 need 28531 have 2911`，且**不同 chunk 同一锚点同一 need-have 数值**（log L29/L34，e.g. c(3,-32)/c(4,-32)/c(5,-32) 三例全同）。
  - **根因**：`o1_o3_cmp.py` 内手写 NBT 解码器使用 `d[r.s_()] = payload(r, tt)` 形态——Python dict 赋值语句**先求值 RHS**（`payload(r, tt)` 会推进光标 r.p）再求值 key（`r.s_()` 读长度/字符串字段）→ key 读到的是 payload 消费后的错误光标位置 → 解码器**全局错位**。签名 = 多样输入却呈「同一错位锚点 + 同一 need-have 数值」（错位是确定性的解析器状态错，非数据差异）。配对坑（同文件 `_i8` 停滞）：读长度字段时光标不推进 → 后续 payload 从错误起点读 → 段丢失截断。两者都伪装成「region 文件坏了」，实际数据 ok=9450/9450 完好（log L39-40）。
  - **定位**：第 1 轮 traceback 直接指向 u1 越界（解析器层非数据层）；「不同输入同一 need-have」签名排除数据随机损坏、锁定解析器确定性 bug；修好后 P14 双臂 gap=0.0000% / hash_mismatch=0/9450 与历史 t8_b5_r3_audit.py 0/9450 互验背书解析器正确性（verdict §1 解析层）。
  - **修复**：调整赋值语句拆分求值序（先 key 后 payload，或显式临时变量固定顺序）+ 修 `_i8` 光标推进；最终轮 A044031A 版通过（judge-review-verdict C-N2）。
  - **教训**：① Python 复合赋值 `d[k()] = f()` 的求值顺序（RHS→key）在带副作用（光标推进）的解析器上下文是活性陷阱，解析器代码禁用带副作用表达式内联进复合赋值；② 「malformed 75% 但 need-have 数值恒定」= 解析器 bug 签名，不是数据 bug——**先疑解析器再疑数据**（可复用判错经验：数据完好性用独立既有解析器互验一步定责）；③ 与 #151（漏读长度前缀）、#159（region NBT 手写解析三坑）同族：手写二进制解析器失真全部伪装成「数据坏」。
- **来源**：o1o3-r3r4-run.log L4-49（三轮原文）；judge-review-verdict C-N1 备注栏（两 bug 定名）；verdict-260919-08 §1。

### A8.【build-tooling】本块-8：手写二进制解析器交付前置——对照已互验解析器逐行对拍 + 独立口径互验兜底

- **家族**：#159 补充案例（region NBT 手写解析三坑的**交付流程**面）+#53（与已验证版对齐必要非充分）。
- **观察**：本块比较器最终版获得解析层正确性背书的路径 = ① 与历史已互验解析器（t8_b5_r3_audit.py）读数互验（hash_mismatch=0/9450 双向一致）② 独立口径 P14 兜底（解析计数 vs snap json 9450 gap=0.0000%）（verdict §1）。前三轮的两次解析器 bug（本块-7）恰是被这两道门拦下、未进判读。
- **判据**：手写 NBT/二进制解析器用于判读前 MUST：已知 chunk sanity（#159 既有）+ 与已互验解析器抽样对拍 + 至少一道**独立口径**互验（不同粒度/不同来源的计数一致性）；判据前置集把互验项写成机械门（本例 P14）。与 #53 合读：「对齐已验证版」防的是写法错，互验防的是**口径错**，两道都要。
- **来源**：verdict-260919-08.md §1；judge-review-verdict N2/N5。
