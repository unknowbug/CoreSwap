## W1【最有价值·本块】单形正则测两种实形的日志 = 假零输出（接管计数 `intercept=0` 而 `content=625`）

- **现象**：首轮冒烟 + 九臂首跑，overworld 臂 `intercept=625`，而 nether/end 臂 `intercept=0`——但同一份日志里 `[WG-CONTENT] chunk(...)` 明明有 **625** 行，**接管显然发生了**。若只看 `intercept`，会得出「nether/end 未被接管」的**完全错误**结论（而本块正要判 nether/end 覆盖）。
- **根因**：接管日志在本载体有**两种实形**——
  - overworld：`[Mixin] populateNoise intercepted chunk(-15,-13)`（**无**维度名）
  - nether/end：`[Mixin] populateNoise(nether) intercepted chunk(-15,-13)`（**带**维度名，`end` 同理）

  正则 `intercept = CountPat "populateNoise(\(.*\))? intercepted"` 与旧形 `"populateNoise\($Dim\) intercepted"` **各只能命中一种**；本块首轮两度只取单形（先取旧形 `populateNoise(<dim>)` ⇒ overworld 假零；改成无维度名形 ⇒ nether/end 假零），**在另一维度上恒 0**。
- **定位**：拿「`intercept=0` 但 `content=625`」这一**自相矛盾**组合起疑（接管计数为 0 却有条目级产物 ⇒ 两者必有一者测错）；直接 `Select-String -Pattern "intercepted"` 裸 grep 原始日志 625 命中，肉眼看到 `populateNoise(nether) intercepted` 实形 ⇒ 一轮定位。
- **修复**：正则改 `"populateNoise(\(.*\))? intercepted"`（兼收两形）；**从既有日志复算**（零重跑）⇒ 九臂一律 625。运行台 v2 已落盘该正则 + 注释说明两形。
- **教训**：
  1. **同一语义事件在不同分支上打印格式不同时，单形正则就是假零制造器**。判据计数器写完后 MUST 先做**恒等式自检**（`intercept == content` 这类本应成立的等式）；等式破了先查测量侧，别急着下机制结论。
  2. 「A 计数 = 0 而 B 计数 = 625 且 B 蕴含 A」= **测量侧矛盾签名**，与 workflow-patterns **#13 家族**（探针零输出先查过滤/驱动条件、grep 证明性零结果先核自身转录）同族。
  3. 本块代价为零（**在既有日志上复算**）——保留原始日志不删的价值实证；若首跑即删日志，本项须重跑 9 臂。

## W2 异常面计数未排除环境良性噪声 ⇒ `exceptions=3` 伪装成「有异常」

- **现象**：每臂 `exceptions=3`，看着像「有 3 个异常」。
- **根因**：正则 `Exception|Error:` 命中 3 行 `WmiQueryHandler` 的 COM 警告——`COM exception querying Win32_Processor/Win32_PhysicalMemory` 是**沙箱环境**固有的良性噪声（与 CoreSwap 无关），但**计数层面与真实异常无法区分**。
- **定位**：逐行打印命中内容（只打计数就会误读），肉眼识别 3 行全为 WMI/COM。
- **修复**：新增 `nonWmi` 计数（排除含 `WmiQueryHandler|Win32_Processor|Win32_PhysicalMemory` 的行）；异常面判据以 `nonWmi` 为准 ⇒ 11 臂全 0。
- **教训**：**计数器的分母/排除集必须显式定义**——「异常数」这种宽口径正则计数 MUST 附「良性噪声排除清单」，否则环境噪声会持续伪装成信号（#139 ② 计数载体家族的**噪声面**）。

## W3【方法学·跨块】把上一块的缺陷机制默认继承到本块载体（范围未核）

- **现象**：进入本块时，交接与经验都指向「**无冒号 `runServer` 会双命中** `:runServer` + `:content-test:runServer`」（260912-02 C-17 的机制）。若直接照此判断，会认为 1.21.6 也有「两次 JVM 写同一日志」的计数载体缺陷。
- **根因**：该机制**依赖子工程存在且应用了 fabric-loom**。1.21.6 的 `versions\1.21.6\java\content-test\` **目录根本不存在**（`Test-Path` = False；`git ls-files` = 0 条），但 `settings.gradle:13` 的 `include 'content-test'` 仍让 Gradle **自动建一个空子工程**（无 loom）⇒ 该子工程**无 `runServer` 任务** ⇒ **1.21.6 根本不触发双命中**。旧机制被当成「普遍规律」而**未按载体核实**。
- **定位**：**先做廉价独立验证**（AGENTS.md「交接结论验证纪律」+ #139 ② 要求的 `gradle --dry-run` 任务图直证）：跑两版 `--dry-run runServer` 与 `--dry-run :runServer` 对照 ⇒ 1.20.1 裸跑列出**两个** `runServer` 任务、1.21.6 裸跑只列出**一个**；再用 `gradle :content-test:tasks --all | grep runServer` = **零命中** 定因。
- **修复**：无需修复代码；**登记不对称性**（verify §4.1 + 命令表 §1），运行台仍显式用 `:runServer`（防御性，防将来补 content-test 后退化）。
- **教训**：
  1. **「上一块的根因机制」不是普遍规律，是带前提的机制**——跨块承接前 MUST 核对**前提条件在本块载体上是否成立**（此处前提 = 子工程有 loom 的 `runServer`）。同 260912-02 W7 的「同一判据的旧诊断必须继承」互补：**继承机制的同时必须重核其前提**。
  2. **反方向错误同样致命**：把 1.20.1 的缺陷误记到 1.21.6 头上，会给后续所有 1.21.6 计数下「载体不可信」的错误前提（比漏记更贵）。
  3. 任务图直证（`--dry-run`）是**零机时**的判别手段——此类「机制是否在本载体成立」的问题，一律优先用它而非推理。

> ⚠️ **§15.4 取代指针（2026-09-13，本块 W5）**：本条 W3 的**结论不变**（1.21.6 无双命中，已由任务图双向直证），但其**根因表述**中的「目录为空」有误 —— 真实是「**目录不存在**，`settings.gradle:13 include` 让 Gradle 自动建空子工程」。**W3 原文保留不改**，取代记录与完整教训见本台账 **W5**。

## W4 冒烟臂口径未声明就参与观察（观察纪律）

- **现象**：先跑了一个 `smoke-ow` 臂验证运行台，其日志与正式 9 臂混在同一目录、同一命名族（`1216-*.log`）。
- **根因**：冒烟轮的目的是「验证测量装置」，不是产出判据数据；但它**天然会进 MANIFEST 与目录枚举**，若不当场声明口径，下游（含 judge）可能把它当第 10 个正式臂参与对比。
- **定位**：自查「哪些臂进了判据对比」时发现冒烟臂在盘且命名同族。
- **修复**：命令表 §5 显式声明「冒烟臂`smoke-ow` **不进入**正式九臂台账」；比对器只读 9 个正式 tag 的文件名，**不按 glob 全收**（这是防护点）。
- **教训**：**冒烟轮 MUST 带口径隔离声明**（命名或目录区分，最差也要在命令表里写明不入账）；比对器**按显式清单取名，禁止 glob 通配**——否则一次性验证臂会静默混入判据。

## W5【最有价值·judge 独立抓出】「结论对而解释错」——靠任务图得出正确结论，却事后用未经核实的目录措辞去解释

- **现象**：本块 W3 的机制解释（写在 verify §4.1、命令表 §1、本台账 W3 共 **三处**）称「1.21.6 的 `content-test` 目录**为空**（无 `build.gradle`）」。judge 独立核对后指出：**该目录根本不存在**（`Test-Path` = False；`git ls-files` = 0 条）。
- **根因**：真实机制是 **`include` 与目录存在性解耦** —— `settings.gradle:13` 的 `include 'content-test'` 令 Gradle **自动创建一个空子工程**（`gradle :content-test:tasks` → BUILD SUCCESSFUL，能列出 help 任务），即使该目录在磁盘上不存在、也从未被 git 跟踪。故「子工程存在但无 `runServer`」**不蕴含「目录存在但为空」**——我把「子工程」与「目录」当成了同一件事，用**未核实的中间实体**去解释一个已由**正确手段**得到的结论。
- **定位**：judge 用 `Test-Path` + `git ls-files` 两条独立证据复核目录存在性（**不是**复核结论本身，而是复核**结论的叙述层**）。
- **修复**：三处措辞改为「目录不存在 + `settings.gradle` 自动建空子工程」；本台账按 §15.4 记录（**W3 原文保留不改**，以本 W5 为取代指针）；verify §4.1 加取代注记。
- **教训**：
  1. **「结论正确」不豁免「解释错误」**——本块结论（1.21.6 无双命中）由 `gradle --dry-run` **任务图双向直证**，方法本身是对的；但事后叙述引入了「目录为空」这个**没有核实过的事实**。**判据的证明手段正确 ≠ 叙述里的事实都正确**，叙述层 MUST 同样过一手核对（workflow-patterns #95「scout 结论的事实前提与结论分开验证」的同族，且此处更严：**结论对、前提错也要修**）。
  2. **判别「某任务是否存在」的唯一可靠依据 = 任务图，不是文件系统**（`include` / 插件 / 约定都可能凭空造出任务或子工程）。用目录/文件存在性去推断构建图 = **用错误层级的证据解释正确层级的结论**。
  3. **同一错误措辞在三处重复 = 转录扩散**（#90 家族）：一处写错后被复制进 verify / 命令表 / 台账。**修正必须全量 grep 三处**，只改一处会留下「同一文档族内自相矛盾」。
  4. judge 的价值本项实证：**judge 复核的不只是数字，还有「解释数字时顺带断言的事实」**——本项若漏过，错误的机制解释会随 confirmed 一起进知识库，成为下游的第二个错误前提。

1. **「两个本应相等的计数不等」= 测量侧矛盾签名**，先查测量，别下机制结论（W1）。
2. **跨块继承机制 MUST 同时重核前提**；反向误记（把 A 载体的缺陷记到 B 载体）比漏记更贵（W3）。
3. **计数器的排除集必须显式定义**，否则环境噪声长期伪装信号（W2）。
4. **【最高价值】结论正确不豁免解释正确**——证明手段层级正确 ≠ 叙述里的事实都经过核实；判别构建图类问题 MUST 用**任务图**而非文件系统，且同一措辞多处复用时修正要全量覆盖（W5）。
