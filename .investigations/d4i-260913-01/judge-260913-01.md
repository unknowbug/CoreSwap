### MUST-1【事实错误·三处重复·须更正后方可 confirmed】`content-test` 目录状态叙述错误

  - `versions/1.21.6/java` 目录列表：**无 content-test 项**（1.20.1 有）

## 3. 独立新发现（本项价值最高）

### 发现 A【承重】：`settings.gradle` 的 `include` 与目录存在性解耦 —— 1.21.6 的 `:content-test` 是「空 Gradle 子工程」而非「空目录」

这是**推翻 verify §4.1 机制叙述**的直接证据，且给出更准确的前提模型：

```
1.21.6: settings.gradle:13 include 'content-test'  → 目录不存在，Gradle 自动建空子工程
        gradle :content-test:tasks        → BUILD SUCCESSFUL（子工程存在）
        gradle :content-test:tasks --all | grep runServer → 0 命中
        gradle --dry-run runServer        → 仅 :runServer（无双命中）✅
1.20.1: content-test/ 目录存在（3 文件，含 build.gradle + fabric-loom）
        gradle --dry-run runServer        → :runServer + :content-test:runServer（双命中）⚠
```

**方法论价值**：判别此类问题**不能看目录**，必须看**任务图**（`--dry-run` / `tasks --all`）。verify 的结论恰是靠任务图得出的（方法对），但**事后用目录状态去解释机制**（方法错）——这正是 `workflow-patterns #112`（事后补解释）与 W3 自身教训「机制的前提条件」的**双重复发**。

### 发现 B【补强 C-1】：625 不是「行数相等」，而是**完整无缺格网格**

我独立解析 18 个 fp 文件的 chunk key：**625 unique / 0 重复 / 25×25 完整网格 / 0 缺失格**（`x=[-15,9] z=[-13,11]`）。这排除了「以缺失换取相等」的伪等价形态——**比 verify 的多重集判据更强的一层**，且是 verify 未主张的。建议并入结论。

### 发现 C【交叉校验】：`sections_replaced + air_sections_skipped = calls × 24`

bulk 臂读数 `calls=625 / sections_replaced=5000 / air_sections_skipped=10000` ⇒ `5000 + 10000 = 15000 = 625 × 24`（1.21.6 世界高 384 ⇒ 24 section/chunk）。**与 content 行数 625 独立自洽**（此算术在 260912-02 judge §A9 已用于 1.20.1 的 `607×24=14568`）。本块 verify 未用，可作 `calls` 语义的**第三条独立交叉校验**。

### 发现 D【正面】：跨块基线同一为**逐字节级**

`ow-default` 合并 fp 与 260912-02 冻结件不仅 sha 前 16 位相同，**全 64 位相同**（`8184d609847c704e461d1a52e2c6fa8434db7de622dbec3ba98f662094f9878a`）且**文件尺寸同（86248 B）**。260912-02 judge §C-5 曾以「整文件全 64 位 sha 同一」作为最强形态；本块**再次独立复现该同一性** ⇒ 跨块可比性主张（§9.7「可直接比」）**被实证**，非仅声明。
