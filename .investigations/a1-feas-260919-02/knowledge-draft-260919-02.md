## 1. 课题错误台账（260919-02，五段式）

### E1：打点字段误标——kernel_us 打印的是 outv 分配段（dp-t1）而非内核墙钟

- **现象**：第一版打点构建（dll sha8 **60abb61b**）采集的四臂数据中，`kernel_us` 读数 ~86μs 量级（即 dp-t1 计时值，实为 outv 分配段），而同 kernel 窗内各 phase（fill/blockbfs/skyfall/skyseed/export）合计已达 **~23ms**——`kernel_us ≪ Σphases`，子段之和远大于母段窗，物理不自洽。
- **根因（机制）**：打点插桩时**窗标签与计时代码实际括住的工作不一致**——`kernel_us` 标签挂在名义上的「内核墙钟」位，实际计时变量取的是 dp-t1（outv 分配段的计时点）；标签是文档语义、变量是代码事实，两者脱钩，属测量口径层错误而非内核行为异常。
- **定位（怎么发现）**：**数据自暴露**——自洽性 sanity（子段合计 vs 母段窗）一眼见矛盾：86μs 的 kernel 装不下 23ms 的 phases。判据前置集在采集前即载明「修正后重编为 f1d30ee9，60abb61b 数据不进判定」，第一版四臂数据按 #144/#146 纪律**留档不删、不进判定**（cmd-output/P1-\* 系列留作缺陷对照）。
- **修复**：修正计时窗（kernel 窗真正括住内核墙钟）→ 重编 dll（60abb61b → **f1d30ee9**）→ R2 四臂重采；判据 §前提集同步登记构建替换与读法（verdict §1 读法附注：判据 §3.2 陈旧字面 60abb61b 按前提集修正版 f1d30ee9 读，判据冻结不改）。
- **教训**：**分段打点的窗标签必须与计时代码实际括住的工作一致，正式采集前先做自洽性 sanity（子段合计 ≤ 母段窗、各段之和 ≈ 任务总量）**。本例由「子段 > 母段」物理不自洁暴露，一轮抓出，未污染任何判定——sanity 检查的成本远低于带着错口径走完整个判定链的返工。→ discovered 条目草稿 **#189**（测量口径家族，#134 同族）。

### E2：stderr 并发交错产生残缺 [LIGHTPHASE] 行 → 提取脚本 KeyError 崩溃

- **现象**：R2-on2 臂日志中 19/457 行 `[LIGHTPHASE]` 残缺（缺 key），提取脚本按全 key 校验直接 KeyError 崩溃；R2-on1/on3 亦有 5/8 行（1.09%/1.75%）。现场样本：R2-on1 log:6991/9354/10193/10235——FP-FILL/FP-LIGHT 行切入 `[LIGHTPHASE]` 行中间。
- **根因（机制）**：诊断通道输出走 stderr，并发下多线程写 stderr 无行原子性保证，其他诊断行（FP-FILL/FP-LIGHT）插入 `[LIGHTPHASE]` 行字节流中间，产生**结构性残缺行**——解析器假设「每行要么完整要么不存在」，该假设在并发 stderr 下不成立。
- **定位（怎么发现）**：提取脚本 KeyError 崩溃暴露；回查原日志行号找到残缺行的物理形态（交错切入样本），确认非数据缺失而是输出通道层问题。
- **修复**：**判据追补残缺行条款（§3.7）**——解析器按全 key 校验 + 残缺率门双档：**≤5% 如实报告继续判定 / >5% 整臂 VOID**。时序锚实证：追补条款 commit 080d6e7 @14:49 **早于全部 R2 log 首时间戳（15:05:03–15:22:26）**，条款先于数据被消费（#112 同批纪律）。实测 on2 = 4.16% 贴线通过，登记 **idk-4**（复跑上行 >5% 即 VOID，on1/on3 双臂支撑方向不翻转）。
- **教训**：**并发 stderr 诊断行必须容忍交错残缺：解析器按全 key 校验 + 残缺率门（报告/VOID 双档），判据预登记时一并写入**。裸 KeyError 崩溃既浪费整臂采集也不给出「还能不能信」的判据；残缺率门把「输出通道质量」变成判定面的一部分且阈值预登记，防事后挑臂。→ discovered 条目草稿 **#190**。
