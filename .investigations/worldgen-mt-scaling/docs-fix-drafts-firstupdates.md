## 2026-08-16：多线程并发下慢 7.5× 结案——探针污染定论（MT8）

> 承接同日期「线程池 notify 丢失修复」条目（0a781e1）；本条目**正式结案「worldgen 多线程每 chunk 并发下慢 7.5× / density 11×」课题 = 不存在**，是 WG_* 计时探针在并发下污染测量的幻影（MT8）。完整五段式错误记录：`.investigations/worldgen-mt-scaling/mt-scaling-errors.md` MT8 段；修正链：`density-latency-rootcause.md`；勘探（C1-C10）：`scout-map.md`；per-chunk trace：`per-chunk-concurrent-slow-mtrace.md`；GPU 复核：`gpu-op-verify.md`。

### ✅ 结案结论：并发下慢 7.5× 不存在，真实并发正常

- **可靠基准 = 干净 bench 整 chunk wall**（无任何探针 env、独立进程、`wg_fill_blocks_multi` 直接测）：

| T | 整 chunk wall（ms/chunk） | 相对 |
|---|---|---|
| T=1 | 64.23 | 基线 |
| T=8 | 69.57 | **+8%（正常，density-latency-rootcause 记同场景 +8~12%）** |
| T=0(24t) | 80.7 | over-subscription 正常劣化 |

- **WG_CLOCKTRACE 归一化后 GHz 恒 2.99**（无睿频降频）——排除「全核降频」解释（scout-map L99）。
- **结论**：T=8 比 T=1 慢 8~12% = 正常多线程调度/缓存开销，**不是「7.5× 灾难」**；notify 丢失 bug（真 bug）修复后，多线程能正常伸缩（T=8 快 8-12%）。之前「每 chunk 并发下慢 7.5× / density 11×」**全是探针污染幻影**。

### ⚠️ 探针污染链（3 个探针各自污染机制）

1. **WG_PROFILE density（T=1 34ms / T=8 400ms = 11×）**：每采样点 `steady_clock` 计时 + 原子 `fetch_add`（98,304 点/chunk）→ 8 线程并发下**原子总线/缓存行 RMW 竞争 + steady_clock 系统调用** → 探针自身成热点，计时失真（并发下放大非真实）。「density 11×」即此来源。
2. **WG_MTTRACE dur（470ms）**：每 chunk `fprintf(stderr)` → 8 线程同时写 stderr **锁竞争**（同步打印串行化）→ dur 被拉大。WG_MTTRACE 曾解释「批间 525ms ≈ 8×65ms」，同样是打印串行 + 锁竞争，**需无 fprintf 计数器复测才可信**（现已定性为污染）。
3. **WG_DENSITYTICK（QPC/墙钟，T=1 33-44ms 可信 / T=8 370ms）**：QPC 墙钟差分读「线程从循环开始到真正执行完」的间隔，被**调度切换/等待**拉大 → 370ms **超过整 chunk wall 69ms（测量崩坏铁证）**；+ 重复循环 bug（曾把 density 循环算两次 → 5ms/370ms/33ms 反复）。

- **矛盾自检铁证**：探针测的阶段（370ms）**> 整 chunk wall（69ms）** = 测量崩坏，弃用该探针。
- **单线程可信 / 多线程不可信**：阶段计时探针（steady_clock/QPC/fprintf）在单线程读的是真实计算（T=1 34ms 与 WG_PROFILE 吻合 → T=1 基准可信），在**多线程读到的是「本线程执行 + 调度等待/竞争」，非真实计算**。

### ↩️ 作废清单（建立在探针污染数据上）

- **「每 chunk 并发下慢 7.5× / density 11×」**：不存在，是探针污染幻影（见 ⚠️ 链）。
- **C1-C10 候选排查链**（scout-map.md）：整个「并发下慢」候选调查（C1 堆分配 / C2 睿频+SMT / C3 LLC 容量 / C4 调度亲和 / C5 原子读 / C6 共享表 / C7 带宽 / C8 锁 / C9 阶段串行 / C10 诊断开销）建立在「并发下慢」前提下，**该前提作废**。
  - **⚠️ 保留边界（错误优先原则）**：C1/C2/C3/C7 **负面排除结果**（A/B 实测：堆分配非主因、T=8 无 SMT 惩罚、8T 活动集 10.4MB < LLC 16.5MB 不贴边界、带宽仅 1-2%）方法论上成立——**排除链本身是资产**（缩小了 notify 定位空间，见 MT1 教训）；作废的是「这些候选解释了并发下慢」的**框架**，非排除结果本身。
- **C3（LLC 容量）误判修正**：scout-map 早期把 C3 列为与 C1 同源的高疑候选 → 实测排除（8T 活动集 10.4MB < 16.5MB 最低 LLC，曲线平滑无容量拐点），仅 T=22 贴边可能贡献（28.6MB）——修正本身记录了排除，但「**C3 解释并发慢**」的定位作废。
- **WG_PROFILE「density 11×」**：探针污染（原子竞争），非真实 density 变慢——作废。

### ✅ 保留结论（真实，独立于探针污染）

- **notify 丢失 bug（真 bug，0a781e1 已修）**：「反降假象」来源（[A] T>1 顺序跑下补建 worker 错过 notify → 串行）；修复后多线程正常（T=8 +8%）。
- **线程池正确性**：修复后池能正常伸缩（T=8 快 8-12%）；T=8 单独跑完美并行（池本身正确，bug 只在扩容路径暴露）。
- **Threads clamp（MT3，独立问题）**：`wg_fill_blocks_multi` L1189 `threads > count` clamp（66e05f5 引入，池化 c792e9d 后语义失效）→ count=1 结构性串行，实机 M=1「多线程从未真正并行」——与 notify bug 独立（只影响 [B]/实机），待实机实跑对比（candidate）。

### 教训（本项目最重要，第 6 个探针污染案例）

1. **测量工具的选择 > 算法分析**：整个课题（多线程反降 → C1-C10 → density 11× → C3 误判修正）**被一个探针污染误导**——本项目所有 WG_* 计时探针在**并发下都会污染测量**（原子竞争 / fprintf 锁 / QPC 调度），**并行性能只能信「无探针整批 wall + 调用次数计数（非计时）」**，不能用任何阶段计时探针测并发。
2. **「探针测的阶段 > 整 chunk wall」= 测量崩坏铁证**（本案例 370ms > 69ms）——用此自检立即弃用探针。
3. **先测「整 chunk wall」再下「阶段慢」结论**：若探针报「某阶段 11×」但整 chunk wall 只差 8% → 探针污染，阶段结论作废。
4. **性能探针自身会污染测量**：「慢 10 倍」先做探针开/关对比标定（探针开关差 = 探针开销），再查代码；计时与计数必须分离。
