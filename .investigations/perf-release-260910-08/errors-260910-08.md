# 错误台账 — perf-release-260910-08（1.0.28 性能基准 / 引擎因子复核）

> 实际时刻：2026-09-10 23:45 – 2026-09-11 01:30（本地）。块标签沿用起始日 `260910-08`。
> 记录原则（AGENTS §三.2 错误优先）：**现象 → 根因 → 定位 → 修复 → 教训**，只记「已修复」不算记录。

## E1（最高价值）引擎 A/B 空跑：覆盖点错在构建上游 + 自证行未做门禁

- **现象**：`.tmp/engine-ab-260910-08/` 两臂（`engNew` / `engOld1027`）wall 与 CPU 秒数几乎相同。逐日志核对 `[CppBridge] dll=` 自证行：

  | 臂 | 脚本 `want`（sha16） | 实际执行 `executed`（sha16） |
  |---|---|---|
  | engOld1027（23:53） | `7a411e01…`（1.0.27 引擎） | **`597e12ed…`**（1.0.28 引擎） |
  | engNew（23:55） | `597e12ed…` | `597e12ed…` |

  后续 `.tmp/perf-factorial-260910-08/` 的 4 个「引擎臂」同病（`eng24-*` 的 executed 全是 `597e12ed`）。

- **根因**（两层）：
  1. **覆盖点错**：`versions/1.20.1/java/build.gradle:36-50` 的 `processResources.doFirst` **无条件**把 `E:/PYTHON/CoreSwap/target/release/worldgen.dll` 拷进 `src/main/resources/native/worldgen.dll`。我把待测 dll 拷进 `src/main/resources/native` + `build/resources/main/native` 的动作，在 `:runServer` 触发 `processResources` 时被撤销 ⇒ **唯一有效覆盖点 = `target/release/`**（构建上游），不是资源目录。
  2. **门禁缺失**：脚本**打印**了 `executed vs want`，但**没有判定**——空跑静默通过，并被当成有效实验去支撑结论。
- **定位方法**：`Select-String -Path logs\*.log -Pattern '\[CppBridge\] dll='` 一次比对全部臂即暴露（7 个日志同值）。
- **修复**：新脚本 `.tmp/engine-ab2-260910-08/run_engine_ab2.ps1`：
  ① 覆盖 `target/release/worldgen.dll`（先备份，臂尾还原并**回读 sha 校验**）；
  ② 每臂删除 `<tmp>/coreswap-native` dezip 缓存（#96/E9 家族防护）；
  ③ **`executed sha != want sha` ⇒ 该臂判 VOID、写 results.txt、硬返回**（不再静默）。
- **教训**：
  - **替换执行体的实验，自证行必须做成硬门禁**（mismatch ⇒ 该臂无效）。只打印不判定 = 没有门禁，等于把"跑了个啥"交给运气。
  - **替换点必须在所有会覆盖它的构建步之上**：先查 `build.gradle` 谁在写这个文件，再决定往哪儿放，别往最终产物里塞。
  - 这对 #23（rlib/dll 陈旧假绿）与 E9（解压缓存复用）是**同一家族**：判据 = 内容指纹 + 硬门禁，mtime/文件名不作数。

## E2 无效结论外泄（已发生，必须停止引用）

- **现象**：260910-08 会话中出现过结论「引擎 A/B：`engNew` × `engOld1027` 差异 0.0298% ≈ 噪声 ⇒ 引擎等价」。
- **根因**：见 E1——两臂执行的是**同一个** dll，那次比较对"引擎差"零判别力；0.0298% 只是该载体的 run 级噪声。
- **定位**：知识库 `workflow-patterns.md` #115 已把 `0.0298/0.0301%` 记为**跨形态 run 级噪声锚**——即该数字的正确身份一直是噪声，不是引擎差。
- **修复**：以修正后的 A/B 取代（见 `MANIFEST.md` §3；1.0.27 vs 1.0.28：async 36s/36s、sync 203s/205s，两形态均无差）。
- **教训**：**"差异 ≤ 噪声"这类结论必须同时给出①噪声锚的来源与②两臂执行体 sha 对照**，否则无法与"空跑"区分。

## E3（载体边界，非错误）1.0.24 dll 与 1.0.28 前端 ABI 不兼容

- **现象**：`eng1024-sync` / `eng1024-async` 两臂 `[CppBridge] dll= …561aff49…` 通过、`Done (14.550s)` 也出现，但随后 initNether 阶段 `Task :runServer FAILED`，RCON 全程 ConnectionRefused。
- **根因**：dll 换法要求 JNI 导出面一致；1.0.24 → 1.0.28 之间 Java↔native 的接口已变（1.0.28 前端会调用 1.0.24 dll 里不存在/签名不同的符号）。
- **修复/处置**：判为**本载体不可测**（`@anchor.idk`），不产出 1.0.24 引擎臂数字；要测须用真 1.0.24 jar 的独立环境（独立 Fabric 服务端 + 该版 jar），不可用 dev 工程（mod id 冲突）。
- **教训**：**dll 换法只适用于 JNI 面未变的相邻版本**（1.0.27↔1.0.28 ✓ 已验证）；跨大版本必须整包换。

## E4 内存指标误读（自查拦截，未外泄）

- **现象**：单对测量得 1.0.28 `maxWs≈5973MB` vs 1.0.27 `2713MB`，看似"1.0.28 多占 3.3GB"。
- **反证**：交替复跑（1028/1027/1027/1028）：`6505 / 4666 / 2984 / 5976 MB`——**同一 dll 同配置两次跑出 2984 vs 4666（1.7× 摆动）**。且 `build.gradle` 未设 `-Xmx`（JVM 默认 MaxHeap = 12.7GB，本机 ~48GB RAM）。
- **根因**：JVM `WorkingSet`/`PrivateMemory` **峰值 ≠ 存活集**；无 `-Xmx` 时它是 G1 堆高水位，由分配节奏与 GC 时机决定，同配置摆动可达 1.7×。
- **修复/判定**：改固定堆判定——`-Xmx2G` 臂：1.0.28 = **36 s / 469 cpuSec / 峰值 3043MB**，1.0.27 = **35 s / 469 cpuSec / 峰值 2223MB** ⇒ **两引擎在玩家常用堆档下均满速跑完，无阻塞性内存回归**；两臂峰值差仍在已证摆动带内（n=1/臂），**不作等价结论**（只作"无阻塞证据"）。见 `MANIFEST.md` §5。
- **教训**：**内存回归判定必须固定堆或读 GC 日志的 live-set，并先测同配置摆动带**；拿单对峰值差说事 = 用高水位冒充存活集。

## E5 口径不可比（§9.7）：bench 的 flags 与出货默认不同源

- **现象**：1.21.6 侧「ca_min 内存优化」的量化收益（`289.1 → 177.9 ms/chunk`，-72%）被当作该项优化的通用收益。
- **根因**：该数字由 `worldgen-core/src/bin-diag/camin_bench.rs` 产出，而该 bench **从不调用 `wg_set_flags`**（handle `flags` 初值 0，`worldgen_handle.rs:503`）⇒ `skip_features=false` ⇒ **features 全跑**；出货配置默认 `mask=3` ⇒ features 关。两者不是同一条执行路径。
- **定位**：subagent 只读代码审查（read/grep）+ 上述行号。
- **修复**：引用时同行声明三要素（载体=bin-diag bench / 覆盖面=features 全跑 / 与出货口径不可比）。
- **教训**：**"优化收益"这类数字必须与出货默认门控同源核对**——bench 里"默认值"往往不是产品的默认值；`flags 初值 0` 是隐蔽的默认翻转点。

## E6 公众文档与出厂行为漂移

- **现象**：`README.md:27` / `README.zh-CN.md:28` 声称主世界「density → aquifer → ore veins → surface rules → carvers → features」全原生。
- **根因**：出厂默认 `mask=3`（`CppBridge.resolveStageMask()` 默认 `0b011`）在 `worldgen_handle.rs:669-670` 切断 `apply_features`、:832 切断 carvers ⇒ **carvers/features 实际由 Java vanilla 执行**。该声明在 260909-03 用户决策（矿物/树/装饰层不接管、保 MOD 兼容）后即过时。
- **修复**：README 双语改措辞（"carvers and features stay vanilla Java for mod compatibility"）+ "How It Works" 段补出厂生效范围。
- **教训**：**面向公众的能力声明必须与"出货默认门控"同源核对**，不能按"引擎里有实现"来写；门控默认值（mask/ca_min/env）是声明的一部分。
