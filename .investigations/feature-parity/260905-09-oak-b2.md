### 2.3 可产生「oak 有 birch 无」的差异点清单（b2 子机制）

- **(b) Y 切片并集近似（最实质）**：Java 并集覆盖全高 py=0..79 每层 quad；Rust 只采 wy∈{0,64,128} → py∈{0,16,32}。**树冠带 py≈17-21（y 68-87）完全无采样点**，地表 biome 只经 py=16（y 64-67）一格代表。depth 随 y 连续变化，birch_forest/forest 的参数行 depth=[0,0]（`versions/1.20.1/data/biome_params.json:406` 等）在 py=16 与 py=18 处可跨最近邻边界 → 并集集合系统性差一格 biome。方向性：在此区域恰好表现为 rust 并集缺 forest 系（→ birch 缺）或反向 —— **未证，需探针**。
- **(a) MultiNoise 定点平局翻转**：`biome_of` 已是 1e-4 long 域（#18 修复后），残余翻转应为散点级，无法解释 28 chunk 单向 oak 超量。**作为主因权重低**。
- **(c) biome→feature 映射/order**：静态核对无缺陷——features_for 直接读 biome json（birch_forest.json/forest.json 数据在 `versions/1.20.1/data/worldgen/data/`，来源 jar-check 副本）；forest.json 植被 = `minecraft:trees_birch_and_oak`（:81 一手核验）；biome_registry_order.json 含 birch_forest(:30)/old_growth_birch_forest(:45)。`biome_allows`（Rust :941-944，any step any fid）与 Java `isFeatureAllowed`（PlacedFeature 身份集合，GenerationSettings.java:88）语义等价（placed feature 字符串 id 一一对应）。**order 差已被 260905-08 registry_order 修复覆盖**。未见静态可证差异。

### 2.4 关键旁证（削弱 b2 为 oak 超量主因）

- **树型分配不取决于 biome**：`configured_feature/trees_birch_and_oak.json`（一手核验）= random_selector{0.2 birch, 0.1 fancy_oak, default oak}——birch vs oak 是 **feature 执行内部 RNG 分支**，不是 biome 决定。Rust random_selector 已按 RandomFeatureConfiguration.java 对齐实现（`tree.rs:750-775` + `feature_loader.rs:393-413`，260905-06 idk-7）。若同 feature 同 RNG 流执行，birch ≈0 概率极低（45 棵全 oak）→ (37,-16) birch 全零要么是 rust 侧该 chunk 根本没跑 trees_birch_and_oak（=b2 并集/分类差），要么 selector 分支有 bug（=b1 域）。
- **leaf/log 失衡签名排除「树归属差」为 oak 超量主体**：b2 各子机制（并集集合差 → 换 feature 执行；biome 门差 → 整树放行/砍除）作用的都是**树粒度**（含 trunk），预期 oak_log 与 oak_leaves 同向同量级变化。v18 实测区域 oak_leaves +29,830 vs oak_log 仅 +197（比值 ~151:1，远超单树叶/log 比 ~1.5:1）→ **oak 超量主体是树冠内部叶块差（b1 域），不是树数量/树型归属差**。v19 佐证：extra 叶 905 中 858 个下方是未知/空气块（悬空叶冠），van-only/rust-only log 位置完全错位且 rust-only 45 > van-only 22 但区域 log 只 +197。
- **chunk (29,-16) 反例**：该 chunk k=6/k=9 p 序列与 Java 逐位一致（260905-08 交接）且 oak 仍 +671——若 b2 并集集合差普遍存在，p 序列（直接依赖并集 biome 集合）应先分叉。说明至少在中部 chunk 两侧并集等价。

## 3. 自洽性评估（任务 2）

b2 能否解释 v18「28 chunk 单向 oak 超量 + jungle/vine 反向收敛」？

- **不能自洽地解释 oak 超量主体**。理由链：① biome 差异机制全是树粒度（feature 换绑/整树门），无法产生 151:1 的 leaf/log 失衡；② (29,-16) p 序列一致但 oak +671，排除该 chunk 并集层分叉；③ 若 rust 广泛缺 forest（birch 缺的并集解释），rust 的 oak 只能来自更低密度的非 forest biome（如 trees_plains），无法产出 45 棵/chunk 的树量。
- **部分自洽地解释 birch 全零签名**：(37,-16) 若 rust 并集缺 forest 系 biome（Y 切片近似最可能），trees_birch_and_oak 不执行 → birch 0 ✓；其 oak 由并集内其它 biome 的树 feature（如 windswept_hills 的 trees_windswept_hills=fancy_oak 系）产出，位置整体错位（不同 feature 不同 RNG 消费）✓。**此路径与 v19 空间签名兼容，但是否成立取决于该 chunk 实际 biome 集合——正需 §6 探针。**
- **jungle/vine 反向（java 多 rust 少）与 b2 无冲突但非必要**：jungle 特征属不同 biome 并集成员，c-A（block_at 越界）已是已交付修复的独立候选；b2 不提供额外解释力。

**结论：b2 作为 oak +29,830 主机制 = 倾向 refuted（签名级，Degraded 静态推理）；b2 作为 (37,-16) birch 全零与局部 biome 集合差贡献 = plausible（待 §6 决定性探针裁决）。建议主会话把 b1（树冠叶块内部差：leaf distance 属性 / no-log canopy / 若干 selector 分支）列为 oak 主战场。**
