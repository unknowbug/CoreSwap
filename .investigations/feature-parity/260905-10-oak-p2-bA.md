## 一、逐行对拍（四项指定点）

### ① getHeight 与 2 次 nextInt 消费
- Java `mcsrc\net\minecraft\world\gen\trunk\TrunkPlacer.java:54-56`：
  `baseHeight + random.nextInt(firstRandomHeight + 1) + random.nextInt(secondRandomHeight + 1)` —— 恒 2 次消费，顺序 a 后 b。
- Rust `worldgen-core\src\tree.rs:99-108`：
  `base_height + random.next_int_bound(rand_a + 1) + random.next_int_bound(rand_b + 1)` —— 同公式、同 2 次消费、同顺序。
- **判定：源级一致。**（`next_int_bound ≡ nextInt` 的等价性已被 placement 阶段 [CNT]/[SQ] 对齐间接支持，但 bound 语义本身未独立验证——见 §四 探针兜底。）

### ② getTopPosition 推导 + min_clipped_height 验收
- Java `mcsrc\net\minecraft\world\gen\feature\TreeFeature.java:92-109`：`for i in 0..=height+1`，按 `minimumSize.getRadius(height, i)` 方形扫描，遇不可替换/藤蔓 → `return i-2`；全通过 → `return height`。**0 随机消费，返回值 ≤ height。**
- 验收 `TreeFeature.java:74-76`：`o >= i || (!minClipped.isEmpty() && o >= minClipped)`。
- Rust `tree.rs:610-623`（get_top_position）与 `tree.rs:512-515`（验收）：逐行同构（0..=(height+1)、`iy-2`、`height`、`o>=i || clipped`）。
- oak 的 minimum_size = two_layers_feature_size（默认 limit=1/lower=0/upper=1，`tree.rs:412-446`），oak JSON 通常无 `min_clipped_height` → 验收实际为 `o >= i`，结合 `o ≤ i` **强制 o == i**。
- **判定：一致。关键推论：Java 侧最终摆放长度 = o = i（getHeight 值），不存在「同高度摆不同根数」的语义空间。**

### ③ trunk 摆放循环上界
- Java `TreeFeature.java:80`：`trunkPlacer.generate(world, ..., random, o, blockPos, config)` —— **传入的是 o 不是 i**；`StraightTrunkPlacer.java:35-37`：`for i in 0..height`（即 0..o），每层 1 次 `getAndSetState`。straight 无 additional length（那是 LargeOak/MegaJungle 的语义）。
- Rust `tree.rs:520-528`：`for iy in 0..o`，同序（setToDirt 先于柱体，`StraightTrunkPlacer.java:33` ↔ `tree.rs:521`）。
- **判定：一致，两侧都摆 o 根（attempt）。**

### ④ canReplace/setToDirt 对摆放次数/消费的影响
- `TrunkPlacer.java:62-66` setToDirt：`forceDirt || !canGenerate` 才放 dirt（`dirtProvider.get` 1 次消费仅在放置分支）↔ `tree.rs:626-639` 同构。
- `TrunkPlacer.java:80-86` getAndSetState：`canReplace` 失败 → 跳过且**不消费 trunkProvider** ↔ `tree.rs:523-527` 同构。
- **判定：一致。canReplace 失败只会减 log、永不会加；不影响 RNG 流的两侧对齐结构。**

## 二、判别问题回答（必须项）

**若 java getHeight 抽样值与 rust 同为 6，java 会不会摆 7 根 log？—— 不会。**
链条：getTopPosition 返回值恒 ≤ i（TreeFeature.java:95-108）；oak 无 min_clipped_height 时验收要求 o ≥ i ⇒ o == i == 6；StraightTrunkPlacer 循环 `0..o` 恰摆 6 attempt（每 attempt 最多 1 根 log）。即使 canReplace 中途失败也只会 <6。**不存在任何路径使 java 以 i=6 摆出 7 根。**

因此：java 实测 7 根 ⇒ **java i = 7**。由此推论：

- **java i=7 → 分叉在 getHeight 的两次抽样本身（或之前），不在 top-position/trunk 摆放语义。假设 .bA 的「语义差」主张被削弱/否证**（精确表述：分叉点 ≤ getHeight 抽样，摆放语义差被静态排除）。
- 但注意：`get_height`（tree.rs:99-108）源级与 Java 逐字同构、且 tree1 base 对齐说明流在此之前一致——若 java=7 / rust=6，剩下三个互斥子嫌疑（供主会话收敛/fan-out .bN 参考，非本候选职责）：
  1. **config 值错位**：rust 解析 oak trunk_placer 的 `height_rand_a`/`height_rand_b`（tree.rs:86）取到的值 ≠ java 实际 JSON（如字段缺省/别名导致 f() 默认 0，或 oak/birch 两 configured feature 载入混淆）；
  2. **next_int_bound 与 nextInt 的 bound 语义差**（仅在该两次调用暴露——但 placement 大量 nextInt 已对齐，先验低）；
  3. **getHeight 之前的隐藏消费点差**（species 选择/weighted provider 等同树内更早消费，数量相同但值不同不成立——值不同会连 base 后续一起漂移；数量差才会只在这里分叉）。
- ⚠️ 佐证注：树 2 起 base 全部错位与「java i=7 / rust=6」自洽（7 树干多 1 次 trunkProvider 消费 + foliage 消费差，流即刻漂移）；若只是摆放语义差（流不分叉），树 2 起不会错位——这独立削弱 .bA。
