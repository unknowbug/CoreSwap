## 1. 子候选判定

### bB-1 树种类 selector 消费语义 — **不存在该差（draft）**

- Java RandomFeature.java:23-29：逐 entry `random.nextFloat() < chance` 即选即返；全落空走 defaultFeature（不再抽选择 RNG）。
- Rust feature_loader.rs:393-413：同语义同顺序（L398-404 逐项 `next_float() < chance` 即选即返；L405-410 default 不抽）。
- 消费次数两侧恒等：命中第 k 项 = k 次 draw，全落空 = 2 次 draw 后 default，逐字对应。
- fancy 排除：见 §0（观测形态 + 配置）。种类差（java oak vs rust birch）理论不改 trunk 长度公式（oak/birch placer 参数 4,2,0,2 vs 5,2,0,2——**注意 birch base_height=5, oak=4**，若两侧选了不同种类，getHeight 分布不同且消费次数同为 2，流不漂移但期望高度漂移——本例只差 1 且需 [SEL]/[TRUNK] 探针排除，见 §3）。
- 结论：selector 级语义差不存在；「种类选差」不可由静态排除，降级为探针待证项（非本族主嫌）。

### bB-2 block provider 单状态消费差 — **不存在该差（draft）**

- Java SimpleBlockStateProvider.java:25-27：`get` 恒返回常量，**0 消费**；WeightedBlockStateProvider.java:35-37：`states.getDataOrEmpty(random)` = 1 次 nextInt(totalWeight)。
- Rust tree.rs:49-64：Simple 0 消费 / Weighted 1 次 `next_int_bound(total_weight)`，同语义。
- 树1 配置（oak_bees_0002 / birch_bees_0002）的 trunk/foliage/dirt 全为 Simple（§0），provider 全程 **0 消费**，两侧一致 → 本例分叉不可能出自 provider。Weighted 路径语义也对齐（非本例）。
- 推论：**trunk 循环里 canReplace 门 false 跳过的格子不产生 RNG 消费差**（provider 0 抽），即「树1 少一节 log」本身**不漂移**树2 的流。

### bB-3 REPLACEABLE_BY_TREES 硬编码子集 — **硬编码集合成员等价（不存在差），但 can_replace 世界状态依赖是 6vs7 的最可能形态（draft）**

- Java TreeFeature.java:53-55 `canReplace = isAir || isIn(REPLACEABLE_BY_TREES)`；1.20.1 tag 成员 = air, water, snow, grass, fern, dead_bush, hanging_roots, vine, glow_lichen, light, tall_grass, large_fern。
- Rust tree.rs:289-297 硬编码清单与上完全对应（多写 `short_grass` 为 1.20.6+ 改名，1.20.1 注册表里多余但无害；grass_block 正确地**不在**集合）。静态判定：**集合成员无差**。
- 但 can_replace 依赖**世界当前状态**：树1 处 java 有 grass_block（setToDirt 分支可处理）而树冠/干域可被 p<20 已执行 feature（forest_flowers p=17、patch_grass）产物占据。若 rust 侧 (602,78,-244) 有一格非 replaceable（先行 feature 产物差或任何世界状态差），trunk 循环（Rust tree.rs:522-528 ↔ Java StraightTrunkPlacer.java:35-37，均 getAndSetState 门 + 0 消费 provider）就少放一节 → **6 vs 7 且流不漂移**（结合 bB-2 推论）。这与「树1 base 一致」不矛盾（base 在 generate 前）。
- setToDirt：Java TrunkPlacer.java:58-66 ↔ Rust tree.rs:626-640（isSoil−grass−mycelium 门）语义一致，0/1 次 dirt_provider.get（Simple=0），无差。
- getTopPosition：Java TreeFeature.java:92-109 ↔ Rust tree.rs:610-623，均 0 消费；oak TwoLayers(1,0,1) 无 min_clipped → 若 rust 侧低层受阻会 o<i → 直接 return false（无树），与观测（rust 有 6 log）不符 ⇒ 树1 的 o=i，**6vs7 只能出自 getHeight 差（流已漂移）或 y=78 格 can_replace=false**。

## 2. 关键静态新发现（.bB 范围外，建议转交主会话收敛）：BeehiveTreeDecorator 在 Rust 侧 0 消费

- Java：oak_bees_0002/birch_bees_0002 均带 BeehiveTreeDecorator（TreeConfiguredFeatures.java:544,547 + :290,291），generate **恒 1 次 nextFloat**（BeehiveTreeDecorator.java:43，命中才继续抽）。
- Rust：TreeDecorator::parse（tree.rs:315-328）不识别 "beehive" → Unsupported（仅 eprintln）；generate（tree.rs:398）no-op，**0 消费**。
- 后果：**每棵 oak/birch 树 rust 少抽 1 次 nextFloat**，从树1 的 decorator（在 trunk/foliage 之后执行，TreeFeature.java:151-155 顺序）开始漂移 → 与「树1 trunk 观测点之前一致（base/前段 log 对齐）、树2 起 RNG 流漂移」的时间结构吻合。⚠️ 但它**解释不了树1 的 6vs7**（decorator 在 trunk 之后）；6vs7 仍需 §1-bB-3 形态或 getHeight 上游漂移解释——而若树1 前已有树0（同带 bees decorator），树0 的缺抽会使树1 的 getHeight 输入流已漂移 → 7vs6 直接成立且树1 base 仍一致（base 在树0 decorator 之前抽）。**该假设一条链同时解释两个观测，当前为 .bB 全局首选机制**（draft，待 [BEE]/[TH] 探针裁决）。
- 注：树1 base 一致要求树0 的 [SQ] 抽样在树0 generate 完成前——vanilla 逐站点「抽位置→generate」顺序下，树1 base 在树0 generate（含 decorator）之后抽，若树0 也是 bees 树则 base 应漂移；因此要么树1=第一棵树（则 6vs7 另需 bB-3 形态 + decorator 缺抽共同作用），要么站点位置抽样批处理顺序与 rust 不同——**探针 [SQ]/[BEE] 时序须一并对拍**。

## 4. 结论（draft）

- bB-1 selector：**语义差不存在**（RandomFeature.java:23-29 ↔ feature_loader.rs:398-410 逐字对齐）；种类选差留探针。
- bB-2 provider：**差不存在**（Simple 0 消费两侧一致；Weighted 亦对齐；树1 配置全 Simple）。
- bB-3 replaceable：**硬编码集合成员等价**（tree.rs:291-295 vs 1.20.1 tag），但 can_replace 世界状态依赖可产生「少一节 log 而不漂移」形态，是 6vs7 的候选形态之一。
- **附送发现（范围外，优先级最高）**：rust 漏实现 BeehiveTreeDecorator 的恒 1 次 nextFloat 消费（BeehiveTreeDecorator.java:43 vs tree.rs:315-328/398 no-op）——每棵 bees 树必漂移，与树2 起漂移的时间结构吻合；一条链可同时解释两观测（待时序探针确认）。
