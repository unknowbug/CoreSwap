## ① BlockPredicate 字段名错读 → 全部方块谓词解析为 Unsupported（树放置全灭）【本块最重】

### 现象
树 feature 全链路「正常」——configured/placed 加载无崩溃、树 dispatch 全通、日志无报错——但**零放置**：树 would_survive 全灭、random_patch 的 air 过滤（predicate 条件）全灭，受控 A/B 树族残差纹丝不动。且该 bug **长期未暴露**：skip 类告警只在树放置路径打印，服务器正常 run 时无人走到该路径，静默带了多个工作块。

### 根因（机制层面）
`placement.rs` 解析 BlockPredicate 时读的字段名是 **`"predicate_type"`**，而 1.20.1 vanilla JSON 里实际键是 **`"type"`**——字段永远取不到 → 每个方块谓词都落到 fallback 分支解析为 `Unsupported`。下游连锁：① 树放置的 would_survive 检查（BlockPredicate predicate）恒失败 → 不种；② random_patch 的 patch air 过滤（would_survive air predicate）恒 false → patch 内全部 skip。本质 = **对数据格式的字段名凭印象写而未对一手 JSON 校验**——语义层（谓词结构）理解对了，字面键名错一个词全灭。

### 定位（怎么发现的——完整定位链，五段跳）
1. **字节一致假象**（先被 bug ⑤ 污染）：修复前后 dump 逐字节一致 → 误判方向跑偏一轮（先破除 #23 rlib 陈旧假绿才有的真起点）。
2. 排除陈旧 rlib 后，`[nested]` 诊断日志显示 **unknown configured id** → 指向 feature 加载层。
3. placed/configured 语义修正：generate_nested 里两者的角色接反/未接线 → 修正后树 dispatch 全通。
4. **树 dispatch 全通但零放置** → 矛盾点收窄到放置判定内部。
5. 谓词解析枚举 **Discriminant 追踪**（对解析结果打标看落到哪个分支）→ 实锤全部谓词落 `Unsupported` → 回查字段名 → `"predicate_type"` vs `"type"`。

### 修复
`placement.rs` 谓词解析字段名 `"predicate_type"` → `"type"`；谓词解析从 Unsupported fallback 变为主路径。

### 教训
1. **判据：数据驱动解析的新分支，首验必须拿一手真实 JSON（data/ 下真实数据文件）跑通，禁止凭印象写键名**——字段名是字面契约，语义对≠键名对。
2. **「全灭但无报错」+「告警只在特定路径打印」= 静默腐烂组合**——fallback 分支（Unsupported/skip）必须有无路径前提的全局可见信号（计数器/汇总行），不能只藏在触发路径日志里。
3. Discriminant/枚举分支打标是「解析全落 fallback」类 bug 的通用定位器（一次打标直接看到分布）。
4. 起点是「字节一致」时先破除构建陈旧（#23），否则定位链整体在假象上打转——本条与 ⑤ 互为因果。

## ② selector default 键错读

### 现象
random_selector 特征的 default（fallback）feature 分支行为不符预期，selector 类树（如随机选 oak/fancy_oak）选择结果与 vanilla 不一致。

### 根因
random_selector JSON 的 default feature 键名/结构读错（默认分支取不到 → 走了错误 fallback / 空），与 ① 同族：**字段面凭印象、未对一手 JSON 校验**。

### 定位
谓词/selector 解析统一打标追踪 + 对照真实 JSON 文件的键集合（与 ① 同一诊断轮发现）。

### 修复
按 1.20.1 真实 JSON 键名修正 selector default 解析。

### 教训
与 ① 合并记：**同一天同族两犯（键名凭印象）= 解析层系统性缺口**——判据升级为「任何新 JSON 消费点落地前，grep 一手 data JSON 确认键集合」，防第三犯。

## ③ generate_nested 的 placed/configured 语义接反

### 现象
树 feature dispatch「通」但行为不对（与 ① 纠缠，最初表现为 unknown configured id 日志）。

### 根因
`generate_nested` 处理链上 **placed feature 与 configured feature 的语义角色混淆**——placed（含 placement modifier 链 + 索引到 configured）与 configured（纯 placer + 状态提供）两级各自职责被接反/未正确穿透，导致 lookup 用错层级 id。

### 定位
`[nested]` 日志的 unknown configured id → 回溯 lookup 调用点 → 核对 vanilla FeatureSelector/NestedFeature 语义（placed 是 generator 链入口，configured 是叶子）。

### 修复
generate_nested 按 vanilla 语义重排：placed 解析 modifier 链 → 终结于 configured 的 place。

### 教训
**两级 feature 体系（placed/configured）是 1.18+ worldgen 的固定语义结构**，接手/移植时先把两级职责图写下来再写代码——层级语义错比字段名错更隐蔽（不报错，只行为怪）。

## ④ heightmap off-by-one

### 现象
树/表面相关放置的 Y 高度系统性差 1（off-by-one），特定地形下树悬空/嵌入一格。

### 根因
heightmap 查询的**边界语义差一**：`Heightmap.Types` 的 motionBlocking 类语义是「最高阻挡方块 Y + 1 = 放置面」还是「最高阻挡方块 Y 本身」取错——off-by-one 的经典机制（边界含斥搞混），不是精度问题。

### 定位
对拍真实 chunk 的表面 Y 与查询结果逐点 diff → 稳定 ±1 → 锁定边界语义而非采样逻辑（「符号/常数级小差异 = 结构/边界错，不是精度错」判错经验复用）。

### 修复
按 vanilla `HeightmapTypes` 语义修正 +1 约定位置。

### 教训
**「稳定差 1」= 边界含斥/开闭区间语义错的标准签名**——直接对照一手语义定义（Java 源码该类型注释与使用点），不要在采样实现里找精度。

## ⑤ cargo -p 依赖 rlib 陈旧 → 逐字节一致假象（详见 build-tooling 草稿 #23）

### 现象
修复后 `cargo build --offline -p worldgen` 多次 `Finished`，产物正常，但 dump 与修复前**逐字节一致**；`libWorldgenRust.rlib` mtime 停留数小时前；exe/rlib 字符串核验新日志串缺失。

### 根因
`-p worldgen`（薄壳 cdylib）作构建根时依赖包 WorldgenRust 的 rlib 漏判过期未重编——新旧代码链同一陈旧 rlib。

### 定位
字节一致 → 核产物链 mtime → rlib 早于源码数小时 → 字符串核验实锤。

### 修复
显式 `cargo build -p WorldgenRust`；判据 = rlib LastWriteTime 晚于源码 mtime。

### 教训
「构建绿 + 产物在盘 + 运行成功」三绿仍可全假——中间产物 mtime + 内容指纹才是证据。完整展开见 `knowledge/discovered/build-tooling.md` #23（草稿）。**本条是 ① 的污染源：先破此关，① 的定位链才能起步。**
