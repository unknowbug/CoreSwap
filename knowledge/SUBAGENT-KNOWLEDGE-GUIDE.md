## 一、错误优先原则（最高优先级，用户 2026-08-13 明确）

**错误信息 + 详细记录「为什么错」才是最重要的资产，比验证通过的正确结论更重要。**

1. 排查中遇到的**每个错误/踩坑** MUST 按五段式完整记录，不得只记「已修复」而不记「为什么错」。
2. 错误台账的**详实度要求高于一切正确结论**——正确结论只记「是什么」，错误链条要记「不是什么 + 为什么」。
3. **被排除的假说同样保留**（❌ 在主题篇留一行排除清单；完整链条进错误台账/时间线）——排除链条是核心资产，防重走弯路。
4. **判错经验尤其要记**：可复用的判错方法（如「符号级错误一定是结构错不是精度错，先查公式/索引/坐标，别在精度上纠结」）必须沉淀，比单条错误更有价值。

## 二、五段式错误记录格式（每条错误 MUST 完整）

| 段 | 内容要求 |
|---|---|
| **现象** | 具体数据/表现（报错原文、数值、波形、输出片段），禁止笼统描述 |
| **根因** | 为什么错——机制层面（对象搞混/索引错位/语义差/常量传播…），不是表面现象复述 |
| **定位** | 怎么发现的——诊断方法/工具（减法二分、ref_probe 对拍、spirv-dis、grep 断言…） |
| **修复** | 改了什么（文件+逻辑+为什么这样改能修） |
| **教训** | 下次怎么避坑 + 可复用判错经验 |

**反模式**（绝对禁止）：
- ❌ 只写「已修复」不写根因机制
- ❌ 现象=根因（把表面表现当原因）
- ❌ 无定位过程（「改对了」但说不出怎么发现的——下次同类错误无法复用）

## 三、知识库载体映射（CoreSwap 项目实际结构，非 skill 通用 errors/ 目录）

| 内容类型 | 载体 | 说明 |
|---|---|---|
| **错误台账**（排查中每个错误） | `.investigations/perf-rework/gpu-accel-errors.md` 等独立成篇 | 按 A-G/D 系列编号（GPU 课题）或项目相关编号；**独立成篇不散落**；末尾附「错误→根因」速查表（一页索引） |
| 结论/已验证/修复 | `versions/1.20.1/docs/` 01-09 主题篇 | 追加小节，**追加不覆盖**；被排除假说只留一行 ❌ 排除清单 |
| 排查过程/中间结论/被推翻假说/工具演进 | `versions/1.20.1/docs/10-timewise-archive.md` | 时间线追加，每条带状态 ✅/❌/🔍/已结案 |
| 通用可复用模式（跨版本/跨项目） | `knowledge/discovered/`（INDEX.md 入口） | 按 core-knowledge 的「发现 #N」格式，写后同步 INDEX |
| 过程性中间产物 | `.investigations/` | 主会话可写，非结论性 |
| 结论性 docs/discovered | subagent 产出草稿 → 主会话应用 + 验证 | 强制触发点（AGENTS.md 九） |

**载体纪律**：
- 主题篇（01-09）禁止新建时间线式章节（时间线只进 10）；
- 错误台账独立成篇（如 gpu-accel-errors.md），不与正确结论混写；
- 交接文档唯一 `NEXT_SESSION.md`（仓库根，不入库），禁止在子目录建交接副本。

## 四、产出检查清单（subagent 交付前自检）

- [ ] 每个错误都有五段式（现象/根因/定位/修复/教训），无「只记修复」条目
- [ ] 根因是机制层面（为什么错），不是现象复述
- [ ] 定位含诊断方法/工具（可复用）
- [ ] 判错经验已沉淀（有则必写）
- [ ] 被排除假说有标注（❌/⚠️），未删除
- [ ] 写入载体正确（错误→错误台账 / 结论→主题篇 / 过程→时间线 / 通用→discovered）
- [ ] 错误台账末尾速查表已同步（新增错误加一行）
- [ ] 数字来自主会话提供的实测记录，无编造、无占位符
- [ ] 格式与目标文件末尾现状对齐（先读目标文件末尾再写）
