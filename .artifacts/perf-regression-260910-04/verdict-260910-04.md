## 1. 结论（按命题拆分，措辞随证据强度分层）

**命题 A（并发结构，直接实测）**：我们的 mixin 在 `NoiseChunkGenerator.populateNoise` HEAD **同步**完成整 chunk 的 Rust 生成 + 写回，而 1.21.6 世界生成的所有 `ChunkLoader.run()` 都跑在**唯一一条** `SimpleConsecutiveExecutor("worldgen")` 上、`ChunkTaskScheduler` **同时只允许 1 个 entry 在飞**（b1 一手源码 `ServerChunkLoadingManager.java:192,196` + `ChunkTaskScheduler.java:68-84`）→ **实测：同时刻在飞的接管段数峰值恒为 1**（`[CHUNKTIME] … | inflight max=1`，完整 run `cmd-output/ct1-inflight-r2.log`，n 从 256 递进至 4608 全程为 1，23 个 Worker-Main 可用）。即**世界生成并行度 = 1**（该命题为实测直证）。
> 限定：in-flight=1 不区分「车道被我们占满」与「上游 ticket/限流喂不进来」，后者未排除（b1 @idk 之 `ThrottledChunkTaskScheduler maxConcurrentChunks` 线）。

**命题 B（wall 归因，同批同 run 推断）**：coreswap 的 wall ≈ **车道内串行工作之和** → 吞吐 = 1/Σ。**同一次 run**（`ct1-inflight-r2`，Total 0:04:24=264s，wallgen 270.3s）实测 **Σ = sumMixin 232.4s + sumCarve 5.4s + sumFeat 11.4s = 249.2s → Σ/wall = 92.2%**（对 wallgen）/ 94.4%（对 Chunky Total）。vanilla 同仪器（`vt1-r1`）Σ = 0 + 3.9 + 13.1 = 17.0s vs wallgen 60.1s（28%）——vanilla 的重活不在车道里。
> 措辞保留：**不得写「并行度精确 = 1.000」「wall 就是结构下限本身」**；Σ/wall 的 92% 是推断性归因（差 8% 未归因），且每 chunk 工作量本身跨 run 漂 ±10-12%（见 §6 口径）。

**vanilla 的对照形态**：`populateNoise` 返回 `CompletableFuture.supplyAsync(..., Util.getMainWorkerExecutor().named("wgen_fill_noise"))`（`NoiseChunkGenerator.java:331-352`）→ 车道只做 µs 级调度，47ms 级重活交给 23 线程池。

**推论（对修复方向）**：池大小调参 / JNI 微优化 / Rust 内部并行都不会改变这条链（并发恒为 1）；唯一方向是把重活**移出车道**（异步形态对齐 vanilla）。

## 3. 修复方向（candidate，待用户批准 H4 后实施）

**R3（核心）：把接管段移出 worldgen 车道——对齐 vanilla 的异步形态。**
- 现状：HEAD 同步 `fillChunk()` 后 `cir.setReturnValue(CompletableFuture.completedFuture(chunk))` → 47ms 重活留在车道内。
- 目标：HEAD 只做调度——把 `feedBeardifier + fillChunk + writeChunk` 提交到工作池（如 `Util.getMainWorkerExecutor()`，命名通道对齐 `wgen_fill_noise`），返回该 future；车道零重活。
- 预期：wall 从 234-283s 降到与 vanilla 同阶（~53-90s）；若 Rust 段 47ms 优于 vanilla 同段，有望**快于 vanilla**（属预期，非既有实测）。
- 必防：① future 完成时机 = vanilla 的 chunk 状态推进语义；② `writeChunk` 在池线程内调 Chunk API → 核 **ChunkSection 锁语义**（vanilla 在 NOISE 内显式 lock/unlock 24 个 section，`NoiseChunkGenerator.java:336-348`；b2 @idk-10 未闭合）；③ 行为等价门（同 seed/region 双臂逐格对拍 + hash 哨兵）；④ 端到端复测同口径。

**R1（已落地）**：per-chunk mixin `System.out.println` 门控化（1.21.6 + 1.20.1 双版本；默认关、`-Dcoreswap.mixlog=1` 开）。**效果表述降级（judge C4）**：方向确定（消除了每 chunk 2 行同步 log4j 写，生产 jar 同类收益），**量级未离噪声带**（268s→234s 为跨 dll（`5e30187a`→`abd7d889`）+ 跨批 + 单次对，落在本轮 ±20% 摆动与项目 ±10% 噪声带内）→ 需同批 ABBA ≥3 对才能给量级。

**观测面（已落地，默认关/行为等价）**：`[WG-CONF]` 一次性配置行（Rust）；chunk 级分段计时 `-Dcoreswap.chunktime=1`（mixin/JNI/write/hmap/scan/beard/gap/carve/features/臂无关每 chunk 间隔/`inflight` 并发计数）；gradle 映射 `-Pmixlog / -Pchunktime / -PmaxBgThreads / -PcaMin / -PestL2 / -PcaCap`。

3. **异常面收窄（judge C4）**：mixin 层 future 异常由 `AbstractChunkHolder.java:69-77`（CrashReport + `setWorldGenException`）接走、车道不停摆（`ChunkTaskScheduler.java:79-84`）——比本节自述更强；但 `CppBridge.fillChunk/feedBeardifier` 内部仍有 catch 后 print+return 的吞点（`CppBridge.java:360-362,383-391,403-405`，**既有行为、非 R3 引入**）⇒ 端到端「不吞异常」尚不成立，列为技术债。

**判据（可复用·验证三件套）**：接管类优化（把重活从被串行化的执行点搬到工作池）MUST 用三件套收口——① 同构建态**单变量** A/B（旧形态留开关，背靠背同批）；② **并发度直读**（in-flight 计数：1 → N）；③ **行为等价门**（逐块对拍，与既有 run 级噪声基线同量级即可，非零容忍）。

**confirmed 后第一优先收口（judge C7）**：① `pending_cross_writes` 跨 chunk 写序会计（异步序下的正确性核验，不利则按 §15.4 取代）；② 同配置 run-to-run 基线对（补等价门代理缺口）；③ ABBA ≥3 对给 R3 幅度置信区间。
